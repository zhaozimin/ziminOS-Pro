# 第三方组件

ziminOS 把查询、大纲、列表编辑、外观组件与系统插件统一交付。大多数上游仍以独立运行文件或资产交付；v0.15.0 起，Pikaicons 路径数据、lunar-typescript 农历算法与 holiday-cn 格式的当年节假日快照会编译进 `main.js`。三者的 MIT 声明同步写在每份构建产物顶部。下列版本、上游、许可与升级边界是供应链事实源；更新前必须重新构建、真机验收并更新本文。

## lunar-typescript

- 版本：1.8.6（`package.json` 精确锁版）
- 上游：https://github.com/6tail/lunar-typescript
- 许可证：MIT，Copyright (c) 2020 6tail
- 交付形态：随 `main.js` 编译分发，许可声明住在 `esbuild.config.mjs` 的 banner
- 用量：日历仅调用 Solar / Lunar 转换以得到农历日名、传统节日与二十四节气；不调用其 HolidayUtil

HolidayUtil 的假日表是发版时的静态数据，不能回答「明年国务院新公告后怎么无感到库」。农历算法与调休事实因此分层：前者是本地确定性换算，后者交给 HolidayService 缓存并更新。

## holiday-cn

- 数据格式/上游：https://github.com/NateScarlet/holiday-cn
- 许可证：MIT，Copyright (c) 2019 NateScarlet
- 数据性质：上游持续集成从中国政府网的国务院办公厅通知生成按年 JSON；记录的是法定休息与调休上班例外，普通周末由 ziminOS 本地计算
- 远端镜像：`cdn.jsdelivr.net` → `fastly.jsdelivr.net` → `raw.githubusercontent.com`，按顺序尝试，不并发洪泛
- 内置快照：v0.15.0 内置国务院 2026 年放假通知的 39 个例外日，即使首次启动断网也能显示当年休/班
- 运行时缓存：`<笔记库>/.obsidian/plugins/ziminos/holiday-cache.json`，只在数据通过年份、ISO 日期、重复日与 `gov.cn` 公告链接校验后覆盖

日历打开或切换年份时检查「显示年 + 下一个公告年」，24 小时内复用缓存。无定时器、无轮询；全部镜像失败时安静保留最后一份好数据。上游是事实源之一而不是唯一生命线，所以不需要为此再建用户手工维护的网站。

## Pikaicons

- 版本：免费集（`pikaicons@0.0.5`，2023 年发布，与 pikaicons.com 上 V2 系列同一套画法：24 格、2 宽描边、圆头圆角）
- 上游：https://pikaicons.com
- 发布：https://www.npmjs.com/package/pikaicons ・ 源码 https://github.com/girishsawant999/pikaicons
- 许可证：MIT，Copyright (c) 2022 Mau Joost
- 交付形态：**不作为独立文件交付**。三十二个图形的 path / shape 数据以 TypeScript 常量住在 `src/modules/ribbon/icons.ts`，随 `main.js` 一起编译分发；许可声明写在 `esbuild.config.mjs` 的 banner 里
- 用量：三十个命令图标 + 两个设置页专用图标（dock 与 explorer）。十六个源于免费集原图，其余由 ziminOS 复用原图的几何原语补画；日历图标在日记日历框内添加网格，与同组笔画一致。图标服务命令面板、左侧边栏与八张设置标签页

选它而不是继续用 Obsidian 内置的 lucide，理由只有一条：三十条命令要一眼分得清彼此。lucide 是 Obsidian 界面自己在用的图标库，ziminOS 的图标混在里面会与「新建笔记」「搜索」这些系统按钮长得一样，学员分不出哪几个是这套系统的。换一套画法，那一列就自成一体。

不进 `.gitattributes` 的锁定名单：它不是从上游原样落地的发布资产，而是被抄进源码的一串坐标，Git 的换行处理动不了它；它的正确性由 `npm run build` 之后肉眼看那一列图标来保证。升级边界：上游改版不会自动影响我们——已抄进来的坐标就是事实源。要跟进新版必须重画一遍并重新肉眼验收，因为补画的那八个必须与新版原图仍然成套。

## Obsidian 平台已知渲染缺陷：短代码块的编辑态行装饰（1.13.7）

现象：Live Preview 下，光标进入一个**总长不足 20 字符**的受渲染代码块（从开栏 ``` 数到收栏 ```，含围栏与换行）时，只有开栏线带代码块样式，内容行与收栏线渲染成裸正文——底色、行号片段一并失效；随便敲一个字即恢复。ziminOS 的视图块（```ziminos + 四字视图名 = 19 字符，待办 = 17）几乎全部落在阈值之内，学员点进视图块就会看见这个残缺态。

根因（读 1.13.7 app.js 逐层确认）：CodeMirror 计算可见区时把小于 20 字符的块替换装饰当普通文本（`RangeSet.spans` 的 `minPointSize=20`），于是短块被 widget 覆盖期间源码仍算「可见」；Obsidian 的行类装饰插件在此期间用 `lineBlockAt` 把被盖住的几行折叠成同一个 line block，其单调游标只给第一行发出行装饰。光标进入后 widget 消失，但可见区没变、语法树也没变，两个重建触发条件都不满足，残缺装饰便滞留到下一次编辑（编辑改变语法树，强制重建，所以「打一个字就好」）。≥20 字符的块在 widget 期间源码被真正抠出可见区，光标进入时可见区变化触发重建，因此一次就对。

定性：Obsidian 核心缺陷，与 ziminOS 无关——原生 query 块（```query + foo，16 字符）在零插件的库里即可复现，Dataview 同样中招。语法树本身完好（三行的行类节点在树里一个不缺，实测转储确认），故阅读视图、导出、数据检索一概不受影响，纯编辑态观感问题。截至 2026-08-13，1.13.7 为最新版本，上游未修、论坛未见对口报告。

处置：暂不在插件侧硬修。仿造行装饰需要照抄 HyperMD 行类这套内部契约（registerEditorExtension 虽是公开 API，抄的类名不是），为一个上游迟早要修的观感缺陷引入永久耦合，不值。上游报告已于 2026-08-13 提交 forum.obsidian.md 的 Bug reports 版块并已过审：https://forum.obsidian.md/t/live-preview-rendered-code-blocks-shorter-than-20-characters-lose-line-styling-when-the-cursor-enters-them/117301 （含沙盒最小复现、16/22 字对比截图与机制分析）。Obsidian 出新版后先看这一帖有没有官方回应，再用 ```query + foo 探针实测；学员侧的口径是「点进视图块看到源码没有底色，是 Obsidian 的已知问题，打一个字就恢复，数据无恙」。

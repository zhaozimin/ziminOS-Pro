## 0. 总则

### 0.1 V2 要长出来的东西

初始化后学员的库里直接站着两套系统：**人脉管理**（谁在变冷、谁欠谁人情、谁该送礼）与**复盘**（日→周→月→季→年一条主题链）。客户与付费是第三套，不进默认初始化，由一条独立命令按需长出。

### 0.2 四条已拍板的路线（不再讨论）

| # | 决定 | 理由 |
|---|---|---|
| 1 | **视图由插件自渲染代码块**，不用 DataviewJS | 笔记里只留一行块名，逻辑全在 `main.js`；升级即全库生效，学员改不坏；DataviewJS 保持上游默认关闭，V1 规格 §3 不破 |
| 2 | **人脉+复盘进初始化，客户由命令按需长出** | 大多数学员不做生意，默认不给六张永远空着的销售表 |
| 3 | **新增 `05-diary`，根目录变七个** | PARA 四象限分的是「东西属于谁」，复盘分的是「什么时候发生」；两种坐标轴不塞进同一格 |
| 4 | **日主题建笔记时不问，由命令回填** | 主题是对一天的结论，早上答不出；实测强制弹自由文本 34/34 收到「123123」类垃圾，而垃圾能通过一切非空校验 |

### 0.3 三条红线在 V2 的具体含义

1. **人主导**：视图只在代码块被渲染时计算，重算由 `metadataCache` 变更事件触发，**不得引入任何 `setInterval` 轮询**（Dataview 的 2500ms 刷新正是我们不采用它的原因之一）。
2. **脚本驱动**：日记模板的**天气块整体删除**——它 `fetch` 三个 Open-Meteo 接口，插件内零网络请求不可破。地点/天气/温度三个字段一并从模板移除，不留空键（空键是登记表，不是索引）。
3. **只用官方公开 API**：视图引擎只允许用 `metadataCache.resolvedLinks`、`metadataCache.getFileCache().listItems/frontmatter`、`metadataCache.getFirstLinkpathDest`、`vault.cachedRead`、`MarkdownPostProcessor` / `MarkdownRenderChild`。**禁止** `getBacklinksForFile` 等未在 `obsidian.d.ts` 导出的内部方法。

### 0.4 V2 顺手关掉的两个缺口

- **`archived` 字段缺失（必修）**：`transitions.ts` 当前只写 `status`（`transitions.ts:287`），归档时刻无处可查。归档又走 `guard.mark`，`updatedMaintainer` 被自写抑制，连 `updated` 都不刷——「本月完成的项目」会把完成日记到学员最后一次手打该笔记的月份。修法见 §5.4。
- **`90-system/系统配置.md` 不再需要**：它存在的唯一理由是库内 dataviewjs 读不到插件设置。视图搬进插件后直接读 `ctx.settings.archiveFolder`，位置依赖彻底收敛到设置页，该文件不生成、不提及。

## 2. 视图引擎（V2 的核心新架构）

### 2.1 分层与归属判据

沿用 `core/CLAUDE.md` 的既有判据——**谈业务概念的归 modules，只谈文件事实的留 core**：

```
core/vaultIndex.ts   反向链接索引、列表行读取、字段读取        ← 不认识「人脉」
core/table.ts        表格 / 空态 / 提示的 DOM 渲染             ← 不认识「人脉」
core/codeblock.ts    ziminos 代码块解析、分发、生命周期与重算  ← 不认识「人脉」
core/markdown.ts     往指定小节里插一行（落地新增）            ← 不认识「人脉」
core/time.ts         日粒度口径与五级周期算术（扩充）          ← 不认识「人脉」
modules/*/…Views.ts  口径与语义（谁算超期、账本行怎么分段）    ← 业务全在这里
```

**落地差异一 · 新增 `core/markdown.ts`。** 三条命令都要往既有笔记的某个小节里追加一行（记人情写进日记、增加付费写进客户档案、记收款写进项目 MOC），规则完全一样。规则只该存在一份，而它不谈任何业务概念，所以归 core。

### 2.2 `core/vaultIndex.ts`

```ts
export interface ListLine {
    text: string;            // 去掉列表标记后的整行文本
    isTask: boolean;
    checked: boolean;
    links: string[];         // 行内 wikilink 的原始 linktext（未解析）
    line: number;
}
export class VaultIndex {
    backlinksOf(file: TFile): TFile[];
    resolve(linktext: string, sourcePath: string): TFile | null;
    listLinesOf(file: TFile): Promise<ListLine[]>;
    invalidate(): void;
}
export function dayOfFile(file: TFile): string | null;   // 文件名恰为 YYYY-MM-DD 才有值
```

四条必须写进实现的约束：

1. **反向索引一次构建，全渲染周期共享**。`resolvedLinks` 是 `Record<源, Record<目标, 次数>>`，逐个档案去正查是 O(人数 × 全库)。改为**一次遍历建 `Map<目标路径, TFile[]>`**，缓存到下一次 `metadataCache` 变更为止。这是 V2 唯一的常驻缓存，且由事件失效，不是轮询。
2. **行级链接必须经 `resolve()` 比对路径，禁止字符串匹配**。`listItems` 只给位置不给文本，链接更是原始 linktext；`[[张三|老张]]`、`[[人脉/张三]]`、`[[张三#约定]]` 三种写法指向同一文件。移植源 `person-ledger.js` 用正则拼文件名规避此事，V2 用 `getFirstLinkpathDest` 做得更正确——**这是允许优于原脚本的一处**。
3. **`listLinesOf` 靠 `cachedRead` 取文本，按 `listItems[].position` 切行，结果按 `file.stat.mtime` 缓存**。调用方永远只对「反链指向我的那几篇日记」调用它，不扫全库。
4. **`dayOfFile` 只认文件名，不认文件夹**。全库唯一的日记判据，与演示库口径一致（学员挪走 `05-diary` 也不坏）。

### 2.3 `core/codeblock.ts` 与块语法

学员在笔记里写的是：

````markdown
```ziminos
人脉名录
```

```ziminos
主题链
范围: 周
```
````

- **单一语言标记 `ziminos`**，第一非空行是视图名（中文，学员读得懂），其后每行一个 `键: 值` 参数，半角/全角冒号都接受。
- 未知视图名 → 渲染一行友好提示 + 当前可用视图清单，**不抛异常、不留白块**。
- 每个块包成 `MarkdownRenderChild` 并交给 `ctx.addChild()` 托管；`onload` 内订阅 `metadataCache.on('changed')`，带 200ms 防抖后重算；`onunload` 由基类自动解绑。
- 视图渲染函数签名：

```ts
export interface ViewContext {
    el: HTMLElement;
    sourcePath: string;                    // 宿主笔记路径：视图靠它知道「我长在谁身上」
    params: Record<string, string>;
    index: VaultIndex;
    ctx: ZiminosContext;
}
export type ViewRenderer = (view: ViewContext) => Promise<void>;
export interface ViewDefinition { readonly name: string; readonly render: ViewRenderer; }
export function registerViewCodeBlock(ctx: ZiminosContext, views: readonly ViewDefinition[]): void;
```

`main.ts` 只多一行装配：把三个模块导出的视图数组拼起来注册。**客户视图始终注册**（只读渲染，零成本），开关只决定初始化产物——避免任何需要重启才生效的条件分支。

### 2.4 二十个视图名（与演示库 20 个脚本一一对应）

| 宿主 | 视图名 | 参数 | 移植自 |
|---|---|---|---|
| 人脉MOC | 人脉名录 / 投喂名单 / 本月生日 / 人情余额 | — | `moc-roster` / `moc-gifts` / `moc-birthdays` / `moc-balance` |

**落地计数：21 个视图**（复盘 5 + 人脉档案 4 + 人脉 MOC 4 + 客户 8）。比移植源的 20 个脚本多一个，是因为原脚本的两个 `mode` 被拆成了两个视图名。

### 2.5 渲染层纪律

- 表格一律经 `core/table.ts` 的 `renderTable(el, headers, rows)` 产出，单元格支持 `string | TFile | HTMLElement`；**禁止两次 `renderTable` 拼一张逻辑表**（两个 `<table>` 各自算列宽会错位，`review-daily-output.js` 的注释里已记录此教训）。
- 空态一律显式：`📭 + 一句话告诉学员下一步做什么`，禁止空块。缺记录的格子写「（无日记）」，**禁止兜底成 0**——16% 覆盖率下把空值伪装成零值，是最容易骗人的画面。
- 年度全景的柱状图沿用原脚本的纯 DOM + inline style 实现，不引入图表库，不新增 `styles.css`。

## 3. 人脉模块（`src/modules/contacts/`）

### 3.1 数据模型（逐条继承演示库，不发明新键）

人物档案 frontmatter，顺序即呈现顺序：

```yaml
aliases: · description: · created: · updated: · tags: · UID:
type: person
up: "[[人脉MOC]]"     # 归属链接，名录按它分组
tier:                 # 密/近/熟/远 = 7/30/90/365 天联系节奏
direction:            # 向上/平行/向下
gift:                 # true 即进投喂名单
address:              # 整串寄件信息，不参与筛选，唯一雇主是投喂名单
get:                  # 他能给我什么（List）
birthday:
```

三条不可动摇的口径：

1. **卡片不带分类**。没有「客户/生活/工作」枚举；圈子靠 `up`，客户身份靠「名下有 `client` 指向他的项目」从事实反推。身份因此不互斥。
2. **`client` 与 `with` 不能互换**。`client` 是商业契约标记，写下它等于把人注册成客户；朋友一起做的事走 `with`。
3. **位置无关**。全部视图靠 `type` 认身份，唯一位置依赖是 `settings.archiveFolder`（归档即退出名录）。

### 3.2 记录分工（三类记录同一入口，靠行的形态分流）

学员只在**当天日记**里写字，档案自己检索：

| 写法 | 落到哪 |
|---|---|
| `和 [[张三]] 去了新疆，谈定一起投网咖` | 档案「关键事件」 |
| `- [ ] 出网咖投资方案给 [[张三]]` | 档案「待办」 |
| `- [[张三]]｜去｜送了半斤生普｜两清` | 档案「人情账本」+ MOC「人情余额」 |

账本行纪律：全角 `｜` 分隔，`去/来` 必居第二段，状态取 `两清/我欠/他欠`（省略即两清），**人物归属只认首段的链接**——事项里被提到的人不算债主。非法状态值以 `⚠️` 前缀暴露，不静默吞掉。

### 3.3 文件清单

| 文件 | 职责 |
|---|---|
| `templates.ts` | 人脉/客户档案与两张 MOC 的文本生成，纯函数无副作用 |
| `createContact.ts` | 命令「新建人脉」：姓名 → 分层 → 方向三连问，`type: person` 由命令填、模板留空（模板自带 type 会让它自己变成名录里的一个人） |
| `recordFavor.ts` | 命令「记人情」：选人 → 去/来 → 事项 → 状态，账本行追加进当天日记；事项内全角 `｜` 清洗为半角防段错位；日记目录缺失自动创建，不以报错阻断 |
| `personViews.ts` | 档案四视图 |
| `circleViews.ts` | 人脉MOC 四视图 |
| `identity.ts` | 「谁还算数」的唯一答案处（落地新增）：身份靠 type、退出靠归档目录、最近联系只认日记 |
| `ledger.ts` | 日记三类记录的解析层（落地新增）：形态分流与「债主只认首段」的判据 |
| `client.ts` | 命令「初始化客户模块」「新建客户」「增加付费」「记收款」，以及 clientSeed |
| `clientViews.ts` | 客户八视图 |
| `seed.ts` | 人脉模块的开荒贡献 |

**落地差异二 · 拆出 `identity.ts` 与 `ledger.ts`。** 两处判据被命令侧与视图侧共同消费：「谁还算数」与「一行账本怎么归属到人」。留在任一视图文件里，另一侧就得抄一遍，而抄错的表现是视图静默少一行。

选人列表走 `metadataCache` 筛 `type: person`（客户命令筛 `type: client`），**归档目录内的人不进候选**。人机问答一律用 `core/modals.ts`，多选场景需要新增 `SuggesterModal`（基于官方 `FuzzySuggestModal`）——**枚举取代自由文本，让垃圾在语法上不可能产生**。

### 3.4 与 V1 既有自动行为的咬合（必须验证）

- `cardInit` 的放行闸是 `hasValue(frontmatter.type)`，`type: person` 的档案因此不会被补上 `rating/author/source/up` 四个无雇主的键——V1 已修对，V2 依赖它，回归测试必须覆盖。
- `02-areas/人脉/` 落在 `areaFolder` 内：插件建档走 `guard.mark` 不触发自动登记；**学员手工新建空笔记仍会被当卡片初始化**，这是既有行为，README 里说明「建档用命令」。

### 3.5 付费记录（客户模块）

任务行 + 中文行内字段，一笔一行不嵌套：

```markdown
- [x] [产品::Obsidian课] [金额::365] [日期::2025-08-19]
```

未勾＝待交付，勾上＝已交付，checkbox 直接充当交付状态。三条格式纪律各躲一个已核实的坑：键名用中文（含大写的键会被补一份规范名致求和双计数）、一笔一行（父子字段各自扁平上浮会丢配对）、产品名写在值里（当键名则算总收入必须枚举所有产品）。不设「付费次数/累计金额」字段——数行数即次数，求和即累计。

**V2 自渲染的红利**：这三条纪律里前两条是 Dataview 的解析行为所致；插件自己解析行内字段时不重蹈覆辙，但**格式仍按原样交付**，因为学员的库里可能同时装着 Dataview，两边看到的必须是同一笔账。

## 4. 复盘模块（`src/modules/review/`）

### 4.1 主题链

五级复盘的骨架不是数据，是一条主线：**日主题 → 周主题 → 月主题 → 季主题 → 年主题**。学员只在日记里写一次结论，其余四级全是它的投影。左边一句话是人写的，右边全部自动，两者并排才构成一次复盘。

### 4.2 周期笔记契约

| 级别 | `type` | 文件名 | 目录 | 周期锚点 |
|---|---|---|---|---|
| 日 | `diary` | `YYYY-MM-DD` | `05-diary/01-daily` | 文件名即日期，**无 `period_start`** |
| 周 | `weekly` | `GGGG-Www` | `05-diary/02-weekly` | `period_start` = ISO 周一 |
| 月 | `monthly` | `YYYY-MM` | `05-diary/03-monthly` | 月首日 |
| 季 | `quarterly` | `YYYY-Qq` | `05-diary/04-quarterly` | 季首日 |
| 年 | `yearly` | `YYYY` | `05-diary/05-yearly` | 年首日 |

**统一汇总键 `period_start`**（`YYYY-MM-DD` 定宽字符串）。所有区间比较一律降到 `YYYY-MM-DD` 字符串空间——定宽格式字典序即时间序，零日期算术、零跨年 bug、零跨类型比较陷阱。周归属月用 ISO 惯例：`period_start + 3 天`（周四）落在哪个月，该周就算哪个月，每周只归一个月，不重不漏。

导航行 `<< [[前]] | [[后]] >>　↑ [[上级|本周]]`：上级笔记不存在时是未解析链接，点击即按模板创建，这是 Obsidian 原生行为，不做额外处理。

## 9. 真机第一轮暴露的两处修正（v0.4.0 内修订）

### 9.1 选择弹窗永远返回「取消」

`ChoiceModal` 基于 `FuzzySuggestModal`。Obsidian 的 `SuggestModal` 在用户选中一项时是**先 `close()`、再回调 `onChooseItem`**，而 `onClose` 里同步把 Promise 结算成 `null`，于是每一次正常选择都先被判成取消，随后的 `onChooseItem` 因 `settle` 幂等而失效。表现：新建人脉 / 新建客户 / 记人情 / 增加付费四条命令永远只说「已取消」。

修法：`onClose` 先调 `super.onClose()`（基类自身的清理不能被覆盖掉），再把 null 结算推迟一拍。选中路径由 `onChooseItem` 先落定，取消路径没有后续回调、一拍后照常结算成 null。两条路径都成立，且不依赖基类的实现顺序。

### 9.2 UID 从 17 位字符串改为 14 位数字

属性面板要求 `UID` 是数字类型，而 JavaScript 安全整数上限是 `9007199254740991`（16 位）。17 位的 `YYYYMMDDHHmmssSSS` 一旦以数值形态落盘就会被静默四舍五入——真机第一轮已观测到 `UID: 20260812165253780` 这样末位归零的值，不报错、值已变，且此后每次读写都在错误值上继续。同一个库里还同时存在带引号的 `UID: "202608121704..."`（模板直接写字符串）与不带引号的形态，属性面板一半显示文本一半显示数字。

修法：`UID_FORMAT` 改为 14 位 `YYYYMMDDHHmmss`（2.03e13，稳在安全线内），`nowUid` / `nowStampAndUid` 返回 `number`，全部生成器落盘不加引号。代价是同一秒内建的两篇笔记会撞号——命令都是人触发的，一秒一篇是现实上限，这个代价远小于「主键会悄悄改数」。14 位也正是课程属性注册表 v4 原本写的位数。

### 9.3 属性类型不再需要学员手动设置

Obsidian 决定属性控件的依据是 `.obsidian/types.json`，它不看笔记内容——模板里的空字段因此一律显示成「文本」。

修法两件：其一，`vault/.obsidian/types.json` 随库交付，登记全部 25 个属性的类型（文本 12 / 日期时间 2 / 日期 3 / 数字 2 / 列表 3 / 勾选框 1 / 内置 2），全新安装即生效，升级只补缺失键不改用户调过的类型；其二，开荒生成 `90-system/属性类型示例.md`，每个属性都带一个格式正确的样例值，按类型分块说明。它住在 90-system 且 `type` 取封闭枚举之外的 `示例`，因此不会混进任何一个视图。

连带把 `up` 的落盘写法改成 YAML 列表（它登记为列表类型），`cardInit` 首次登记也写成单元素列表。

## 10. 真机第二轮暴露的修正（v0.4.0 内修订）

第二轮把插件自渲染的视图与原版 Dataview 并排比对，暴露的全是「像不像一个能用的系统」层面的问题——不是数据错，是呈现错。

### 10.1 建项目漏了归属这一步

移植源 `create-project-moc.js` 是四步：名称 → 归属（自己的 / 客户委托的）→ 选人 → 概述。V1 移植时只留了名称与概述两步，**归属分支整个丢了**——而 §3.1 明明写着「`client` 与 `with` 不能互换」，那条纪律因此没有任何入口去执行，全靠用户手写 frontmatter。

补法：命令恢复四步。顺序照原脚本——概述放最后，前面全是点选，中途取消不至于让人白写一段话；归属必须在动土之前问完，客户委托却没选到人时中止，不留半个空文件夹。选项文案直接把后果写出来，因为这一问是整条流程里信息量最大的一步。（归属那两个选项在 v0.8.1 被拆成三个，理由见 §15。）

候选人住在 contacts 模块，projects 不 import 它——`createProject` 声明一个 `PersonPicker` 的洞，由 `main.ts` 用 `contacts/identity.ts` 的 `pickPerson` 填上。这是 §5.6 那套注入的第三处应用，方向与前两处相反（projects ← contacts）。

### 10.2 渲染层与 Dataview 的三处差距

| 差距 | 后果 | 修法 |
|---|---|---|
| 文本里的 `[[双链]]` 渲染成死文本 | 视图检索出来的是日记原文，原文里的人名与项目名都是双链——拍平成字符串等于把一张关系网变成一段文字，点不动、跳不了 | `core/table.ts` 新增 `RichText` 单元格与 `renderTextWithLinks`，链接按**来源笔记**的路径解析（事件行来自日记，不能按档案路径解析） |
| 任务行渲染成表格 | 待办不像待办，也勾不掉 | 新增 `renderTaskList`：一条一行、真复选框、日期缀在句尾且可点、勾选写回源文件那一行；写前比对原文，行号漂了就什么都不做 |
| 全框线表格 | 与 Dataview 的三线表风格分裂，同一个库里两种表 | 新增 `vault/.obsidian/plugins/ziminos/styles.css`：三线表、首列表头带行数计数、选择器全带 `ziminos-` 前缀、颜色取 Obsidian 语义变量 |

`styles.css` 是插件的第三个交付文件（前两个是 `main.js` 与 `manifest.json`），手工维护、不经 esbuild，已加入 SKILL 的交付清单与升级复制清单。

**只认双链一种标记，不接完整 Markdown 渲染器**：这些文本是用户日记里的原话，交给渲染器等于把用户数据当代码执行，一个 `![[大图]]` 就会在名录里嵌进一张图。

### 10.3 相关项目的口径修正

原实现列「项目 / 关系 / 状态」，且不分状态全列。改为：

- 列 **项目 / 关系 / 概述**——状态这一列在只剩进行中的表里恒定重复，概述才是决定要不要点进去的信息。
- **只列未终结的项目**。走到 `done` 或 `dropped` 的项目从「相关项目」移进「关键事件」，带着 `archived` 给的确定日期。理由是这四个视图本就是一条时间线：相关项目答「我们现在手上有什么」，关键事件答「我们之间发生过什么」。一个三年前做完的项目永远挂在「相关项目」里，是把履历当成待办。


### 10.4 版面：表格占满整行，待办收成一行

真机第三轮的反馈是「自适应到了最小宽度」——表格缩成内容宽度挤在左边，右侧大片空白没人用；待办则被日期分组标题拉长了一倍。两件都是空间分配问题。

**表格**：`.ziminos-table` 这一级压不住 Minimal 给 table 设的收缩宽度，选择器改成 `div.ziminos-table-wrap > table.ziminos-table` 两级。光撑满还不够——余量得有人收：`renderTable` 新增可选的 `grow` 参数指出哪一列是句子列，其余列 `width:1px + nowrap` 各取所需，句子列拿走全部余量。只在真有句子列的表上指定（概述、事项、发生了什么、一句话、寄件信息、各级主题、笔记），其余交给浏览器均摊。

**待办**：去掉按日期分组，改走与其余视图同一个 `renderTable`，画成三线表（事项一列、日期一列，事项列吃余量）。复选框与事项同处一格——分成两列的话一个待办会被表格的列切成两半，而勾选框离它要勾的那句话越远越容易勾错。格内用 flex 两段，事项段显式 `min-width: 0`：flex 子项默认 `min-width: auto`，长句子会撑破单元格。

**全宽**：两级选择器仍不足以撑满——主题可能用 `!important` 锁死表宽，那场特异性竞争赢不了。改用 `min-width: 100%`：它不参与竞争，浏览器先算出 `width` 的用值再拿 `min-width` 去夹，于是无论主题把 `width` 设成 `fit-content` 还是别的什么，最终宽度都不会小于整行。这比自己也写一个 `!important` 干净——我们并没有覆盖主题的意图，只是声明一条下限。


## 11. 左侧边栏命令与图标（v0.5.0）

### 11.1 要解决的问题

命令面板对零基础学员是隐形的。他知道「记灵感」这件事，却未必记得住 `Ctrl+P` 再打三个字；而一条命令只要点不到，它在产品里就等于不存在。社区插件 Commander 解决的正是这个问题——把命令摆到最左边那一列图标里。

不装 Commander 而自己长出来，理由不是少一个依赖，是**图标要与命令同源**：命令改了名、换了图标，边栏上那个按钮必须当场跟着变。插件之间做不到这件事，只能各存一份，而各存一份迟早对不齐——对不齐既不报错也没人发现。

### 11.2 命令注册台（`core/commands.ts`）

二十三条命令的身份（`id` / 中文名 / 图标名 / 分组）从 `constants.ts` 里分出来，连同注册台一起住进新文件。分家的判据是：`constants.ts` 回答「系统里有哪些东西」，`commands.ts` 回答「用户能让系统做哪些事」；命令还多带了图标与分组两样只服务界面的字段，混进常量表会让那份表同时是数据字典和界面清单。分家后 `constants.ts` 从 575 行回到 531 行，没有触碰单文件 800 行的红线。

`CommandRegistry` 做两件必须同时做的事：把命令交给 Obsidian（命令面板与快捷键因此找得到它），同时在花名册上留一份（左侧边栏因此有东西可摆、设置页因此有清单可列）。全部模块改走 `ctx.commands.register(spec, run)`，`plugin.addCommand` 在业务代码里不再出现。

**花名册存回调本体而不只是 id**，这是本次唯一一处需要解释的取舍：按 id 执行命令的 `executeCommandById` 不在 `obsidian.d.ts` 里。为了让边栏按钮能触发命令而再开一个非公开 API 的口子，代价远大于收益——而回调本来就在手上，接住即可。**因此本次新增功能全程只用公开 API（`addIcon` / `addRibbonIcon` / `Command.icon`），不构成第 4 处红线偏离。**

两处顺带的收敛：`TRANSITION_COMMANDS` 从 `transitions.ts` 搬进来（它本就该与 `TRANSITIONS` 状态机同处一地）；`PERIODS` 里的 `commandId` / `commandName` 搬成 `PERIOD_COMMANDS`，键是 `PeriodKey` 且类型是 `Record`，于是「加一级周期却忘了给它命令」在编译期就过不去，而 `PERIODS` 那张表回归只谈时间。

### 11.3 二十一个图标（`modules/ribbon/icons.ts`）

出自同一套画法（Pikaicons：24 格、2 宽描边、圆头圆角）。十六个取自免费集原图，五个照同一套画法补画——暂停、播放、灯泡、调色板在免费集里没有，四分之一饼则必须与兄弟图标成套才讲得清「季」。补画的一律复用原图的几何原语（半径 9 的圆、日历框），因此它们与原图并排时看不出接缝。许可与来源见 `docs/第三方组件.md`。

| 分组 | 命令 | 图标 | 为什么是它 |
| --- | --- | --- | --- |
| 开荒 | 初始化笔记库 | 三层叠片 | 开荒做的就是一次把层次铺好 |
| 项目 | 新建项目 | 旗 | 项目与领域的区别是它有终点，而旗子插在终点上 |
| 项目 | 初始化当前卡片 | 一页纸 | 它做的就是把眼前这一页登记成卡片 |
| 项目 | 完成 / 暂停 / 放弃 / 重新开始 | 圈中勾 / 双竖 / 叉 / 播放 | 四个共用同一个半径 9 的圆，只换圆心里的记号——它们是同一台状态机的四个出口 |
| 灵感 | 记录灵感 | 灯泡 | 免费集里没有，补画；两道螺纹不能省，只留一道会读成气球 |
| 复盘 | 日 / 周 / 月 | 日历框 + 点 / 横条 / 网格 | 同一个框，一天是一个点、一周是一行、一月是一片 |
| 复盘 | 季 | 四分之一饼 | 再密的格子在 18px 下都和月记一样；「四分之一」只有饼图不会被误读 |
| 复盘 | 年 | 勋章 | 年度复盘是一年的结算，不是更大的一格日历 |
| 复盘 | 写复盘主题 | 笔 | 五级里唯一要动笔写的字段 |
| 人脉 | 新建人脉 | 人 + 心 | 人脉与客户的分别就在这颗心上 |
| 人脉 | 记人情 | 礼物 | 账本记的就是「谁送出去、谁欠着」 |
| 客户 | 初始化客户模块 | 公文包 | 这条命令做的是开张，不是新增某一个客户 |
| 客户 | 新建客户 | 人 | 客户是陌生人，所以不给他那颗心 |
| 客户 | 增加付费 / 记收款 | 钱 / 钱包 | 付费是承诺，收款是钱真的进了口袋，两件事两个图 |
| 外观 | 打开外观开关 | 调色盘 | 免费集里没有，补画 |

两处技术决定：

1. `addIcon` 把内容塞进一个 `0 0 100 100` 的外层 svg，我们再套一层自带 `0 0 24 24` 的内层 svg 把 24 格铺满，而**不是**把每个坐标乘以 4.1667——`path` 里的数字是设计稿上的数字，换算过一遍就再也改不动了。
2. 描边宽度取 `var(--icon-stroke, 2)` 而非写死 2。ziminOS 随库交付 Minimal + Style Settings，学员在外观面板里把图标调细时，只有这二十三个不跟着变的话，那一列会一眼看出是外来户。

### 11.4 摆法（`modules/ribbon/dock.ts`）

默认摆出七条：新建项目、记录灵感、今天的日记、写复盘主题、新建人脉、记人情、外观开关。判据是「一天里可能按不止一次」。其余十六条要么一辈子只按一次（初始化笔记库、初始化客户模块），要么发生在某个具体场景里（初始化当前卡片、四条流转、三条客户流水、周月季年四级复盘）——那些场景里用户本来就停在对的笔记上，命令面板比一根图标柱更快。二加十二，正好十四。二十三条全摆等于把选择的负担丢回给学员。

**只为勾上的命令调 `addRibbonIcon`**，不是一次建齐二十一个再切显隐。第一版正是后者，被真机核对推翻，两次判断都记在这里：

`WorkspaceRibbon.onChange()` 遍历它自己那份 `items`，对每一项无条件执行 `buttonEl.toggle(!item.hidden)`——**inline 的 display 是 Obsidian 保留给自己的通道**，而 `item.hidden` 只有它的边栏菜单能改，公开 API 里没有入口。于是第二次启动（`workspace.json` 里一旦存下 `left-ribbon`，`loadLayout` 就会调 `leftRibbon.load` → `onChange`）、装任何一个也调 `addRibbonIcon` 的插件、用户在边栏右键或拖一下，都会把二十一个图标全放出来，而设置页还显示「已摆出 7 条」。

更根本的一层是 DOM 修不好的：手机端底栏的边栏菜单与桌面「设置 → 外观 → 功能区 → 管理」弹窗都遍历 `leftRibbon.items`、只看 `item.hidden`，不看 DOM。一次建齐的话，那两处永远列着全部二十三条——包括「初始化笔记库」。只建勾上的，这两处才跟着对。

本次会话内取消勾选的按钮收不回来（没有公开的「撤下这一个」），只能加一个 `.ziminos-ribbon-hidden` 先藏起来，下次重载它压根不会被建出来。在那之前它仍留在 `leftRibbon.items` 里，于是另外三处入口照旧列着它、点了还照旧执行：手机端底栏的边栏菜单、桌面「设置 → 外观 → 功能区」的管理弹窗、边栏空白处的右键菜单。桌面上无伤——边栏那一列是主入口，用户看到的就是消失了；**手机上则完全看不出变化**，因为 `.is-phone .side-dock-ribbon` 本来就是 `display:none`，手机根本没有那一列。为此 `syncVisibility` 在手机端取消勾选时弹一句「重启后才会从边栏菜单里消失」，把疑惑变成预期。这条 CSS 是 `styles.css` 里唯一的 `!important`：它压的不是主题的设计意图，而是「用户取消了勾选，这个图标就必须消失」这条没有商量余地的声明，输掉那场特异性竞争等于功能不存在。代价是本次会话内新勾上的图标追加在末尾而非插回原位，重载归位——而顺序本来也不完全归我们，用户可以在 Obsidian 里拖着排。

**另一处如实备案：两把锁，且另一把不归我们**。Obsidian 自己也能藏边栏图标（边栏右键，或「功能区」管理弹窗里的删除），它写的是 `item.hidden` 并持久化进 `workspace.json`。启动顺序是插件先建按钮、`loadLayout` 后把 `hidden` 盖回来，所以那把锁永远压过我们这把：一条命令可以在 ziminOS 设置页显示为已勾选、边栏上却始终不出现，而且在 ziminOS 里反复拨开关也救不回来——只能回 Obsidian 的「其他功能区项目」里放出来。公开 API 读不到 `item.hidden`（`obsidian.d.ts` 里的 `WorkspaceRibbon` 是个空类），要读只能再开一处非公开 API 的口子，不值得。当前处置：设置页的说明文字如实交代这件事并指路，代码不做检测。

**一处如实备案，没有在本次修掉**：二十三条里只有「初始化当前卡片」可能被点了完全没有反应。它的守卫是静默放行（不在项目/领域目录二级以下、已登记过、是 MOC 本体、没有活动文件，一律直接返回不作声），那是 `initialize-card-note.js` 的移植纪律——原脚本的守卫与文案一字不改，要给它补提示得先在规格里授权。在真实使用的库里这不是边缘情况：日记、五级复盘、灵感集、人脉、客户、模板、导航页，以及所有已登记过的卡片，点下去都是零反馈。从命令面板执行同样如此，所以它不是本次引入的缺陷，但把它做成一个亮闪闪的图标确实放大了它。当前处置：**不进默认清单**（学员要主动勾才会遇到），行为一字不改。要不要给它补一句「这篇笔记不在项目或领域目录里，不需要登记」，是一个需要单独拍板的产品决定，因为它会动到一条写在 modules/projects 的 L2 里的移植不变式。

**第三个入口带来的一个连带修正**：外观开关的浮层原本只放行状态栏按钮，边栏那个调色盘按钮不在名单里，于是点它一下会被同一次手势处理两遍（mousedown 判定「点了别处」先关，click 再开回来，浮层闪一下还在）。改法不是扩充放行名单——「谁能打开我」会随入口增加而增长，名单迟早漏掉一个——而是记下「上一次因点别处而关闭」的时刻，同一次手势内的再次打开直接忽略。判据与 `SelfWriteGuard` 同形：都是在问「这动作是不是我自己刚才引起的」。

### 11.5 设置页第五区

`ribbonCommands: readonly string[]` 存已勾选的 id。声明成 `readonly` 不是洁癖：它在用户没调过时与 `DEFAULT_SETTINGS` 共用同一个引用，允许原地 `push` 的话，用户第一次勾选就把默认值本身改掉了，此后连「恢复默认」都恢复不回来——这条约束交给编译器执行，不靠人记得。每次勾选都照花名册重排一遍生成新数组，顺带把 `data.json` 里不认识的 id 扫掉。

设置页那一区不认识任何一条具体命令，清单现读花名册，分组标题按相邻两行的 `group` 变化切出来（与外观开关面板同一套画法）。每行左侧画出该命令的真实图标——勾之前先让人看见它长什么样。

设置页要让边栏那列已经画出来的图标跟着变，于是多了第四个「函数类型的洞」。三件注入的事（执行开荒、同步状态栏、同步边栏）改由 `SettingActions` 一个对象递进来，而不是三个位置参数：后两个的类型都是 `() => void`，摆成位置参数时调换顺序照样能通过编译，出的错却没有任何编译期信号。

### 11.6 交付物同步

`vault/README.md` 是学员手册，它通篇教「按 `Cmd + P` 输入命令名」——而那正是本功能要消灭的摩擦，不改它等于功能做了没人知道。三处改动：

- 开荒三步之后新增「先看一眼最左边那一列」，用一张「图标长什么样 → 它做什么」的对照表交代默认七条，并说明另外十四条在设置里勾。
- 明说下文每个动作仍写 `Cmd + P` 那条路，因为二十三条都能那么走，而边栏上只有勾过的那几个——两条路通向同一件事。
- 小提醒里补一条「关于左边那列图标」，如实写明两件反直觉的事：取消勾选后手机端边栏菜单要重启才彻底干净；在 Obsidian 自己的「功能区」里藏掉的，回 ziminOS 勾上也不会出现。

`skill/SKILL.md`（桌面 Agent 的安装契约）里的交付话术也该加一句「最左边多了七个图标」，那份文件不属于本节范围，由发布流程一并处理。

### 11.7 验收

1. 全新库首次加载，左侧边栏出现七个图标，顺序为：新建项目、记录灵感、今天的日记、写复盘主题、新建人脉、记人情、外观开关。
2. 逐个点过去，行为与命令面板里执行同名命令完全一致。
3. 设置 → 左侧边栏，勾上「完成项目」，边栏立刻多出一个图标，且落在「新建项目」与「记录灵感」之间（注册顺序，不是追加到末尾）。
4. 取消全部勾选，边栏上 ziminOS 的图标一个不剩，命令面板里二十三条一条不少。
5. 命令面板搜「ziminOS」，每条命令左侧带着与边栏相同的图标。
6. 在 Style Settings 里调粗/调细图标描边，这二十一个跟着变。
7. 切换明暗主题，图标颜色跟随（取 `currentColor`）。
8. 老库升级（`data.json` 里没有 `ribbonCommands`）：默认七条正常出现，其他设置一项不丢。
9. **重启验收（第一版栽在这里，必须走一遍）**：勾成非默认的一组 → 完全退出 Obsidian → 重开 → 边栏上仍然只有那一组。再装一个带边栏图标的第三方插件，边栏不应冒出未勾选的 ziminOS 图标。
10. **重载之后**，手机端底栏的边栏菜单里只列勾选中的命令，不该出现「初始化笔记库」；桌面「设置 → 外观 → 功能区 → 管理」同理。注意刚取消勾选、尚未重载时这两处仍会列着它，那是已备案的会话内残留，不是回归。
10b. 手机端取消一条勾选：应当立刻看到一句「重启后才会从边栏菜单里消失」的提示（手机上没有边栏图标柱，没有这句话就完全没有反馈）。
11. 边栏上点调色盘图标：浮层开；再点一次，浮层关（不是闪一下又开回来）。
12. 手改 `data.json` 把 `ribbonCommands` 写成 `null` 或字符串，重开：设置页七个分区完整可见，边栏回落默认七条。

## 12. 设置页按系统模块分页（v0.6.0）

### 12.1 起因

真机截图给出的判据很直白：一页排下来是开荒、两个自动化开关、五项灵感、一个外观开关、二十一行边栏、九个折叠的目录字段、七行模块清单——**四十来个控件排成一条长路**。想改灵感的落点得越过边栏那二十一行，想改产品清单得先想起它藏在一个叫「高级设置（一般不用改）」的折叠区里。这不是控件多，是**没有边界**：一页同时回答了七个系统的配置问题，于是每个问题都得从头找起。

而边界本来就存在，只是没有在界面上显现——`src/modules/` 下那七个目录就是它。设置页不做分页时，代码的模块边界与用户看到的顺序是两套东西，「客户的设置在哪」的答案取决于当初谁把它排在了哪一段。

### 12.2 切法：一页一个模块，页标识与目录同名

八张页：`setup` / `projects` / `inspiration` / `review` / `contacts` / `clients` / `appearance` / `ribbon`。前七个同名于 `modules/` 下的目录，`clients` 是 `contacts` 模块里 `client.ts` 那一支——单列成页的理由与它在 `COMMAND_GROUPS` 里单列成组的理由是同一条：客户与人脉在业务上本就是两个物种。

标签一律两个字（开荒 / 项目 / 灵感 / 复盘 / 人脉 / 客户 / 外观 / 边栏）。长短不齐的标签会让人以为它们不是一类东西；八枚两字标签加图标约 610px，在设置弹窗内容区里一行排得下，窄窗口自动折行。

顺序即学员的使用顺序，也正好是 `main.ts` 的装配顺序与命令的注册顺序：先开荒，再是每天在用的三套（项目、灵感、复盘），然后是关系与生意（人脉、客户），最后两张管的都不是笔记而是屏幕（外观、边栏）。

### 12.3 目录字段各回各家

原来九个目录/格式字段全堆在页尾一个统称「高级」的折叠区里。分页之后它们各自归还给服务的那个模块：项目/领域/归档三个目录归项目页，复盘目录归复盘页，人脉目录归人脉页，客户目录归客户页，时间格式归开荒页（它服务全库的 created/updated，没有别的模块能认领它）。

**`clientSources` 与 `clientProducts` 就此离开折叠区**。判据不是「难不难懂」，是「改了会不会让学员的库与课程讲义对不上」：目录名与时间格式是课程内容的一部分，所以既要留出口又不能摆在明面上诱导人去动；而渠道与产品清单本来就是学员自己的业务数据——产品名只能由他自己写，把它锁进一个叫「一般不用改」的抽屉里才是真的误导。

每页仍有自己的「高级设置（一般不用改）」折叠区，永远在页尾；本页没有高级字段就整块不出现——一个点开来是空的折叠区，比没有它更让人怀疑自己漏了什么。

### 12.4 一张表喂三处

`TABS` 是各页的唯一身份表（短名 / 图标 / 模块全名 / 交付状态），同时喂：标签栏、每页页头那句「这一页是谁、跑没跑起来」、开荒页那份「系统模块」清单。于是不可能出现「标签上写着外观、清单里写着外观包 v2、页头又是第三句」。

**v0.9.2 修订：十张收成八张，标签栏改底线式。** 参考成熟插件（Copilot）的设置页形制，两条改动：其一，appearance 与 about 撤页——前者只有一个开关、后者只有一张名片，一个控件撑一整页是把分页做成摆设；开关并进开荒页（排在初始化之后，外观包本就是开荒交付物的一部分），名片收作开荒页尾的落款（排在高级折叠之后，它不是设置是署名，这也是全部八页里唯一排在折叠区之后的东西）。八张两字标签一行排下，标签栏永远不换行。其二，标签栏由分段式凹槽改为「整行底线 + 当前页填充胶囊」：一条细线通到底把导航与内容分成上下两个世界，标签自然宽度左对齐，当前页填充实底、字重加粗、图标着强调色。同名纪律的表述随之修正：有设置项的模块一模块一页；只有一个控件的模块并进开荒页，在 TabId 的注释里备案。

**v0.9.1 修订：标签栏分段式 + 图标同源。** 首版标签是十颗 Obsidian 默认样式的按钮配彩色 emoji——十个自带底色投影的立体按钮排成两行，看着像十个待按的动作，emoji 又与系统其余图标全不同源。改法两条：其一，十枚标签收进一条分段式凹槽（次级底色 + 1px 边框），按钮卸干净立体外观、flex 均分整行，当前页用内容区底色从槽里凸起并加投影与字重，图标着强调色——三个信号叠加，不只靠颜色；其二，emoji 全部换成 COMMAND_ICONS 里的 Pikaicons 笔画图形，与左侧边栏、命令面板同一套画法同一条描边变量，页头用同一枚放大一号着强调色，是整页唯一的强调色锚点。「边栏」页没有现成图形，照原画法补一枚 dock（带左栏的面板，登记在 COMMAND_ICONS 但不属于任何命令）；「关于」页取写主题那支笔——作者，即执笔人。

**第一版还在开荒页上列了一份逐行可点的模块清单，随即摘掉**：九张标签一直摆在屏幕最上方、点一下即到，在首页把同样九行重列一遍，是把「索引」误当成了「介绍」——用户要的是切过去，不是先读一遍目录。那句交付状态没有跟着消失，它就在各页页头，在那儿它回答的是「我现在在哪、这页管什么」，而不是「这套系统都有些什么」。`TABS` 因此只喂两处：标签栏与页头。

十二个文本字段同理收进 `TEXT_FIELDS` 一张表，每条自带 `tab`（这是谁的设置）与 `advanced`（该不该收进折叠区）。一页的骨架固定为**页头 → 明面字段 → 自有控件 → 高级折叠**，这条顺序让灵感页的落点三问天然排在插入位置与格式之前，那一页因此不必自己再画一次字段。

### 12.5 三处实现取舍

- **加一页是编译期的事**。每页自有控件挂在 `Record<TabId, PanelRenderer>` 上，漏写一页是编译错，而不是运行时一张点进去空空如也的页。复盘、人脉、客户三页确实只有目录字段，写成显式的空实现而非让它们缺席，穷尽检查才继续成立。
- **「当前停在哪一页」不进 `data.json`**。设置对象里存的都是「这个库是什么样」，不是「上次那个人翻到了第几页」。它随插件实例存活：关掉设置弹窗再打开仍停在原页，重启 Obsidian 归位——与 Obsidian 自己记住你上次停在哪个插件设置页同一档待遇。
- **标签栏吸顶，换页后滚动条归零**。边栏那页有二十一行，翻到第十八行时标签栏若已滚出视野，换页就得先滚回顶部；而从二十一行的边栏页切到只有一个开关的外观页，滚动条不归零的话用户迎面是一片空白，会以为切坏了。标签是真的 `<button>`（键盘与读屏器认得），只带 `aria-pressed` 不自称 `role=tab`——没实现方向键遍历就自称 tablist 是撒谎。

## 13. 排版整理（v0.7.0）

### 13.1 起因与现状核对

真机核对先于设计。扫过测试库里那十三篇笔记，两类问题各有一个确凿样本：

- **中英之间没有空格**：`这是一个MOC笔记，现在要写[[卡片笔记]]`（用户手写的项目概述）。
- **空行不合规**：日记里 `## 今天做了什么` 下面两个空行、列表下面又两个空行——那是学员删掉模板留的 `%%` 提示块之后剩下的；以及灵感集的 `# 灵感集` 紧贴着 ```dataview 围栏，那一处是**插件模板自己写错的**，一并修在 `inspiration/templates.ts`。

同时确认了一件更要紧的事：**插件生成的字里，中英相邻只有三处，而且三处都绝对不能加空格**——`人脉MOC.md`、`客户MOC.md` 是文件名兼链接目标，`B站,抖音,小红书` 是渠道候选值（加空格会与已有档案里存的值对不上，渠道统计当场散架）。结论因此是硬的：**这条规则的对象是用户写的字，不是插件的模板**，而它的第一要务是知道哪里不能加。

### 13.2 九条规则住在 core，纯函数且幂等

`core/markdownStyle.ts` 零 import，只认字符串。九条：中英空格、标题/列表/表格/代码块上下留空行、YAML 后留空行、连续空行收一行、去行尾空格、文末一个换行。

**幂等是设计前提而非碰巧成立的性质**：`formatMarkdown(formatMarkdown(x)) === formatMarkdown(x)`。自动整理会写盘，写盘触发 `modify`，`modify` 又排下一次整理——断开这个环靠的正是「第二趟算出来的与第一趟一字不差，于是没有第二次写入」。五十六条断言逐条覆盖，每条都同时验一遍幂等。

八条空行规则合成同一趟扫描，而不是八个独立变换：「标题上下留空行」与「列表上下留空行」在「一个标题紧跟一个列表」这一处是同一个决定，拆开的话它们会各插一行、再靠第九条压掉多余的——那样既慢，也让「为什么这里是一行不是两行」变成一道要追八步才答得出的题。

### 13.3 保护名单：真正的难点

六种东西整段保护：行内代码、`[[双链]]`（连别名）、`[文字](链接)`、裸网址、HTML 标签、`#标签`；YAML 属性区在切分阶段就被摘出去，一个字符都不参与。

**但保护段外面照加**——`打开[[人脉MOC]]看看` → `打开 [[人脉MOC]] 看看`，空格落在方括号之外，链接一字未动。这个区分是整条规则的要害：会断链的是括号里那一个空格，而括号外那一个恰恰是中文与英文之间该有的呼吸。接缝处补不补空格只看一条：一边是汉字、另一边是可见的半角字符；全角标点因此永远不会被塞进空格（`路径，` 与 `。[[链接]]` 都原样）。

标签是个值得记的边界：`#项目2026的事` 在 Obsidian 里是**一整个**标签（标签允许含汉字），从 `2026` 后面切一刀会把它劈成两半。所以整段保护、只在它前面补空格——补完它才真的被 Obsidian 认成标签。

### 13.4 什么时候动手：三个时刻，都不是「你正在打字」

用户选定「命令 + 停手后自动（默认开）」，但**自动整理刻意不碰你当前正在编辑的那一篇**。理由是具体的：中文输入法在合成中途被外部改写会吞字；就算不吞字，整篇重写也会把光标从他正打字的位置上移开。「停手两秒」这个信号对 `updated` 那种只改一个 YAML 字段的动作足够，对整篇重排远远不够——斟酌一句话时停两秒太常见了。

于是自动整理只发生在三处：**用户从一篇改过的笔记切走**（`active-leaf-change` 管换面板、`file-open` 管同面板换文件，两个都订，漏一个就会留下永远等不到整理的笔记）；**一篇不在活动编辑器里的笔记被改动**（比如记人情刚往今天的日记里插了一行）；**用户自己按下命令**——那一条不受任何限制。“不活动”仍可能“在另一分栏显示”；此时写入统一经 `core/markdownViewState` 保住那个分栏的滚动位置。

### 13.5 与 updatedMaintainer 共处一室

两个常驻编辑监听，规矩必须写死：

| | updatedMaintainer | formatter |
| --- | --- | --- |
| 看 SelfWriteGuard 吗 | 看，插件刚写过就跳过 | **不看** |
| 断环靠什么 | 守卫 | formatMarkdown 幂等 + 「没变化就不写」 |
| 改动范围 | YAML 里一个字段 | 整篇 |
| 正在编辑的那一篇 | 照记，写后恢复视口 | 绝不碰 |

formatter 故意不看守卫，因为插件自己插进去的那一行（记人情、增加付费、记收款、记灵感）恰恰最需要整理——里面有用户现敲的字。它写盘前仍 `guard.mark`，那是给对方看的：整理是机器的动作，不该被记成用户的编辑。代码里另留一把一秒的再入锁，它挡不住设计错误，只是不把「幂等」这条性质押在一句注释上。

### 13.6 设置：一个自动开关 + 九个规则开关

`autoFormat` 回答「谁来按」，`formatRules` 回答「按下去做哪几件事」，刻意不合成一个——自动关掉后命令仍按九条勾选执行，合并就没法表达「我自己按，但按下去要全套」。

`formatRules` 存启用中的规则 id 清单而非九个布尔字段，与 `ribbonCommands` 同法同因：加一条规则不必动设置契约，而老库升级时那条新规则不在清单里、于是默认不开。设置页因此多出第七张标签「排版」（九张页的顺序里它排在客户与外观之间，与命令注册顺序一致），命令总数二十一 → 二十二。

### 13.7 验收

1. 新建一篇笔记，写 `使用Dataview查询3篇笔记`，切到别的笔记再回来：变成 `使用 Dataview 查询 3 篇笔记`。

3. 在一段正文下面紧跟一个列表、一个表格、一个 ```ziminos 代码块，切走再回来：三者上下各空一行，块内一个字未动。
4. 连打五个空行、行尾敲一串空格，切走再回来：空行收成一行、行尾空格没了。

## 14. 新建领域与 MOC 改名（v0.8.0）

### 14.1 MOC 改名：`文件夹名` → `MOC-文件夹名`

**起因**：一个项目是「一个文件夹 + 一篇 MOC」，而此前那篇 MOC 与文件夹同名，于是文件树里父子两级写着同一个词，哪一篇是总览全靠记。加个前缀，它在任何按名字排序的地方都浮到最上面，也一眼认得出。

**改这个名之所以不是改一行**，是因为这个约定有四个消费方：建项目照它落笔、卡片登记照它反推归属、状态流转照它认出「这是不是一篇 MOC」，以及**MOC 正文里那个 base 视图要照它写筛选表达式**。第四处最容易漏——`up == link("项目名")` 收的是 up 指向本 MOC 的卡片，MOC 一改名，这条筛选就再也匹配不上，而**那张表不会报错，只会静默少收一半文件**。四处因此收进 `modules/projects/moc.ts` 一个文件，改一次命名只改一处。

**存量笔记一篇都不改名**。读取侧一律走 `resolveMocPath`：先认 `MOC-名`，认不到再认 `名`，两个都没有时返回新名。三处消费方都吃这条回落，所以 v0.8.0 之前建的项目照样能被卡片认领、照样能执行四条流转。状态流转还多一条纪律：搬的是整个文件夹，MOC 的文件名一个字都不会变，所以目标路径沿用它**此刻**的名字，而不是照当前约定重新拼一个——否则老库的项目会在搬完之后「找不到自己的 MOC」而整体回滚。

### 14.2 新建领域

PARA 里「项目」与「领域」是同一个问题的两个答案：这件事有没有终点。所以它们共用一条流程，差别只有三处，全部收在 `ContainerKind` 那张表里：

| | 项目 | 领域 |
| --- | --- | --- |
| 根目录 | `projectFolder` | `areaFolder` |
| `type` | `project` | `area` |
| 问归属吗 | 问 | **不问** |

不问归属不是省一步，是那个问题在领域上不成立：领域是你对自己某一部分人生的长期关注——健康、手艺、人脉——它天然只属于你自己，问一句「这是谁委托的」是在问一个不存在的答案。

**一处主动的偏离，在此备案**：领域的 frontmatter **不写 `status`**。用户的要求是「只改 type，其余不动」，但导航页那张「正在进行中」正是按 `status == "active"` 筛的——照搬 `status: active` 会让每一个领域都混进那张表，而领域没有终点，说它「正在进行中」本身就是个假命题。少写一行的代价是零：`type == "area"` 那张表照常收得到它，四条状态流转本来就只认 `type: project`。

实现上，`createProject.ts` 里那条流程整体搬进 `createContainer.ts`，项目与领域各留一个薄入口。这样做而不是加两个 if，是为了让「新建领域某天悄悄少一道防覆盖校验」在结构上不可能发生；`label` 取「项目」时它吐出的每一句话与 V2 逐字相同，`create-project-moc.js` 的移植纪律未破。

命令总数二十二 → 二十三，新增图标一枚：一个缺口开在右上的环，与「新建项目」那面旗子成一对反义词——旗子插在终点上，而领域没有终点。它不进默认边栏七条：一个人的领域屈指可数，建完就是好几年。

### 14.3 验收

1. `Cmd + P` →「新建领域」，输入「健康」与一句概述：长出 `02-areas/健康/MOC-健康.md`，全程只问两次，不问「这是谁的」。
2. 打开它看 YAML：`type: area`，**没有 status 行**，没有 client/with。
3. 打开导航页：「领域」那张表里有健康；「正在进行中」那张表里**没有**它。
4. `Cmd + P` →「新建项目」，建「写本书」：长出 `01-projects/写本书/MOC-写本书.md`，问答流程与 v0.7.0 相同（归属三选项见 §15）。
5. 在「写本书」文件夹里新建一篇空笔记，随手写点东西：它被登记成卡片，`up` 指向 `MOC-写本书`，点得动。
6. 打开 `MOC-写本书`，看那个 base 表：第 5 步那篇卡片在表里（这一条验的是 `up == link("MOC-写本书")` 没有写错）。
7. 站在 `MOC-写本书` 上执行「完成项目」：整个文件夹搬进归档，`status: done` 与 `archived` 同时落笔。

9. 站在一篇领域 MOC 上执行「完成项目」：应当被拒绝，提示「当前笔记不是项目 MOC」——领域没有终点这件事在代码里也成立。

## 15. 建项目的归属改成三选项（v0.8.1）

### 15.1 这是一处自相矛盾，不是偏好问题

原流程的归属只有两项：

- 自己的项目（不写 client，不进客户统计）
- 客户委托的（写 client，我欠他一个交付）

选完第一项，紧接着仍会弹一次选人，标题是「和谁一起做？（自己独做就按 Esc 跳过）」。

于是标签刚说完「这是自己的项目」，下一屏就问「还有谁」，而想表达「真的只有我」的唯一办法是**按取消键**。一个必须靠取消才能走完的流程，是在拿取消当确认使——用户按 Esc 的那一刻并不知道自己是取消了选人、还是取消了整个建项目。

### 15.2 改法：把「要不要挂人」并进同一屏

三个选项，一次答完：

| 选项 | 挂什么 | 没选到人怎么办 |
| --- | --- | --- |
| 自己做（只有我，不挂任何人） | — | 不问，直接进下一步 |
| 和别人一起做（写 with，不算客户） | `with` | 照建，只是少挂一条 |
| 客户委托的（写 client，我欠他一个交付） | `client` | **中止**，不留半个空文件夹 |

后两项分家不能省。`with` 不是装饰字段：人脉档案里那张「相关项目」正在读它（`personViews.ts` 按 `client` 或 `with` 指向本人来收项目）。把两项砍成一项、只留 client，等于让「和朋友一起做的事」要么消失、要么被无声注册成一笔商业委托——而后者恰恰是 §3.1 那条「`client` 与 `with` 不能互换」明令禁止的。

必答性也不同，理由在业务里：客户委托却没选到人，那是一笔没有债主的交付债务，不成立；一起做的人没选到，项目照样成立，只是少一条关系。

### 15.3 顺带拆掉一个没人拨的旋钮

`PersonPicker` 此前带第二个参数 `quietWhenEmpty`：库里一个人都没有时要不要吭声。它只为「自己独做但顺口问一句同行者」那条路存在——关联本来可选，所以不该拿一句提示打扰用户。

那条路没了之后，会走到选人弹窗的每一次调用都是用户刚刚明确表示要挂一个人，于是这个开关的值恒为 false。参数、分支与那句解释一并删除：`pickPerson(ctx, title)` 两个参数，库里没人时那句引导一律要说。留着一个只有一种取值的开关，下一个读代码的人得花时间确认它到底有没有第二种用法。

### 15.4 备案：这是 `create-project-moc.js` 移植纪律的第一次主动破例

modules/projects 的 L2 写着「其余逻辑连同守卫与错误文案原样保留」。本次改动破了它，理由记在这里：原脚本那两个选项在 QuickAdd 里是同一套问答的两个分支，移植时逐字保留是对的；但把它放进插件、放到零基础学员面前之后，「靠 Esc 表达确认」这件事的成本才暴露出来。破例的边界很窄——只动归属这一屏的选项数量与是否追问，名称校验、防覆盖、光标落点、错误文案一字未改。

### 15.5 验收

1. 「新建项目」→ 选「自己做」：**不再弹选人**，直接问概述。建出来的 MOC 里既没有 `client` 也没有 `with`。
2. 选「和别人一起做」→ 选张三：MOC 里是 `with: "[[张三]]"`，导航页与客户表都不把它当客户。
3. 选「和别人一起做」→ 按 Esc 不选人：项目照样建出来，只是不带 `with`。
4. 选「客户委托的」→ 按 Esc 不选人：提示「未选择客户，操作已取消。」，且**不留任何文件夹**。
5. 空库（一个人脉档案都没有）选「客户委托的」：弹一句「还没有任何人脉或客户档案……」，然后按第 4 条中止。
6. 打开张三的人脉档案：第 2 步那个项目出现在「相关项目」里（这一条验的是 `with` 仍被读取）。
7. 开荒的首个项目仍免问答，一次弹窗都不弹。

## 18. 正文字体交付（v0.11.0）

诉求原话是「插件初始化时把正文换成霞鹜文楷」。答案却是**插件零参与**——这一章存在的意义就是记下为什么。

**机制（实证自 Obsidian 1.13.7 的 app.js 与 app.css）。** `appearance.json` 的 `textFontFamily` 就是「设置 → 外观 → 正文字体」，值为逗号分隔家族名，第一款本机装了就用、没装自动顺延——降级天然免费。运行时它被写成 body 内联样式的 `--font-text-override`，与 `--font-text-theme`、`--font-default` 逗号拼接进 `--font-text`。因此曾考虑过的两条路都被否掉：CSS 片段硬设 `--font-text` 会把用户在设置里手选的字体无声压死（下拉从此形同虚设）；片段 base64 内嵌 20MB 中文字体则每次启动多解一份 27MB 样式表，移动端有启动崩溃实例。**正门就在那里，旁门一个不走。**

**交付形态。** 四款字体（霞鹜文楷 GB 屏幕阅读版＝默认正文、思源宋体 CN Regular+Bold、朱雀仿宋、霞鹜新晰黑＋）作为锁定资产住进仓库根 `fonts/`——与 Dataview 同一套供应链纪律：官方发布资产原样入库、`.gitattributes` 锁字节、SHA-256 与许可（OFL 1.1 × 3、IPA 1.0 × 1，后者许可副本必须随行）备案于 docs/第三方组件.md，每族一份 SOURCE.md。安装契约把五个文件装进**用户级**字体目录（macOS `~/Library/Fonts`、Windows `%LOCALAPPDATA%\Microsoft\Windows\Fonts` + HKCU 注册表值、Linux `~/.local/share/fonts` + fc-cache），全程免管理员——哪一步要密码哪一步就是走错了。笔记库内零字节：字体不是库的内容，是库的环境。

**选型依据（2026-08-13 调研备案）。** 原版文楷 Regular 官方自认 PC 屏幕偏细，Screen 版（Medium 改标 Regular + 度量对齐 Roboto）是官方给出的解；GB 版取大陆规范字形（G 源），教学产品跟着《通用规范汉字表》走。思源宋体取 CN 子集单文件（11MB，实测基本区+扩展 A 零缺字），是四款里唯一带真 Bold 的。朱雀仿宋是风味项：家族名自带「预览测试版」后缀、GB2312 之外会混排，两条都写进它的 SOURCE.md，学员选它是知情选择。代价也备案：仓库从 4MB 涨到约 69MB，这是「安装时不临时下载」红线的直接价格。

**所有权边界。** 与 cssTheme 同款：全新安装预设 `LXGW WenKai GB Screen`；升级时 `textFontFamily` 缺失或为空才补，用户已设其他非空值一字不动。用户字体目录里已存在的同名文件绝不覆盖。升级时 Obsidian 若在运行，新字体要完全退出重开才可见（Chromium 启动时枚举一次系统字体）——交付话术随之更新，「重新加载」在这件事上是假话。

**三条红线的体检。** 人主导：装不装、装完用不用，都发生在用户发起的安装动作里，字体下拉永远归用户。脚本驱动：同一份施工源装出同一套字体、写下同一个家族名。官方 API：`textFontFamily` 是 Obsidian 自己读写的配置键，deviations 仍然只有三条。插件 main.js 在本版一个字节未动——版本号推进记录的是交付物的变化，不是代码的变化。

## 19. 读书笔记系统（v0.12.0）

### 19.1 动机与工作流

学员在微信读书、Kindle、苹果图书里读书、划线、写想法，这些内容散在三个 App 里，谁也不欠谁一份汇总。本系统把「读一本书」收进 ziminOS 的既有骨架：

1. **建书**：命令「新建读书笔记」→ 一个《书名》文件夹 + 一篇 `MOC-《书名》`（一本书就是一个项目，住项目目录）。
2. **补信息**：书籍详情（出版社、评分、豆瓣链接）由学员手填进「书籍信息」小节，或用第三方豆瓣插件插入——那是可选加速器，不是主线的一环。
3. **导划线**：命令「导入读书划线」→ 把三个 App 里导出的纯文本粘贴进弹窗 → 插件识别来源、解析、去重，把新划线合并进 MOC 的「全部划线」小节。
4. **炼卡**：在 MOC 里选中值得拓展的划线 → 命令「摘成卡片」→ 书的文件夹里长出一张十字段卡片，划线原文以引用块打底，光标停在正文起点。

### 19.2 架构判决：集成进 ziminOS，但绝不走网络（本节是「多插件协作还是集中一个插件」之问的唯一答案）

**判决：功能集中在 ziminOS 插件内；导入走「剪贴板文本解析」，不走任何 App 的网络 API。**

社区里现成的三类参考插件全部走网络私有接口：obsidian-weread-plugin 靠微信读书 Cookie 同步、obsidian-douban 靠抓取豆瓣页面、obsidian-kindle-plugin 的云同步靠 Amazon 登录。把它们的代码搬进 ziminOS，等于同时打穿「脚本驱动（零网络请求）」与「同输入同结果」两条红线；让学员另装三个插件，则是把三套账号配置、三种失败模式（Cookie 过期、IP 被封、登录失效）压回零基础学员头上——课程侧对同批插件的源码核实早有结论：微读插件正文全量重渲染、会把 `author` 的库级属性类型污染成 string；豆瓣插件产出非法 YAML；Apple Books 插件整文件覆盖。两头都不可取。

可取的路在中间：三个 App 都有**官方的纯文本导出**（微信读书「导出→复制到剪贴板」、Kindle 的 `My Clippings.txt`、苹果图书的选中复制/笔记分享），格式确定、离线可得。ziminOS 自研解析器认这三种文本——确定性正则、零网络、人粘贴才动（人主导）。豆瓣书籍信息因网络红线**不集成也不捆绑**，MOC 留好「书籍信息」小节作落点，装不装豆瓣插件由学员自便，装了它就是加速器，不装就手抄一行，主线不断。

### 19.3 数据模型

- **`type: book` 进 `NOTE_TYPES` 封闭枚举。** 导航页的「书籍」表（`type == "book"`）与 `isMocFrontmatter` 的放宽早已为它留位，本次把这个值正式注册。
- **书是第三类容器。** `createContainer` 的 `ContainerKind` 表加 `BOOK_KIND` 一行——那张表的注释早写着「将来若再来第三类容器（比如书籍），它是这张表多一条」，本次兑现。书住 `projectFolder`（不新增设置字段：一本书就是一个项目），`status: active`，读完用既有的「完成项目」归档。
- **「哪些 type 算容器」收成 `core/constants` 的 `CONTAINER_TYPES = [project, book]`，两个模块共用。** 消费方有三处，漏掉任何一处都不报错：`transitions` 漏掉，书就按不了「完成项目」（至少还给一句拒绝，用户看得见）；复盘的**「项目动态」**漏掉更糟——它按目录扫、按 type 认 MOC，认不出就把每一本在读的书当成「有改动却没有 MOC 的孤儿」点名报警，于是学员每读一本书，周复盘里就多一条他看不懂的假警报；**「完成的项目」与「年度全景」**漏掉则是另一种错——学员今年读完的书在月记、季记、年记里一本都不出现，而他明明是在这套系统里读的。三处一并放宽，其余守卫、确认框与回滚一字不动。
- **书的 MOC 骨架** = 项目 MOC 的那份 YAML 再加一个 `author`（学员跳过就整项不写）+ 三个空行写字位 + `## 书籍信息` + `## 全部划线` + base 卡片表（视图名「读书卡片」，or 筛选与项目 MOC 同构）。小节正文零提示注释（v0.5.1 纪律）。**`author` 必须落成单元素列表而非标量**：它在 `.obsidian/types.json` 里登记的是 multitext、属性示例笔记也写着「可以有好几位」，而属性类型是全库共享的一张表——某一篇写成标量就与其余笔记不同构，且这种不同构既不报错也不被任何视图挡下（这正是课程侧记下的那条教训：第三方微读插件把 `author` 写成 string 污染了库级注册表，且关开关、删笔记、卸插件都不回退）。
- **划线的形态**：`## 全部划线` 小节内，章节是 `### 章节名`，划线是顶层 `- ` 列表行，想法是缩进一层的 `- 💭 想法`。这个形态同时是导入命令的写入约定与去重判据的读取约定。
- **卡片**：与项目卡片同一套十字段（`CARD_FIELDS`），`up` 指向书的 MOC——因此 base 卡片表、反链、复盘视图对读书卡片零改动全兼容。

### 19.4 三条命令（读书组，功能色朱批红 #C15449——批注用朱笔，是「读书」唯一天然的颜色联想）

| 命令 | id | 行为 |
|---|---|---|
| 新建读书笔记 | `create-book` | 三问（书名 → 作者选填 → 一句话为什么读，后两问 Esc 跳过），书名自动包上《》，经 `BOOK_KIND` 走 `createContainer` 全套流程（防覆盖、光标落点、中文 Notice 一并继承）。books 模块不 import projects，声明一个「建书籍容器」的洞由 main 用 `createContainer` 填上——与 PersonPicker 同一手法 |
| 导入读书划线 | `import-book-highlights` | 站在书的 MOC 上直接进粘贴弹窗；站在别处则先从全库 `type: book` 里选一本。粘贴 → 识别来源 → 解析 →（My Clippings 含多本书时选一本）→ 确认框报「来源 / 识别出的书名 / 新增 N 条、跳过 M 条已有」→ 合并写入。零新增时不写盘、不弹确认，直接一句 Notice |
| 摘成卡片 | `excerpt-book-card` | 只在书的 MOC 上可用（别处给一句为什么不行）。选中文本 → 问卡片名与概述 → 书文件夹里创建十字段卡片，选中原文渲染成引用块，光标停在引用块之后。防覆盖同名卡片 |

三条都不进默认边栏（判据「一天里可能按不止一次」不满足），在设置 → 边栏勾选即得。

### 19.5 解析器（`modules/books/parsers.ts`，纯函数、零 obsidian import）

识别顺序按标记的无歧义程度排：先认 Kindle（`==========` 分隔行 + 「位置 #x-y」/「Your Highlight」行），再认苹果图书（「摘录来自」/「Excerpt From」），最后认微信读书（首行《书名》+ `◆` 章节行）。三种都认不出 → 一句 Notice 讲清支持哪三种、去 README 看导出方法，不写入任何东西。

- **微信读书**：App 内「笔记 → 分享 → 复制到剪贴板」产物，两代版式都认。旧版（约 v7.1–v8.2）`◆` 行开章节、`>> ` 行是划线、想法头是不补零的「YYYY/M/D 发表想法」；现行（约 v8.3 起）`◆ ` 行是划线、想法头是补零且无空格的「◆ YYYY/MM/DD发表想法」、**章节行没有任何标记**，全靠空行数判定（章节前 ≥2 个空行；跨段划线的续段隔 1 个；想法正文的段间隔 1 个；「原文：」的续段隔 0 个）。「点评」区与「◆ 日期 认为好看」评分行是评分不是划线，跳过。「发表想法」条目取「原文」作划线、想法文字作 `💭`；同一条原文往往还会以独立划线重复出现一次，解析完在书内先按归一文本去重、想法挂回被评论的那条。一份粘贴里可以连排多本书，每本以《书名》头重新开始。
- **Kindle**：`My Clippings.txt` 中英新旧四种元数据行都认（「您在位置 #x-y的标注」「我的标注 位置x-y | 已添加至」「Your Highlight on Location x-y」，含无 Your 前缀的老固件），中英条目会混在同一文件里；标注/笔记/书签/剪贴文章四类，书签与受版权保护的占位句跳过，笔记作 `💭` 挂到坐标覆盖它的标注上，挂不上就独立成行。**坐标取不到时是 null，不是 `[0,0]`**：个人文档与 PDF 只有页码没有 location，退成 0 会让全书区间相等、每条笔记都挂到第一条划线上；两边都有 location 就比 location，都只有页码才比页码，一边有一边没有则不比——宁可独立成行也不按顺序猜主人。文件含全部书：解析后按书分组，多于一本时让学员点选。Kindle 无章节，划线落在小节的无章节区。
- **苹果图书**：Mac 上复制划线的「"内容" + 摘录来自 + 书名 + 作者 + 版权行」结构，以及 iOS 分享笔记的对应变体；版权行与出处行剥掉，只留内容。

### 19.6 合并与去重（导入可以反复执行的关键）

- **判据**：划线文本**去除全部空白与强调符**后作键，**章节名同样归一**。去全部空白而非 trim，是因为排版整理会往汉英之间补空格、学员会顺手加粗——否则同一条划线在整理后再导一次就成了「新的」。章节名漏这层归一是最先犯的错：排版整理照样改写「### 第1章 A的意义」→「### 第 1 章 A 的意义」，于是划线认得出、章节认不出，每导一次就新开一个同名章节块、同一章被切成好几段且没有上限。查表用归一键、写标题用原文。
- **一条划线可以有好几条想法**（`ParsedHighlight.thoughts` 是数组）：隔半年重读、写下第二条体会是真事，微信读书会导出两个共用同一段「原文：」的想法条目。「这条想法是不是新的」只问**这条划线自己**有没有过——拿整个小节的想法当判据的话，「重要」「同意」这类短评一旦在别处出现过，学员这次写的就被静默丢掉。
- **落刀时同一行号上想法排在新划线之前**：两者会算出同一个数（既有划线是本段最后一行时，那个位置既是本段追加位、也是它自己的想法位），不分先后的话想法会挂到刚插进去的新划线名下。
- **只增不删不改**：已存在的键跳过；用户在小节里的手改（加粗、批注、删行）一概不碰。删过的行会在下次导入时回来——这是「只增」的正直代价，好过为了记住删除而引入一份影子状态。
- **章节归位**：新划线插进它所属 `### 章节` 块的末尾；章节块不存在则在小节末尾新开一块。小节里若出现围栏（学员挪过 base 块），插入点一律停在围栏之前。
- **无章节的划线落在第一个 `###` 之前那一段的末尾**，一个章节都没有时才是小节末尾。这条是真机测试逼出来的：Kindle 与苹果图书都不给章节，而同一本书很可能先从微信读书导过一次（带章节），此时「追加到小节末尾」恰好是追加进最后一个章节块的内部——那条划线在页面上就长在了它根本不属于的那一章名下，而这种归错不报错。
- **想法补挂**：划线已存在而想法是新的，把 `💭` 行补挂到那条划线名下——想法是学员亲手打的字，是整份导出里最贵的部分，不许静默丢。
- **`## 全部划线` 标题被删**：在文末重建标题再写入——位置不理想好过拒绝写入，与 `insertIntoSection` 同一条法。

### 19.6.5 三条对学员的承诺与一条先后关系（评审后补入）

- **每一次取消都出声**，三个取消点（选书、粘贴、选粘贴里的哪本书）说同一句话并告知剪贴板仍在。学员可能刚粘完几百 KB，静默会让他分不出「取消了」与「卡死了」。仓库惯例如此（建项目连没输名字都要说一句）。
- **Esc 在同一模块里只能有一个意思**：建书三问里 Esc＝跳过，那么摘卡的概述那一问也必须是跳过。取消点只能是必答项（卡片叫什么），不能是选填项——否则学员会照着刚学会的手势把整张卡片按没，还得重新选中划线、重新起名。
- **确认框比对「识别出的书」与「要写入的书」，不一致就亮橙色警告**。写入只增不删、无法撤销，而站错书恰恰最易发生：Obsidian 会替你恢复上次打开的那篇 MOC。书名比对归一到「去书名号 + 去空白」，免得纯写法差异天天报警。认不出书名时那一行照画（写「这段文本里没有书名」），空着会让学员只能盲点确认。
- **写入与打开的先后是硬约束：先打开那本书，再写盘。** 反过来会踩排版模块的纪律——它对「没开着的笔记」排一次两秒后的整篇重写，而两秒后那篇已在学员眼前，于是「绝不整理你正开着的那一篇」形同虚设，整篇重排会吞掉他正敲的中文。这是全仓库第一处「改一篇没开着的笔记、随即把它打开」的流程。
- 另两处小账：只补挂想法（新增 0 条）时成功提示必须报「已导入 N 条想法」而不是「已导入 0 条划线」，否则学员判定失败会回头再导一次；选书清单给归档的书标「（已归档）」，读完八本在读两本的人才分得出哪个是他要的。

### 19.7 纪律自查

- **人主导**：解析与写入全部由「粘贴 + 确认」触发，无监听、无定时器；确认框是唯一授权点。
- **脚本驱动**：解析器是纯函数，同一段文本永远解析出同一批划线；插件内仍然零网络请求。
- **公开 API**：全流程只用 `vault.read/process/create`、`metadataCache.getFileCache`、`Modal`；不新增红线偏离，`deviations` 仍是三处。
- **设置页零新页**：读书模块没有一个可配置项，按 v0.9.2「一个控件撑一整页是把分页做成摆设」的同一判据，不设第九张标签页；三条命令自动出现在边栏页清单（花名册驱动）。

### 19.8 验收

2. 同名再建一次：Notice「读书笔记 MOC 笔记已经存在」，原文件一字未动。

## 20. 读书笔记走向「一步完成」（v0.13.0）

### 20.1 推翻 §19 的理由

§19 交付的是「官方纯文本导出 + 粘贴解析」，它守住了当时的「零网络请求」红线，却把学员的操作留在了两步：在 App 里导出、粘贴进来。用户的判决原话是「**你让用户手动填写了太多没有必要的信息**」，并明令放宽第二条红线：**允许联网、允许登录**。

判据因此改写：书目字段（出版社、ISBN、页数、评分）机器查得到，划线在哪台设备上机器也查得到——把它们留给人不是克制，是失职。§19 的产出不删，降为兜底。

### 20.2 一条命令的全流程

`read-book`「读一本书」，学员只做两件事——报出书名、指认候选里哪一本：

1. **查书目**：豆瓣搜索页 → 候选清单（书名 + `作者 / 译者 / 出版社 / 年份 / 定价`）
2. **建档**：《书名》文件夹 + `MOC-《书名》`，YAML（aliases 全名、author 列表、source 豆瓣链接、type: book、status: active）与「书籍信息」小节（作者/译者/出版社/出版年/页数/ISBN/豆瓣评分/封面）**全部自动填好**
3. **取划线**：遍历本机可用来源，按书名认出这本书，直接写进「全部划线」小节

另两条：`sync-book-highlights`（读到一半再拉一次，共用取数与合并，不再建档）、`connect-weread`（扫码，一辈子一次）。

### 20.3 取数通道（全部实测确认）

| 环节 | 通道 | 实测 |
|---|---|---|
| 豆瓣搜索 | `search.douban.com/book/subject_search` 的 HTML，结果在 `window.__DATA__` 明文 JSON 里 | 200 ✓（`/j/search` 与 rexxar 的 JSON 接口一律 **403**，故走 HTML） |
| 豆瓣详情 | `book.douban.com/subject/{id}/` 的 HTML | 200 ✓，书名/封面/出版社/出版年/ISBN/评分/页数全可抓 |

| Kindle | 挂载卷宗里的 `documents/My Clippings.txt`，解析仍用 §19 的 parsers | 路径固定，扫挂载点即得 |
| 微信读书 | `weread.qq.com` 的 `/api/user/notebook`、`/web/book/bookmarklist`、`/web/review/list` | 端点存活 ✓（无 Cookie 时 401「LOGIN ERR」）；登录走 `@electron/remote` 的 BrowserWindow 扫码 |

### 20.4 实测逼出来的四条

- **丛书要剔除**：搜「人类简史」第一条是「[丛书] 人类简史三部曲」，它的详情页没有 ISBN 与页数，建出来是个字段全空的壳。丛书/套装/系列一律不进候选。
- **详情页失手要兜底**：拿候选那行摘要（`作者 / 译者 / 出版社 / 年份 / 定价`）补齐作者与出版社。

- **`author` 落列表不落标量**：`.obsidian/types.json` 把它登记为 multitext（§19.3 同一条教训）。

### 20.5 红线备案

第二条红线的放宽只对本模块生效，落地为 L1 deviations 新增的两条：其四，books 联网（两个出口，全走公开的 requestUrl）；其五，`require('@electron/remote')` 开登录窗口（按与外观开关同样的三条纪律收窄：只有开窗这一步借用、探不到就整条命令降级而不抛异常、声明与调用同处一个文件）。删掉 `modules/books` 即让零网络重新成立。

## 21. 书的身份与分类、设置页并页、名片致谢（v0.14.0）

### 21.1 为什么

四条改动出自用户同一次指示，共同点是**把已经成立的事实在界面上说出来**。

第一，书的 UID。全库每篇笔记都有一个 14 位时间戳 UID，因为它们没有别的身份。书有：ISBN 是国际标准书号，同一本书在任何一台机器、任何一个库里都是同一串数字。给书再发一个只有本库认得的时间戳，是给同一个东西造两个主键；而「这两篇是不是同一本书」一旦要靠比对书名来回答，同名书、繁简、副标题写不写都会让它失手。

第二，书的标签。分类不该问学员——他填的是此刻想到的词，豆瓣给的是几万人读完投出来的词。后者才是这本书在知识地图上的真实位置，也才可能与他书架上另外二十本对得上（两本书都被打上「方法论」，它们才连得起来）。这与 §20 那句「机器查得到的就不该问人」是同一句话。

第三，读书笔记的设置住进项目页。**一本书就是一个项目**——书落在项目目录、走项目的四态流转归档，代码里这条事实自 v0.12.0 就成立了；给它单开一张设置页等于在界面上否认它。

第四，客户并进人脉页。客户与人脉是两个物种，这条对**命令**仍然成立（建人脉和建客户是两件事，分组色也不同），对**设置**不成立：两页加起来只有四个字段，其中两个还是同一种东西（人脉目录 / 客户目录）。分页的意义是「一页看完就不必再往下翻」，而不是「每个物种都得有张页」；一张只有一个目录框的页，翻到它的人只会以为自己漏了什么。

### 21.2 UID = ISBN

`isbnUid(raw)` 是唯一实现，纯函数，两条约束定死了它的形状：

1. **必须产出数字。** `UID` 在 `.obsidian/types.json` 里登记为 `number`，属性类型是全库共享的一张表；某一篇写成字符串就与其余笔记不同构，而这种不同构既不报错也没有任何视图会挡下。拿不出数字就返回 `null`，由调用方回落到时间戳。
2. **ISBN 有两代。** 13 位纯数字原样取用（`9787115564672` ≈ 9.8e12，远在安全整数 9007199254740991 之内，不会重蹈 17 位 UID 那种「落盘即被静默四舍五入」的覆辙）；10 位（末位可能是 X）按国际标准换算成 978 开头的 13 位——换前缀、按模 10 重算校验位，前九位数字一位不动。这是无损转换不是猜测，因此老书也拿得到它的真号。

其余一律 `null`：豆瓣没给、给了个残缺串、或者根本是电子书没有书号。硬凑一个数字出来会污染主键。

判断只发生在 `readBook`：换得出就把 `uid` 装进 preset，换不出则整项不带，`createContainer` 自动落回 `nowStampAndUid` 那一份。容器流程因此不认识 ISBN。

### 21.3 标签 = 豆瓣分类

**取数点**：详情页那个「豆瓣成员常用的标签」小节（`id="db-tags-section"`）已经不在页面上了——四本实测样本（35503571 / 26943161 / 1084336 / 30329536）无一存在。同一份数据完整留在页首那行广告投放参数里：

```
criteria = '7:写作|7:方法论|7:笔记|7:读书笔记|…|3:/subject/35503571/'
```

豆瓣拿它去定向投广告，因此它必须是这本书最能代表读者群的那几个词，也就必须与常用标签同源、同序。`7:` 是标签，`3:` 是这本书自己的条目地址，只收前者。取它而不取 DOM 是权衡：页面版式改版频繁，而那行参数是发给广告系统的接口。它失效时的表现是「这本书没有标签」，不是报错也不是标错，因此没有兜底的必要。

**落地形态**：`书籍/{分类}`，写进 YAML 的 `tags` 列表，**不带井号**——井号是正文里的写法，属性里写的是标签本身，带上它会变成标签名的一部分。渲染出来仍是 `#书籍/方法论`。

**为什么要前缀**：让书的标签成片。标签面板里 `书籍/` 一展开就是整个书架的分类地图；散着的「方法论」会与灵感、卡片、日记里同名的标签混成一堆，从此分不出哪一条来自哪本书。

**合法性归一**（`tags.ts`，这是本节最容易出错的一段）：Obsidian 的标签里不能有空格、点号、括号，而豆瓣的分类里「尤瓦尔·赫拉利」「2017 书单」比比皆是。非法字符不报错，Obsidian 只会在那个字符处把标签截断——`#书籍/尤瓦尔·赫拉利` 悄悄变成 `#书籍/尤瓦尔`，一个谁也不会去核对的半截词。因此走白名单而不是黑名单：认 Unicode 字母（含汉字）、数字、下划线与连字符，其余一律换成连字符，再收拢重复连字符、掐掉两头。归一后撞车的只留第一个。

前缀多认一个斜杠（写「阅读/书籍」是正当的嵌套用法），做法是**按斜杠切段、每段各自归一、再拼回去**。第一版把斜杠也放进白名单再补两道 replace，评审当场打穿：「阅读 / 书籍」这种斜杠两边带空格的写法会拼出 `阅读-/-书籍/写作`——空格变成的连字符紧贴斜杠，而掐头去尾只掐整串两头；更狠的是「书籍 /」把整个书架的根变成 `书籍-`，标签面板里 `书籍/` 一展开什么都没有，而那正是这个设置存在的全部理由。按段归一之后「斜杠是分层符」这件事在代码里也成立，而不只写在注释里，同时删掉了一条正则与两行补丁。

**`bookTags` 是全函数。** 前缀与条数都是学员敲进去的自由文本，空串、怪数、手改 `data.json` 写进来的东西一律在这里回落默认，与 `core/folders` 的 `normalizeFolderPath` 担同一职。两处的判据都不是想当然的：

- 条数问「在不在 `BOOK_TAG_COUNTS` 里」而不是「大不大于零」——`NaN <= 0` 是 false、`n >= NaN` 恒为 false，一个 NaN 会一路穿过守卫与截断变成「豆瓣给几条写几条」，而设置页此时仍显示着「前 5 个」。0 在清单里，所以「不写标签」照旧是它自己。
- 前缀被清空时回落默认值，而不是解释成「关掉整个功能」。设置页的每一个文本框都承诺「留空即用占位符里那个默认」（`renderTextField` 的契约、`normalizeFolderPath` 的行为），只有这一处例外的话，学员清空输入框会得到一个静默失效的功能——而「关掉」已经有专门的控件了（条数选 0）。

**条数**：取前 N 条（默认 5），不是全取。豆瓣按投票数从高到低排，前几条是公认位置，往后很快滑向个人化的碎语（「知识要转化成生产力啊」真的在榜上）。截断本身就是筛选，不需要再发明一条「多长算废话」的规则。0 即不写标签。候选清单 `BOOK_TAG_COUNTS` 与默认值 `BOOK_TAG_DEFAULTS` 住在 `core/constants`，理由与 `INSPIRATION_INSERT_POSITIONS` 同一条：这份清单同时是**设置页的下拉选项**与**读取侧的合法性判据**，各写一份的话怪数会在一边被拍平、在另一边照单全收。

### 21.4 设置：项目页多一段，客户并进人脉页

**项目页**新增「读书笔记」一段，三项，排序是「书建出来长什么样 → 划线从哪儿来」：

| 项 | 类型 | 默认 |
| --- | --- | --- |
| 标签前缀 | 文本 | `书籍` |
| 标签条数 | 下拉（不写 / 3 / 5 / 8） | 5 |
| 微信读书 | 状态 + 扫码连接 / 断开 | 未连接 |

书目字段（作者、出版社、ISBN、评分怎么写）一项都不在这里：豆瓣怎么给就怎么落，让人去配等于让人去改事实。

微信读书那一项在设置页而不只在命令面板，是「人主导」的兑现——它是全插件唯一一份存在 `data.json` 里的凭据，必须有一处能看见它在不在、并且能当场撤掉；命令面板那条「连接微信读书」只能连不能断，一条只往一个方向走的命令不构成开关。断开只清本机那串 Cookie，不去动微信读书那边的任何东西。设置页不 import books 模块，扫码那一步经 `SettingActions.connectWeread` 由 main 填洞（第七个洞）。

**人脉页**收下客户的三个字段，页内按「人脉」「客户」切段。段标题由 `TextFieldSpec.section` 驱动，相邻两行段名一变就切一道——与边栏页按分组切标题是同一套画法，段序因此不需要另一张表。

**字段类型分两层**：`TextField` 是「画一个文本框需要知道的全部」，`TextFieldSpec` 才带 `tab` 与 `section`。这一层是必需的而不是洁癖——读书笔记的标签前缀必须紧挨着它的条数下拉框，而骨架画的字段一律排在面板之前，进表就会被拆到两段里去；分层之后面板也能画文本框，且没有闲置字段。

标签页由八张减到七张，`TabId` 的 `clients` 取值删除，`panels` 的 `Record<TabId, …>` 穷尽检查随之收紧。

**settings.ts 一分为二。** 加完这一段之后它逼近一千行，越过了 CLAUDE.md 那条「单文件 ≤800 行，超出即重构契机」。切法不是按行数腰斩，是按变更理由：`settingsModel.ts` 回答「这一页有什么」（TABS / TEXTS / TEXT_FIELDS / BOOK_TAG_PREFIX_FIELD 与它们的类型，零渲染代码、零 obsidian 依赖），`settings.ts` 回答「它怎么画出来」。加一个设置项、改一句文案动的是前者；改滚动行为、改标签栏样式动的是后者。切完 711 + 291 行。这条约束的用处正在于此——它先于人察觉到一个文件在同时干两件事。

### 21.5 名片致谢

作者名片以「致谢」收尾，两块性质不同：

- **思路致谢**（六条）：一行代码都没抄，但每一条都改变了 ziminOS 的某个决定。判据只有一条——**没有它，这里会走错**，因此每条后面那句话必须指得出具体的东西（是它让我们知道豆瓣的 JSON 接口走不通、是它让我们知道苹果图书的划线躺在哪个 SQLite 里）。「优秀的开源项目」这种句子一条都不要，那是客套不是致谢。排序即欠得多少，不是字母序。名单：obsidian-weread-plugin、obsidian-kindle-plugin、obsidian-apple-books-highlights-plugin、obsidian-douban、QuickAdd、Obsidian Linter。
- **随库交付**（九项）：Dataview、Minimal、Style Settings、Pikaicons、Simple Icons 与四款正文字体。这一块是许可要求的署名不是客套，所以只列名字与许可证、连排成一段文字而不是又一列条目——排成清单会让它看起来和上面一样重要。明细在 `docs/第三方组件.md`，两处须同步。

  收尾那句话必须**逐项属实**。第一版写的是「许可证全文随成品一同交付」，评审核实后判假：真正随文件交付全文的是 Dataview、Minimal、Style Settings 与四款字体；Pikaicons 只有一条许可声明，写在 `main.js` 开头的 banner 里；Simple Icons 是 CC0，法律上不要求署名，因此库里一个许可文件都没有。三种安排各自为真，就分三句写。这不是措辞洁癖——学员照着那句话去找一个根本不存在的许可文件，得到的结论是这套系统在署名这件事上说了谎，而署名恰恰是这一段唯一的作用。

位置就是态度：一张自我介绍的卡片，最后一段留给别人。整块压到弱化色与小一号字——这一段该被读到，不该被点着走。名片挂两处（README 顶部、设置页开荒页尾），致谢跟着一起去。

## 22. 微信读书取数改走网关（v0.14.0，真机实测修订）

### 22.1 老路是怎么断的

2026-08-14 用真账号实测《思维：关于决策、问题解决与预测的新科学》，v0.13.0 的实现**一条都取不回来**。逐个查下来，两条老路都已作废：

| 端点 | 真 Cookie | 空 Cookie | 判定 |
| --- | --- | --- | --- |
| `/api/user/notebook`（书架） | 200 有数据 | — | 活 |
| `/api/review/list`（想法） | 200 有数据 | **401** | 活 |
| `/web/review/list`（想法，旧） | 200 `{"errCode":-2012,"errMsg":"登录超时"}` | — | **死** |
| `/web/book/bookmarklist`（划线） | 200 `{}` | **200 `{}`** | **空壳** |

最后一行是这次调查的关键：那个端点**连身份都不校验**，书号写成 `00000000` 也回同样的 `{}`。它不是「这本书没有划线」，它是一具空壳；而两者在代码里长得一模一样。

### 22.2 活路：取数网关

参考 `obsidian-weread-plugin` 的源码——它的 `api.ts`（V1）与我们撞的是同一堵墙，`api-v2.ts` 才是活路：

```
GET  https://weread.qq.com/api/skills/apikeyGet        （带 Cookie，换令牌）
POST https://i.weread.qq.com/api/agent/gateway         （带 Bearer 令牌，取数）
     body: { api_name, skill_version: "1.0.3", ...params }
```

用到三个 `api_name`：`/book/bookmarklist`（划线，响应自带 `chapters` 章节表）、`/review/list/mine`（想法，条目自带 `chapterName`）、`/book/chapterinfo`（备用）。

同一本书实测对比：**老路 0 条，网关 3 条划线 + 1 条想法**。

**令牌刻意不落盘。** 它随时能拿登录态再换，存下来只会让 `data.json` 多一份会过期、要维护、断开时要记得一并清掉的凭据。全插件的持久凭据仍然只有 Cookie 一份，「断开」因此仍然只需清那一个字段。插件重载即重换，代价是一次 GET。

**换不到令牌时降级**，只取带想法的那些，并**必须留一句交代**（`SourceHit.note`）：静默地少交一半，与「这本书没划过线」在学员眼里长得一模一样，而前者是我们的问题。

### 22.3 判成败不能只看状态码

这是本次最值钱的一条。微信读书失败时**照样回 200**，把错误写在正文里。只看 `response.status` 的话，一次失败会被当成一份「一条划线都没有」的正常结果，于是学员收到「没在设备里找到这本书的划线」——一句关于他自己的书的假话，且正是那条红线的反面。

两套错误字段都要认：网关用 `errcode`/`errmsg`，老接口用 `errCode`/`errMsg`。认错一套等于不认。

顺带作废一个想法：书架条目上的 `bookmarkCount` 不可信（实测报 0，实有 3 条），拿它对账的方案试过并已放弃。

### 22.4 书名匹配收一批名字

同一次实测暴露的第二个洞。豆瓣写「思维 : 关于决策、问题解决与预测的新科学」，主书名只有**「思维」两个字**（文件名只能用主书名）；微读那头是带副标题的全名。于是逐字不中、归一不中，第三轮「互相包含」又被那道**四字门槛**挡住——防《活着》乱配的闸，把这本书一起关在外面。

出路不是把门槛降到两字（那会引回它本来要防的毛病），而是**把这本书已知的每个名字都拿来试**：主书名、带副标题的全名（正是写进 `aliases` 的那个）。全名一到手，第二轮归一比对直接命中，门槛一寸未动。

「读一本书」递 `[主书名, 全名]`，「同步这本书的划线」从 frontmatter 的 `aliases` 里取——两条命令必须递同一批名字，否则同一本书在两处会得到不同的匹配结果。

空名字要先滤掉：`normalize('')` 是空串，而空串被任何字符串包含，第三轮会拿它匹配上书架第一本书——一次静默的、100% 错的命中。

### 22.5 划线必须压平成单行

微信读书的 `markText` **可以带换行**（划过一整段又续到下一段）。原样写进去，那条划线自己撑破了自己那一行：`- 第一段` 之后的换行让第二段变成一条与列表无关的裸行，Markdown 上不再属于这一条，去重时也读不回来——下次同步算出的键含两段、文件里那条只有第一段，于是**每同步一次就重复一次，且没有上限**。

实测抓到：4 条划线里 2 条跨段，第二次同步新增 2 条。

压平放在 `mergeHighlights` 入口而不是写入处，为的是让写入与去重看到同一份文本——这正是本模块「去重键与写入格式必须同源」那条纪律的延伸；分开做就会再次分叉。

### 22.6 验收

1. 《思维》跑「读一本书」：4 条全部落进「全部划线」，章节名正确，想法缩进挂在它评论的那条下面。
2. 立刻再跑一次「同步这本书的划线」：新增 0、跳过 4。
3. 跨段划线在笔记里是**一行**，不产生游离的裸行。
4. 断开微信读书再跑：如实说未连接，不谎称「这本书没有划线」。

## 23. 划线与想法分块显示、书目搬进 YAML（v0.14.0）

### 23.1 为什么

用户看着自己刚同步出来的第一本书说：「整个项目乱得一团糟，并不能清晰地显示划线和我写的内容。」

他说得对。原先的形态是划线一条 bullet、想法缩进一层再加个 💭，三五条排下来，**书的声音和人的声音糊成同一串灰字**。而这两种字的价值完全不同：划线是书的，想法才是他的——整个读书笔记系统存在的理由就是后者。

### 23.2 标注块

```markdown
### 章节名

> [!quote]
> 划线正文

> [!quote]
> 另一条划线
> > [!note]
> > 我对这一句写的想法
```

三条取舍：

- **用 quote / note 两个内建类型，不自造名字。** Obsidian 与 Minimal 都为它们备了配色与图标；自造的类型在没装对应片段的库里会退化成灰框，而这套系统承诺换主题不必改笔记。
- **想法嵌在划线块里，不与它平列。** 想法是**对着某一句写的**，平列会让它变成一条与上下文无关的独白。
- **每块之后留一个空行。** 那一行是「这条到此为止」的唯一分界，写的时候靠它、读的时候也靠它。

### 23.3 两代形态：读得懂旧的，只写新的

换形态时**不迁移存量笔记**——「只增不删不改」这条承诺对已经写下的笔记同样成立，而一次静默的全库重写正是它要防的东西。

因此 `mergeHighlights` 的盘点段两种都认，`ExistingHighlight.legacy` 记着每条是哪一代。这不是多余的谨慎：不认旧形态的话，学员已有的每一本书在下次同步时会把全部划线**再写一遍**。

补挂想法必须按**那条划线自己的形态**落笔。往旧笔记的列表行下面塞一块标注，会得到一条既不属于列表也不属于引用的孤儿行。

代价是一本旧书会长成新旧混排。那是诚实的样子，不是缺陷。

### 23.4 书目搬进 YAML

`## 书籍信息` 整节撤销。同一批值改写进 frontmatter：

```yaml
translator:
  - "李慧中"
  - "祝锦杰"
publisher: "浙江人民出版社"
published: "2018-9-1"
pages: 324
cover: https://img2.doubanio.com/…
```

判据是**谁在读它**：那一节是给人读的登记表，而这些值机器读得更多——按出版年排、按页数挑、按出版社筛，都得是属性才做得到；摆在正文里它们只是五行谁也不会读第二遍的字。

搬家时刻意丢掉三样：**ISBN** 已经是 UID、**豆瓣链接**已经是 source、**豆瓣评分不写**——`rating` 是学员自己打的分，两个评分挤一个字段是在制造误读。

两个类型细节：

- `published` 是 **text 不是 date**。豆瓣给的是「2018-9-1」也可能是「2021-7」，后者根本不是一个完整日期，登记成 date 会让属性面板整列解析失败。
- `translator` 是 **multitext**，写成列表。与 author 同形同因：属性类型是全库共享的一张表，同一个字段一处标量一处列表就与其余笔记不同构了。

五个属性同步进 `.obsidian/types.json`，排在 author 之后（同类相邻）。

### 23.5 验收

1. 新建一本书：正文只有 `## 全部划线` 一个小节，书目五项在 YAML 里，属性面板类型正确。
2. 划线各成一块引用，想法嵌在它所属的那条里，块与块之间有空行。
3. 同一本书再同步一次：新增 0。
4. v0.14.0 之前建的书再同步一次：**新增 0**，旧的列表行逐字未动；新划线以标注块追加，新旧混排。
5. 给旧笔记里的旧划线补一条想法：写成 `\t- 💭 …`（旧形态），不混进标注块。

## 24. 苹果图书必须认 -wal（v0.14.0，真机实测修订）

学员问「我 Mac 上那本划过线的书能自动取到吗」，实测答案是**取不到**，而且失败得毫无声息。

原因是打开参数。`sourceAppleBooks` 此前以 `file:…?immutable=1` 打开两个库，初衷是「不去碰图书 App 正开着的库」。但 `immutable=1` 会让 SQLite **完全忽略 `-wal` 文件**，而苹果图书是 WAL 模式且把新数据长期留在 `-wal` 里迟迟不回写主库。同一台机器实测：

| 打开方式 | ZBKLIBRARYASSET | ZAEANNOTATION |
| --- | --- | --- |
| `immutable=1`（旧） | **0** | **0** |
| `mode=ro`（新） | 1 | 4 |

主库文件 124 KB、`-wal` 428 KB——数据几乎全在 WAL 里。插件因此如实汇报「这台机器上没找到划线来源」，一句听上去像事实的假话。

**改法**：先 `mode=ro`（只读，认 WAL），失败再退 `immutable=1`。初衷没错，只是选错了参数——`mode=ro` 同样一个字节都不写。退回那一支不是摆设：只读连接读 WAL 需要 `-shm`，库彻底 checkpoint 过、`-shm` 不在时 `mode=ro` 开不了，而那时陈旧快照与真相恰好是同一份。两条合起来才覆盖全部状态。

**验收**：机器上有一本在苹果图书里划过线的书，跑「读一本书」→ 划线与批注一并落进笔记；批注挂在它所属的那条划线下面。

2026-08-14 真机验收通过：同一份 `AEAnnotation` 用 `immutable=1` 查询为 0 条、用 `mode=ro` 查询为 3 条有效划线；在 Obsidian 1.13.7 中对《戒糖》执行「同步这本书的划线」，MOC 写入 3 个 `quote` 块与 1 个嵌套 `note` 块。立即再次同步，文件 SHA-256 前后不变，证明 WAL 读取、批注挂载与重复同步去重三段链路同时成立。

## 25. README 一键安装契约（v0.14.0 起）

用户不该先理解仓库结构，才能知道怎么安装。公开仓库 README 的第一个用户动作固定为「一分钟安装」：用户创建并命名一个空文件夹，用桌面智能体打开它，然后复制一整段 `text` 代码块。

这段指令必须同时说清五件事：

1. 事实源是 Gitee 默认分支上的 `skill/SKILL.md`，链接直指 `https://gitee.com/ziminzhao/zimin-os-v1/blob/main/skill/SKILL.md`。

**第二版把它变成并排两段（v0.19.0）。** 两份契约互不引用，首页只摆一段等于让智能体自己猜版次，而装错版次不报错、只让用户多出两本他没要的库。两段各自点名自己的仓库：第一版取 `gitee.com/ziminzhao/zimin-os-v1`，第二版取 `gitee.com/ziminzhao/ziminos-pro`。**分仓不是洁癖**——第一版契约会把施工源整份克隆到用户机器，指向 pro 仓库等于让每个免费用户顺手把付费交付物拉到本地。
2. 当前工作区就是用户已创建、已命名的最终 Obsidian 笔记库。
3. 智能体不再询问名称或安装路径，不创建子级笔记库。
4. 源码仓库不得克隆到当前工作区，取源、验证、清理均以 SKILL 契约为准。
5. 交付后告诉用户如何用 Obsidian 打开同一文件夹并执行初始化。

这不是又写一份安装手册。README 只负责把人导向正确入口，文件安全检查、全新安装/升级分支、用户配置保护、字体安装、产物验证与临时目录清理仍只在 `skill/SKILL.md` 定义。README 后文的完整安装步骤只回指顶部指令，不复制第二份话术，避免两处漂移。

### 25.1 发布前验收

1. Gitee 默认分支首页在架构介绍之前显示「一分钟安装」。
2. 指令住在 fenced `text` 代码块，整段可一次复制，不夹带 Markdown 引用符。
3. 把指令交给一个只知道当前工作区和 Gitee 链接的桌面智能体，它能从 `skill/SKILL.md` 独立完成原地安装，最终根目录只有 `.obsidian/` 与 `README.md`。
4. 公开 README 对产品的数字与边界与代码一致：三十五条命令、八张设置页（v0.18.0 起），网络仅服务读书取数与日历节假日校验，不再保留「八条命令」「二十九条命令」或「读书是唯一网络例外」的过期说法。
5. 第二版仓库的首页两个版次各有一段指令，各自指向自己那个仓库的契约；仓库里不存在任何一条仍指向 `github.com/zhaozimin/ziminOS` 的克隆或安装指令——那个地址已 403，留着会让安装停在克隆这一步，而报错听上去像网络问题。

## 26. 中国农历日历与调休无感更新（v0.15.0）

日历不是又一张「能看日期」的装饰卡，而是五级时间记录的图形坐标。它默认常驻右侧边栏，没有关闭设置；用户点的不是文本链接，而是时间维度本身：

- 点日期：打开或创建该日日记。
- 点 ISO 周数：打开或创建该周周复盘。
- 点月：打开或创建月复盘。
- 点季度：打开或创建季度复盘。
- 点年：打开或创建年复盘。

日历只注入 `periodKey + day`，笔记文件名、目录、模板与幂等创建仍由 review/openPeriodNote 唯一实现。这是 OCP 的边界：新增一种入口，不分叉第二套周期笔记系统。

### 26.1 年、季、月是三个独立坐标

头部参考 Dust Calendar 1.4.0 已经过验证的布局：第一行是年与季度，第二行是月份与「今 / 月·年视图」。但迁移的是交互原则而不是 React/Redux 代码：ziminOS 仍用原生 Obsidian ItemView 和语义 CSS 变量渲染。

- 年箭头每次±1年，保留当前月份。
- 季度箭头每次±3个月，保留在季度内的相对月份。
- 月箭头每次±1个月，跨年时自动归一化年月。
- 三个标题仍是年/季/月复盘入口，箭头只导航；「今」是全局归位动作，无论当前在月视图还是年视图，都显式切回月视图并定位当天；「月/年」才是常规视图切换。

箭头常驻但低对比，悬停与键盘聚焦时加强；这比桌面端完全隐藏更易发现，在没有 hover 的触屏上也始终可用。月网格为「ISO 周数 + 周一至周日」八列，节日/节气用主题强调色，今日用实心强调色，非本月日期降低透明度。

### 26.2 三层日历事实

1. **公历网格与 ISO 周**：本地纯函数计算，无网络。月视图以周一开始，一周归属取 ISO 周年，所以 12 月末可显示下一个周年的 W01，不伪装成本年周。
2. **农历、节气与传统节日**：由锁定版本 `lunar-typescript@1.8.6` 本地换算。显示优先级为传统节日 / 节气 / 农历月首 / 农历日名。不调用库里的静态 HolidayUtil。
3. **法定休息与调休上班**：只表达国务院通知对常规周末的例外，普通周末仍由本地日期判定。「休」表示法定放假，「班」表示调休上班，两者不能只靠颜色区分，必须同时有文字标识。

### 26.3 无感更新不等于后台轮询

日历首次打开或用户切换年份时，HolidayService 检查当前显示年及下一公告年。24 小时内的数据直接读 `holiday-cache.json`；过期后按 jsDelivr → Fastly jsDelivr → GitHub Raw 顺序请求 holiday-cn 年度 JSON。请求不并发洪泛，也不在插件启动后挂定时器。

远端数据必须同时通过年份、ISO 日期、重复日、布尔类型与 HTTPS `gov.cn` 公告链接校验，才能覆盖缓存。其中任意一步失败，都安静保留最后一份好数据；不清空日历，不把不可验证的网络内容当成官方事实。同一个年份请求失败后，会话内 5 分钟不重试，避免断网时每次重画都发请求。

v0.15.0 内置国务院 2026 年放假通知的 39 个例外日，保证断网首启仍可用。尚未公布的年份明示「待公布」，不用上一年规则猜明年调休。

### 26.4 负责任的更新边界

用户不需要创建网站、不需要手工维护 API，也不需要配置密钥。holiday-cn 是免费开源数据镜像，但它不是政府官方 SLA 服务；因此 ziminOS 同时保留内置快照、多镜像和最后好数据三层退路。如果未来要承诺商业级 SLA，再增加 ziminOS 自己签名、审核、发布的镜像；在没有该承诺之前，不先建一个需人年年喂数据的网站。

### 26.5 验收

1. 2026-02-17 显示「春节 / 正月初一 / 休」；2026-01-04 显示「班」。
2. 2025 年 12 月末跨年周显示 2026-W01，点击后打开 2026-W01 周复盘。
3. 断网打开 2026 年仍能读内置快照；远端返回重复日或错年数据时不覆盖缓存。
4. 点日/周/月/季/年各创建一篇笔记，再点一次不重复创建且不覆盖已写内容。
5. 测试库升级只替换 main.js / manifest.json / styles.css，data.json 的 SHA-256 前后相同。
6. 年、季度、月份三组左右箭头各自导航；切换月/年视图后坐标不丢失，跨年翻月与跨年翻季度都得到正确年月。
7. 在任意年份的年视图点「今」，必须回到月视图并高亮当天，不停留在年视图的当前月份。

## 29. 文件夹计数（v0.16.0）

> **章号说明**：本节与下一节原编为 §27 / §28，v0.18.0 合线时改为 §29 / §30——`main` 那条线已把 §27 用于「代码审计加固」、§28 用于「Gitee 公开部署源」。让号的是后到的一方；两条线的内容都完整保留，没有任何一节被覆盖。

需求来自一句朴素的话：「在文件夹右侧显示当前文件夹内有多少篇笔记，或者说有多少个文件夹」，并点名参考社区插件 File Explorer Note Count。

这句话里有一个被顺口带过的分岔——**笔记数和文件夹数是两个数**。它不是提问者没想清楚，恰恰是这套系统的结构逼出来的：ziminOS 里的文件夹不是杂物箱而是容器。`01-projects` 里装的是项目，一个项目文件夹里装的是卡片，一本书的文件夹里装的是摘出来的划线。于是同一棵树上，`01-projects` 这一行该回答的是「我有几个项目」（子文件夹数），而《写一本书》那一行该回答的是「攒了多少张卡片」（笔记数）。两个都对，取决于站在哪一层。

### 29.1 一个数字，两个答案

按文件夹自动切换口径的方案被否掉了：那要靠「这个文件夹有没有 MOC」之类的推断，而推断错了不会报错——用户只会看到一个不知从何而来的数字。侧边栏并排放两个数也否掉了：它的宽度以像素计，两个数会把文件夹名挤成省略号，为了一个附带信息牺牲主信息。

落地是三条：

1. **常驻的只有一个数字**，口径由用户在设置里选一次：笔记 / 文件夹 / 全部条目（含附件）。
2. **悬停把三项一起报出来**（`12 篇笔记 · 3 个文件夹（含子文件夹）`）。于是另一半答案随时能拿到，不必回设置页换口径——这是那句需求里「或者说」三个字的完整兑现。
3. **另有一个「含子文件夹」开关**，与口径分成两个设置而不是一个六选一的下拉框：「数什么」问的是我关心哪一类东西，「数多深」问的是这个文件夹算到哪儿为止，两个问题彼此独立。

默认是「笔记 + 含子文件夹」。它是唯一一档在任何层级上都说得通的口径——关掉递归时 `01-projects` 会显示 0，与一个真正的空文件夹长得一模一样，那个数字于是既不解释什么，还让人以为功能坏了。反过来，想让它回答「我有几个项目」，关掉递归正是对的做法，界面上也这么写。

空文件夹与库根一律不显示数字。前者因为一个 0 不解释任何事，后者因为根那一行的标题被 Obsidian 与 Minimal 双双压平——往一个看不见的地方挂数字，等于让它的位置由主题决定。

### 29.2 计数不排除 90-system

这是一条与既有纪律**相反**的决定，因此必须写清理由。V4 立下的「一切检索排除 90-system」服务的是二十二个知识视图：属性示例里的 `[[某位客户]]` 是教材不是事实，让它进名录是错的。但计数回答的不是「这里有多少知识」，而是「这个文件夹里有几个文件」——文件浏览器把 90-system 明明白白摆在屏幕上，给它一个减掉了模板的数字，那个数字就与用户自己点开看到的对不上。判据是：**这个数字要能被用户当场数一遍验证**。

### 29.3 不读 view.fileItems

参考插件的实现读文件浏览器视图的 `view.fileItems`，那个字段不在 `obsidian.d.ts` 里。ziminOS 改走两步公开 API：`workspace.getLeavesOfType('file-explorer')` 拿到叶子，`View.containerEl` 拿到那块 DOM，再在里面找 `.nav-folder-title[data-path]`。

这仍然是一层宿主假设，已按第 26 节同样的格式记入 `CLAUDE.md` 的偏离备案（第 7 条），并与前六条一样收窄成三句话：四条约定与调用处同处一个文件、探不到就整条功能静默缺席、删掉 `modules/explorer` 即让本条消失。区别值得说明：它依赖的是**主题与 CSS 片段共用的同一层约定**（Minimal 自己就有七条规则指着 `.nav-folder-title`），不是别人的私有字段。

### 29.4 无定时器，也不自激

重算由两类事件驱动，没有定时器也没有轮询：

- **一个 MutationObserver** 观察文件浏览器容器的子节点增删——展开、收起、懒渲染都在这一类。
- **vault 的 create / delete / rename 三个事件**。改名必须单独听：Obsidian 复用同一个 DOM 节点、只改它的 `data-path`，那不是子节点变更，观察者一个字都看不见，而那一行的数字已经是别人的了。

两类事件都只排一次 80ms 防抖，到点后一趟遍历数完全库（O(全库)，与屏幕上展开了几行无关），再把每一行该显示的数字写上去。

往 DOM 里写数字本身也是一次子节点变更，因此断环有两道：其一，变更回调先问「这变化是不是我自己引起的」——判据与 `SelfWriteGuard` 同形，只是这里连时间窗口都不需要，我们的痕迹都带着 `ziminos-folder-count` 类名；其二，值没变就一个字都不写。第二道单独就能让它收敛，但收敛不等于不该成环。

### 29.5 设置页第八张标签「文件」

`TabId` 加 `explorer`，`TABS` 加一行，`panels` 表加一个渲染函数（`Record<TabId, …>` 的穷尽检查保证漏写即编译错）。它是 v0.14.0「八张减到七张」之后重新回到八张，但换了一张：那次减掉的 `clients` 是因为两页加起来只有四个字段；这次加上的 `explorer` 是因为三项彼此独立、缺一个就说不完整。同一条判据的两面。

排在「边栏」之后：命令坞与文件浏览器同住屏幕最左边那一条，学员找「左边那个数字的设置在哪」时翻的正是它旁边那一页。图标是照同一套 Pikaicons 画法补画的一个文件夹，与 `dock` 并列成为第二个不对应任何命令的图标名——两枚画的都是那块地方本身而不是它的功能（文件夹上刻意不挂数字），因为把当期功能画进图标，下一件功能进来时图标就开始撒谎。

三项设置都要让 `syncFolderCount` 叫一声：它们改的不是「下一次触发时怎么办」，而是此刻屏幕上那串数字本身。这是 `SettingActions` 里第三处重绘同步，与状态栏按钮、边栏图标同形同因——已经画在屏幕上的 DOM 不会自己再问一次设置。

### 29.6 验收

1. 展开 `01-projects`，每个项目文件夹右侧有数字；空文件夹没有数字；库根那一行没有数字。
2. 默认设置下 `01-projects` 的数字等于它下面全部 md 文件数（含各层子文件夹）；把「含子文件夹」关掉后它变成 0，把「数什么」改成「文件夹」后它变成项目个数。
3. 鼠标停在任一数字上，提示同时报出笔记数与子文件夹数，开着递归时带「（含子文件夹）」。
4. 新建一篇笔记 / 删掉一篇 / 把一篇拖到另一个文件夹，两个文件夹的数字都在不到一秒内跟上，不需要重启也不需要折叠再展开。
5. 重命名一个文件夹，它的数字仍然是它自己的（这一条专门验 rename 事件；只靠 MutationObserver 会留下上一个名字的数字）。
6. 把「文件夹右侧显示计数」关掉：数字当场全部消失，DOM 里搜不到 `ziminos-folder-count`，且不需要重启。
7. 禁用 ziminOS 插件：同上，一个残留节点都没有。
8. 文件夹名很长时，名字截断成省略号而数字完整可见——挤压发生在名字上，不发生在数字上。
9. 90-system 有数字，且等于它里面实际的笔记数（不排除功能目录）。
10. 测试库升级只替换 main.js / manifest.json / styles.css，data.json 里三个新字段以默认值补齐，用户原有设置一字不改。

## 30. 七个社区功能的取舍：五个自己写，两个打包（v0.17.0）

用户点名七个开源插件，并给了处置规则：「如果有插件非常复杂，可以直接将它的插件放在插件包中」，其中 Quiet Outline 明确「直接放进笔记库，不需要额外集成」。

划这条线时，**许可证比复杂度更硬**。查证结果：

| 插件 | 上游 | 许可 | 最后更新 | main.js | 处置 |
| --- | --- | --- | --- | --- | --- |
| Outliner | `vslinko/obsidian-outliner` | MIT | 2026-06-27 | 464 KB | 打包 |
| Quiet Outline | `guopenghui/obsidian-quiet-outline` | MIT | 2026-08-07 | 603 KB | 打包（用户点名） |
| Recent Files | `tgrosinger/recent-files-obsidian` | GPL-3.0 | 2026-07-21 | 53 KB | 自己写 |
| Remember cursor position | `dy-sh/obsidian-remember-cursor-position` | MIT | 2026-07-15 | 105 KB | 自己写 |
| Paste URL into selection | `denolehov/obsidian-url-into-selection` | 无 | 2025-08-27 | 7.9 KB | 自己写（不能转发） |
| Show Current File Path | `ravimashru/obsidian-show-file-path` | 无 | 2021-10-13 | 39.7 KB | 自己写（不能转发） |
| Legacy vault switcher | `Quorafind/Obsidian-Legacy-Vault-Switcher` | 无 | 2024-06-22 | 5.4 KB | 自己写（不能转发） |

三条判据，按优先级：

1. **没有许可证＝保留一切权利，不能转发。** 三个插件因此连「打包」这个选项都不存在，不论它多小多方便。
2. **体量决定要不要自己写。** Outliner 重写的是 CodeMirror 6 的列表编辑内核，Quiet Outline 自带 Vue 3 与一整套虚拟树——自己写一遍等于在知识管理插件里再养一个编辑器内核、再引一套前端框架。这与 Dataview 当年的判据一字不差。
3. **能自己写的一律自己写。** 这是仓库既有的家法，不是这一版的新规矩：QuickAdd 与 Linter 都是这样被替换掉的（见 V1 与 §14）。GPL-3.0 的 Recent Files 与 MIT 的 Remember cursor position 都**可以**打包，但一个 53 KB、一个 105 KB 的插件换来的两件事，自己写各只有两百多行，而且能与 ziminOS 的设置页、命令注册台、状态文件纪律长在一起。

「初始化时直接下载进去」这句要求按仓库既有的交付形态落地：**不是安装期联网下载，而是把锁定的发布字节提交进 `vault/.obsidian/plugins/`**，安装器只做拷贝。对学员的效果一样（打开即有），但断网可装、版本可复现、SHA-256 可核。安装期零网络这条纪律不因这次新增而松动。

### 30.1 五个自己实现的落点

它们不是散在五处，而是按「变的是什么」归到三个模块：

- **modules/editing**（新）——粘贴成外链、光标记忆。两件都不改变库里有什么，只改变敲键盘的手感。
- **modules/explorer**（扩容）——最近文件、状态栏当前路径，与 v0.16.0 的文件夹计数合成同一个模块。三件事回答同一个问题：我在哪、有哪些、刚才去过哪儿。这就是「不会在自己的库里迷路」，因此同住第八张「文件」页，并只向设置页交回**一个** `syncExplorer`。
- **modules/legacy**（新）——旧版三入口，见 §30.3。

设置页因此到九张：`排版 → 编辑 → 文件 → 边栏`。这四张的先后是从「字」走到「屏幕」；边栏排在最末不是随手放的——它在 `main.ts` 里必须最后装配（照命令花名册摆图标，摆时花名册必须收齐），而 TABS 承诺自己的顺序就是装配顺序。v0.16.0 把「文件」摆在边栏之后曾经打破这条承诺，那时它一条命令都不注册所以没露馅；这一版它有了两条命令，承诺重新收紧。

### 30.2 状态不是设置

新增两份运行时状态文件，与日历的 `holiday-cache.json` 同一档：

- `recent-files.json`——最近打开过哪几篇（留 50 条，显示设置里那几条）
- `cursor-positions.json`——每篇笔记上次的光标行列与滚动位置（留 200 篇，LRU 淘汰）

它们**绝不**进 `data.json`，判据来自升级契约本身：那份契约承诺 `data.json` 的 SHA-256 前后不变，而这两样每分钟都在改。混进去之后那条承诺永远验不过，而验不过的承诺等于没有承诺。SKILL.md 的第 0a 条因此从「保留 holiday-cache」推广成「保留插件目录下的三份状态文件」，并顺手写清了状态与选择的区别：状态丢了只是少一点便利，选择丢了是把学员的设置抹掉。

两份都做逐条验形（有限的非负数字、非空字符串），理由与节假日缓存一样：它们是用户能手改、也可能被同步工具截断的普通 JSON，而读出来的数字会直接喂给 `setCursor` 与 `scrollTo`——一个 NaN 就让光标跑到不存在的行上。

### 30.3 红线第二处缺口

「旧版三入口」必须调三处非公开成员：`app.setting.open`、`app.openVaultChooser`、`app.openHelp`。`obsidian.d.ts`（1.13.1）里 `App` 的公开成员只有十项，这三件事一件都不在其中；`executeCommandById` 同样不在，所以那条路也不是出路。

这次借用**由用户明确授权后才开**，备案第 8 条，三条纪律逐条对齐第 3 条（`customCss`）：

1. 只借「点下去要发生什么」这一步——摆按钮走公开的 `addRibbonIcon` 与命令注册台。
2. 模块增强声明成可选成员，并在**点下去的那一刻**验形（不是注册时验一次：热重载与版本升级都可能让答案在之后改变）。
3. 声明与调用同处一个文件，删掉 `modules/legacy` 即让红线重新完整。

**一处与预案不同的落地：** 预案写的是「探不到就不画那一枚按钮」，实际做的是照常注册、点下去说明白。因为 CommandRegistry 有一条更硬的纪律——命令必须在任何情况下都可见可点，用户在做不到时该得到一句「为什么」，而不是眼看着命令凭空消失。两种都是降级，后者与其余三十四条命令的行为一致。

三条命令进 `DEFAULT_RIBBON_COMMANDS`（默认七条 → 十条）：一个需要先去设置页勾选才回来的按钮，等于没有回来。它们单列成命令分组「旧版」并着中性灰——做的是 Obsidian 自己的事，不属于 ziminOS 的任何一摊，颜色把这句话说出来。

### 30.4 settings.ts 第二次分家

这一版把 `settings.ts` 顶到 895 行，破了 ≤800。按家法「超出即重构契机」就地分家，判据与 v0.14.0 分出 `settingsModel.ts` 时一字不差——**变更理由不同**：

- `settingsModel.ts`（443 行）：有什么、以及要别人替它做什么（`SettingActions` 这一版搬进来了——骨架与面板两边都要认它，放在共同的下游才不成环）
- `settings.ts`（278 行）：骨架怎么画——标签栏、一页的四段、开关与文本框、折叠区
- `settingsPanels.ts`（653 行）：每一页塞什么——九个渲染函数

面板向骨架借四样东西（`ctx` / `actions` / 画开关 / 画文本框 / 重建整页），收在 `PanelHost` 一个接口里；`ZiminosSettingTab` 实现它。唯一排在高级折叠**之后**的作者名片仍归骨架而不归面板：落款的位置是跨九页的承诺，不是某一页自己的事。

### 30.5 验收

1. 选中一段文字，粘一条 `https://` 网址 → 变成 `[选中的字](网址)`；粘一个 `www.` 裸域名 → 原样粘贴；不选字直接粘 → 原样粘贴；选中跨两行的文字再粘 → 原样粘贴。
2. 在一篇长笔记中间放好光标，切走再切回来 → 回到原处；完全退出 Obsidian 再打开 → 仍回到原处。
3. 从一条 `[[某篇#某标题]]` 跳进去 → 落在那个标题上，**不**被上次的位置抢走。
4. 关掉「记住光标位置」后再切换笔记 → 不再恢复，也不再往 `cursor-positions.json` 写新条目。
5. `Cmd + P` →「打开最近文件」→ 右侧栏出现清单，点任一行打开对应笔记；重命名其中一篇 → 那一行跟着改名且仍点得开；删掉一篇 → 那一行消失。
6. 把「显示几条」从 10 改成 50 → 立刻有 50 条（不是从此刻重新攒）；把「怎么排」改成按修改时间 → 顺序按 `mtime` 重排。
7. 状态栏显示当前笔记路径，点一下 → 系统剪贴板里是完整路径且弹出提示；关掉开关 → 那一块消失，命令「复制当前笔记路径」仍可用。

9. 在一个探不到那三个成员的环境里点它们 → 弹一句中文说明，**不**抛异常、**不**让命令消失。
10. Outliner 与 Quiet Outline 随全新安装就位并默认启用；`community-plugins.json` 含五个 id；两者的 `main.js` SHA-256 与 `docs/第三方组件.md` 记录一致。
11. 测试库升级只替换受管运行文件；升级前已存在的五份 `data.json` 与 ziminOS 那三份状态文件 SHA-256 全部不变。
12. 设置页九张标签，顺序为 开荒 / 项目 / 灵感 / 复盘 / 人脉 / 排版 / 编辑 / 文件 / 边栏；「文件」页三段、「编辑」页两个开关且没有高级折叠区。
### 30.6 用户评审后的两处修订

**其一，排版并进编辑（九张页 → 八张）。** 原话是「排版和编辑应该算作一起，它们属于一类」。这一条的判据比 §21.4 那两次并页都直白——**它们发生在同一个时刻**：你在编辑器里敲字，粘贴变成链接、光标记住位置、走开之后这一篇被整理成标准写法，是同一件事的三个瞬间。排版单列成页时，学员得先分清「整理格式算不算编辑」才知道该翻哪一页，而那个问题本身就不该存在。

并的是**页**不是模块：`modules/format` 的边界、命令与监听一个字没动，只是画那两个控件的地方从 `format` 那一页搬进 `editing` 那一页的下半段。`TabId` 删掉 `format` 一个取值，`render` 表漏删的那一行立刻编译错——这正是那张 `Record<TabId, …>` 表存在的意义的反面证明。页内先后是「立刻发生的」在前（粘贴、光标）、「走开之后发生的」在后（排版一道小标题带自动开关与九条规则）。

**其二，最近文件不显示路径。** 原话是「历史最近文件的显示方式应该与文件列表一致，不需要在下面多增加路径……我的想法是，尽可能不要增加这个路径显示」。原实现是两行：名字一行、所在文件夹一行灰字。去掉的判据是它破坏了这张清单的身份——**文件树里一行就是一个名字**，多出一行灰字之后它就从「同一棵树的另一种排法」变成侧栏里另一种控件，而学员每认一行都要多读一行不需要的字。

「与文件列表一致」落实到具体做法上，不是抄一遍主题的规则，而是取 Obsidian 自己给出的那套变量：`--nav-item-padding / -size / -weight / -color / -color-hover / -background-hover`，六个都在本机运行的 1.13.7 里核实存在。于是换主题、或在 Style Settings 里调过侧栏字号之后，这张清单跟着一起变，不会变成侧栏里唯一一块「别人家的控件」；六个都带回落值，取不到也不出错。

完整路径没有丢，只是搬进悬停提示——两篇同名笔记要分辨时问一句就有，平时不占屏幕。用户提过的备选方案（名字左对齐、路径右对齐同一行）没有采用，因为他同时说明了偏好；那个方案仍然成立，改动只在 `renderRow` 一处。

### 30.7 追加验收

13. 「最近文件」清单每行只有笔记名，行高与字号与文件浏览器里的一行**目视一致**；把 Style Settings 里的侧栏字号调大，两处一起变。
14. 悬停任一行显示完整路径；两篇同名笔记在清单里靠悬停能分辨。
15. 设置页八张标签，顺序为 开荒 / 项目 / 灵感 / 复盘 / 人脉 / 编辑 / 文件 / 边栏；「编辑」页从上到下是粘贴开关、光标开关、「排版」小标题、自动整理开关、九条规则。
16. 命令「整理当前笔记格式」仍在命令面板与边栏清单的「排版」分组里——并的是设置页，不是命令分组。

## 31. 两个版次与三库系统（v0.16.0）

### 31.1 判据

第一版（免费·单库）已经在外面流传，它必须原样活着。第二版（付费）在它之上加两本库与一个口述入口。两版共用同一份 `main.js`——分成两个插件产物就等于分成两套代码，而两套代码迟早在同一个 bug 上修两次、修错一次。

隔离因此落在**装配期**而不是运行时：第二版安装器写下一个第一版永远没有的版次标记 `.obsidian/plugins/ziminos/edition.json`；`src/core/edition.ts` 在 onload 最前面读它；main 拿到 `free` 就根本不接第二版那条线。免费库里 `modules/eternal/` 一行都不执行，没有命令、没有视图、没有监听。

失败方向是刻意的：文件缺席、读不动、JSON 坏了、字段不认识，一律回落 free。**坏标记把付费功能塞进免费库比坏标记让付费库退化严重得多**——后者用户看得见（功能不见了会来问），前者他看不见（凭空多出的文件不会有人报错）。

标记同时是三库布局的唯一事实源。它必须是数据而不能是常量，因为从第一版升级上来的用户那本库叫什么是他自己当初取的。

### 31.2 三本库

| 库 | 职责 | 初始化 | AI 参与度 |
| --- | --- | --- | --- |
| 兼收并蓄 | 进料口，只接住不加工 | 安装器直接建好 | 只判归类，不改原话 |
| 以人为本 | 工作台，= 第一版那本库 | **用户手动点初始化** | 仅口述日记一个入口 |
| 赛博永生 | 成品库，卡帕西 LLM wiki | 安装器建好骨架与 Schema | 全流程 |

分家的判据不是内容不同，是**三种内容对「被改写」的容忍度完全不同**。只有「以人为本」保留手动开荒，因为它的骨架由插件代码生成，另外两本是文件拷贝。

`vault/` 是两版共享的程序与外观资产唯一出处，`vault-pro/` 只装第二版特有内容；同一份资产不存两遍，否则迟早只更新其中一遍，而两本库长得不一样不会报错。

### 31.3 归档移交

用出库单而不是跨库直写。Obsidian 的 vault API 被沙箱锁在本库内，借 Node `fs` 能写隔壁库，但那是「只用官方公开 API」第三次破例且手机上必炸。因此插件只往本库 `90-system/赛博永生出库单.md` 追加一行，搬运与提炼由桌面智能体一次完成。

只有 `done` 触发移交。暂停与放弃同样搬进归档目录，但它们不是结论——一个还没想好、一个明确不要了，当成知识素材会让《赛博永生》长出一堆讲「我当时没做完」的页。

UID 是跨库身份。项目可重新开始再次完成，同一 UID 第二次出现意味着「同一件事有了新版本」，不是「又一个新项目」；插件保证单子上不出现两行，智能体按 UID 更新已有的 wiki 页而不是新建一页。

「哪些原料已提炼」的答案在《赛博永生》的 `90-系统/账本.md` 而不是原料上的标记——往原料里写一个字段，它就不再是当初归档时的那份东西了。两处解析都跳过代码围栏：账本正文里就写着格式示例，逐行扫会把示例里的 UID 当成真账。

### 31.4 口述捕获

第二条红线的措辞改写为「写入用户原话的路径上零 AI」。LLM 只回答「这句话是灵感、剪藏还是日记」；清洗、链接搬运、人名双链、插入位置、日记骨架全部交给 `skill-pro/scripts/notectl.py`，零第三方依赖，31 条回归测试钉住。

三处只在中文里发作的坑收口于脚本：地址字符集必须显式排除汉字、配平的右括号属于地址本身、全角竖线必须换成半角。人名双链只在「以人为本」的日记里发生——人物档案住在那本库，在「兼收并蓄」里写双链是一条永远点不开的死链。

整套捕获只有一处允许为写入而反问：今天的日记还没建时问主题。主题是用户对这一天的结论，AI 替他写等于伪造；「没给 theme」与「明确传空」是两种语义。

### 31.5 验收

1. 一个没有 `edition.json` 的库里，归档一个项目不产生出库单，`待搬运` / `待提炼` 两个代码块显示未知视图而非空表。
2. 删掉 `edition.json`，该库立刻退回第一版行为，不报错、不损坏数据。
3. 三份 `edition.json` 的 `vaults` 两两一致，且每个值都是系统根下真实存在的目录。
4. `daily_note()` 的输出与 `periodNoteContent(PERIODS.daily, …)` 逐字节相同，含导航行里的全角空格 U+3000 与 ISO 周年。
5. 说一句灵感进《兼收并蓄》，说一句今天的事进《以人为本》并被问一次主题，当天第二句不再问。
6. 完成一个项目 → 出库单出现一行未勾 → 智能体搬运并提炼 → 账本记下 UID → `待提炼` 归零 → 出库单那行被勾上。
7. 从第一版升级：用户原库一个文件未动，`data.json` 的 SHA-256 前后相同，另外两本库建在它同级。
8. `python3 skill-pro/scripts/test_notectl.py` 全绿；`npm run build` 类型检查零错误。

### 31.6 出库单协议的解析边界

第二版额外收紧出库单协议：可见分隔符仍服务人读，但解析从 UID 与反引号路径等固定边界定位，不再对整行盲目 `split`。项目名或归档路径包含「 · 」时，名称、路径与 UID 仍能无损往返；旧格式不迁移，既有清单继续可读。

## 32. 《赛博永生》汉化与提炼的第二个入口（v0.19.0）

### 32.1 目录名为什么必须动

那本库的三层结构照抄了卡帕西原文的 `10-raw` / `20-wiki` / `90-system`。抄的时候看着像忠于出处，装到库里才看出问题：这本库里除了目录名之外**每一个词都是中文**——宪法、README、四种 `kind`、账本里的三种记录、「待提炼」那张表，全是。三个英文目录名不是异域风情，是一句中文里夹着的三个没翻完的词，而它们恰恰是用户在文件树里天天看见的那三行。

改法与判据：

| 旧 | 新 | 判据 |
| --- | --- | --- |
| `10-raw/` | `10-原料/` | 数字前缀**留着**。它保证「原料在上、知识在中、系统沉底」的顺序稳定，而这三层是有先后的；纯中文名按拼音或码位排，顺序随机 |
| `20-wiki/` | `20-知识/` | 同上 |
| `90-system/` | `90-系统/` | 同上 |
| `20-wiki/index.md` | `20-知识/索引.md` | 正文里本来就管它叫索引 |
| `90-system/log.md` | `90-系统/账本.md` | 正文里本来就管它叫账本 |
| 账本标记 `ingest` / `query` / `lint` | `消化` / `提问` / `体检` | README 教给用户的本来就是这三个中文词，只有账本自己还在说英文 |
| 页面 `type: wiki` | `type: 知识` | 值是给人读的 |
| `type` / `kind` / `updated` / `sources` 四个键名 | **不动** | 见下 |

**字段名是机器的，字段值是人的。** 键名翻译成中文会让两本库对同一个概念叫两个名字——Obsidian 的属性面板、搜索语法与《以人为本》认的都是 `type` / `updated` 这套键。这条线《以人为本》一直在守（`created` / `UID` 配中文值），赛博永生照抄，不发明第二套规矩。

同一条判据顺手补掉一处漏网的英文：「待提炼」表格的类型列此前直接显示原料 MOC 的 `type` 字段，于是在一张全中文的表里渲染出 `project` / `book`。改为与出库单共用 `KIND_LABELS`，两张清单讲同一件事时不会各叫各的。

**不与《以人为本》统一。** 那本库是 `00-inbox`…`90-system`，改不得也不该改：PARA 那六个是外面世界的既有约定，学员照着英文名查得到资料；这三层是本产品从一篇文章长出来的自有结构，没有外部约定要守。两本库因此在 `90-` 这一格上写法不同，这是**刻意的**，不是遗漏。

### 32.2 账本读两种标记，只写一种

`ETERNAL_LOG_INGEST_MARKS` 是数组而不是常量：写只写「消化」，读认「消化」与 `ingest` 两个。理由不是念旧——账本是**智能体逐行追加、用户也会手改**的文件，而某台机器上 `.ziminos/skills/` 里那份契约副本可能还是汉化之前的。少认一个标记不会报错，只会让那几份原料整体退回「待提炼」，接着被重复消化一遍、知识层跟着重一遍。代价高度不对称，因此宽松在安全侧，与该文件既有的解析姿态一致。

同理，升级契约里的迁移只 `mv` 目录、绝不批量替换账本里已有的行。改用户的账本等于重写他的记录。

### 32.3 提炼的第二个入口

原本只有一个入口：读出库单，把没勾的全部搬完提炼完。它是对的，但它把「我刚做完这一个，现在就想看见它变成知识」这个真实动作挡在门外——旧契约甚至明写着「不要去归档目录里自己翻」。

于是加一条路径驱动的入口：用户把项目 MOC 的路径粘过来（库内相对路径 / 绝对路径 / `obsidian://` 链接 / 双链，四种形态都得认），只提炼那一个。

**入口只决定名单，不决定做法。** 搬运与提炼的步骤在契约里仍然只写一遍，两个入口都跳进同一节。这是为什么它不是一个新 skill：另起一份契约等于把「怎么拷进原料层、怎么记账」写两遍，而两份迟早只改一份，且不报错。

路径入口比出库单入口多四道闸，因为出库单上的行是插件写的、天生可信，而用户手里的路径可能指向任何东西：

1. `type` 不是 `project` / `book` —— 不是容器，问他是不是指错了。
2. `status: active` —— 项目还没归档，退回，让他先按「完成项目」。
3. `status: paused` / `dropped` —— **必须问**。§31.3 那条判据在这里同样成立：暂停是「还没想好」，放弃是「明确不要了」，都不是结论。他坚持就照办。
4. 账本里已有这个 UID —— 说清上次消化的时间与触及的页，问是要重新消化还是搞错了。默默再消化一遍正是把知识网写重的路子。

另外，路径入口处理的项目可能**根本不在出库单上**（第一版时期归的档、手建的项目）。这时不许补写一行再勾掉：出库单回答的是「插件记下的移交欠账还剩几笔」，塞一条它没记过的等于伪造它的记账。账本里有 UID，「待提炼」自然归零，两张清单各自都还是真的。

### 32.4 验收

1. 《赛博永生》模板里不存在 `10-raw` / `20-wiki` / `90-system` 任何一个目录，`10-原料` 由安装契约 mkdir。
2. 账本里写英文 `ingest` 的旧行，「待提炼」仍认得出，那份原料不重新出现在清单上。
3. 「待提炼」表格的类型列显示「项目」/「书」，不显示 `project` / `book`。
4. 粘一条 `status: active` 项目的 MOC 路径，智能体退回并说明，不拷贝任何文件。
5. 粘一条已消化过的 MOC 路径，智能体报出上次消化时间并等确认，不擅自重写知识页。
6. C 模式升级把旧的三个英文目录 `mv` 成中文名，`10-原料/` 内容逐字节不变，账本里已有的行一行未改。
7. `skill-pro/SKILL.md` 的两条来路取的都是 Gitee 的第二版仓库 `ziminzhao/ziminos-pro`，clone 行里不出现 GitHub 的第一版地址——后者 clone 得下来却没有 `vault-pro/`，失败要等到交付物清单才发作。
8. `npm run check` 与 `python3 skill-pro/scripts/test_notectl.py` 全绿。


## 33. 从「能开关」到「能改」：片段的两个出境口（v0.20.0）

### 33.1 面板差的那一半

外观开关自 v0.9.x 起回答的是一个是非题：这十二个片段，哪些开着。它答得很好——清单现读磁盘、分组照用户的【】命名、开关即刻生效。但用户真正想干的事往往是下一句：**这条线的颜色我想改**。而从「看见这个片段」到「改到这个片段」之间，此前隔着一段没有任何入口的路——退出面板、找到笔记库文件夹、打开被系统默认隐藏的 `.obsidian`、进 `snippets`、在十二个中文文件名里认出刚才那一个。

判据因此不是「加两个按钮方便一点」，是**这张面板此前只答了一半**：开关回答「要不要」，没有任何东西回答「怎么改」。两个出境口补的是后半句。

### 33.2 两个按钮，两种画法

| 位置 | 长相 | 动作 | 为什么这样 |
| --- | --- | --- | --- |
| 每行开关**左边** | 只有图标（`file-code`） | 用系统默认程序打开这一个 `.css` | 它一屏出现十二次。十二个「打开这个 CSS 文件」会把片段名从清单里挤走，而它在哪一行本身就说明了它开哪个文件 |
| 面板**页脚右下角** | 图标 + 「片段文件夹」 | 在文件管理器里打开 `.obsidian/snippets/` | 它每面板只出现一次，说清它去哪儿的成本只付一遍 |

页脚是 `position: sticky` 而不是普通块，这一条是必须而非讲究：浮层有 460px 的高度上限，十二个片段一定滚动，页脚若随内容走，「右下角那个按钮」就变成「滚到底才看得见的按钮」。

行内按钮排在开关**之前**，因为 `ToggleComponent` 是往行上追加的——谁先建谁在左边。位置本身是句话：先问怎么改，再问要不要。

### 33.3 第四次伸手，以及借的到底是哪一步

「把文件夹交给访达」「用默认程序打开这个 `.css`」在 `obsidian.d.ts`（1.13.1，8482 行）里没有任何入口：全文搜不到 `shell`、`openPath`、`showInFolder`，App 的十个公开成员也没有一个沾边。不碰，这两个按钮就不成为功能。

但**借来的只有最后一步**。绝对路径走的是公开的 `FileSystemAdapter.getBasePath()`（`obsidian.d.ts` 里标着 `@public` 的导出类），所以「文件在哪」全程由 Obsidian 回答；借的仅仅是「把它打开」。这一条决定了塌方时的后果有多大：Electron 哪天没了，坏掉的是两个按钮，不是路径、不是清单、不是开关。

三条纪律与 `books/sourceWeread` 那一处逐条对齐，见根 `CLAUDE.md` 备案第 10 条。

### 33.4 探不到时画不画

两个问题分开答，判据是它们本来就是两个问题：

- **画不画**：`Platform.isDesktopApp` 且库落在本机文件系统上（两个都是公开且稳定的事实）。手机上没有文件管理器可去，画一个点了只会道歉的按钮不如不画——与文件夹计数的角标同一条纪律。
- **点了会怎样**：Electron 探得到探不到，在**点下去的那一刻**才验——与 `modules/legacy` 同一条纪律，因为注册发生在插件加载最早的一段，而热重载与版本升级都可能让答案在之后改变。桌面上按钮照画，探不到时用户得到的是一句为什么，而不是一个凭空少掉的按钮。

### 33.5 两种成功与一次降级

`openSnippetFile` 返回布尔而不是抛异常，与 `setSnippetEnabled` 用「即刻生效 / 只落了盘」区分两种成功是同一套写法：

- `true` —— 默认程序接手了，闭嘴。程序自己跳到最前面，就是最好的反馈。
- `false` —— 这台机器没有登记 `.css` 的默认程序，已退一步在文件管理器里**选中**它。这不是失败，但必须说一声，否则用户会以为按钮没反应。

真正的失败（探不到 Electron、库不在本机）才抛，由呈现层翻成一句中文。

「打开片段文件夹」在目录不存在时先建出来：这个按钮最该有用的时刻恰恰是「库里还一个片段都没有、我想去放一个进去」，此时报一句「文件夹不存在」等于把人堵在门口。建目录走公开的 `DataAdapter.mkdir`，且只在用户点了按钮时发生——人主导那条红线要的是「写入由用户动作触发」，不是「永不写入」。

### 33.6 面板不因此关闭

想改 CSS 的人往往一次要开好几个片段对照着看，点一个关一次会逼他把面板重开三遍。外部程序抢走焦点之后，他点回 Obsidian 的任何地方都会让浮层自己消失，这已经够了。

## 34. 状态栏路径的两种去处（v0.21.0）

### 34.1 「完整路径」原来是句含糊话

状态栏那一块自 v0.17.0 起做两件事：显示当前笔记在哪个文件夹里，点一下复制。设置页的说明写着「点一下把完整路径复制走」——而它复制的一直是 `01-projects/开源之道/开源之道.md`。

这句话在库里成立，出了库就不成立。用户真正要拿这串字去的地方常常在 Obsidian 外面：终端里 `cd` 过去、拖进别的程序、交给一个智能体去读那个文件。此时他需要的是 `/你的用户目录/笔记库/01-projects/开源之道/开源之道.md`，而拿到的是一条从谁的家目录算起都不知道的相对路径。

判据不是「加个选项更灵活」，是**两种路径对应两种去处，而不是「短的」和「长的」**：

| 口径 | 说给谁听 | 典型动作 |
| --- | --- | --- |
| 库内路径 | Obsidian 自己 | 写双链、跟同一个库的人说「我那篇在哪儿」 |
| 本机绝对路径 | 库外面的世界 | 终端 `cd`、拖进别的程序、交给智能体去读 |

猜错的代价还不对称：猜短了，人粘进终端得到「文件不存在」；猜长了，人粘进笔记得到一条永远断的双链，而且**断链不报错，也没人当天发现**。两边都会错，所以它必须是一个设置，而不是一次由我们替他做的取舍。

### 34.2 显示不跟着走

**屏幕上那一块永远是库内路径，只有复制走的那一串随设置变。** 这不是省事，有两条各自独立的理由：

- 机器前缀（`/你的用户目录/笔记库`）对库里每一篇都一模一样——它提供的信息量为零，占掉的宽度却最大。而那一块在 `styles.css` 里写着 `max-width: 32ch` 并带省略号：把绝对路径塞进去，被省略号吃掉的恰恰是唯一有信息的那一头（笔记名）。
- 这一块回答的是「我在库里的哪儿」，复制往往是要把这篇交到库**外面**去。两个问题的答案本就不必是同一串字。

代价是「看的」与「拿的」不一致，因此必须当场说清而不是留给用户去发现：悬停提示写着「点一下复制：」加上**这一下真会复制的那一串**，复制完的 Notice 把复制走的原样报回来。两处都取同一个解算结果，所以不存在提示说一套、剪贴板里另一套。

### 34.3 默认必须是老行为

默认 `vault`（库内路径），也就是 v0.20.0 之前唯一的行为。老库的 `data.json` 里没有这个字段，于是每一位老用户升级后拿到的都是这里写的默认值——默认一旦改成本机绝对路径，他某天粘进笔记的双链会突然带上 `/你的用户目录`：链接从此是断的，本机路径还顺手写进了一篇可能要分享出去的笔记。回归里有一条专钉这个默认值。

### 34.4 拿不到本机路径时降级，而不是罢工

库不在本机文件系统上（手机端、某些同步实现）是一个**事实**，不是用户做错了什么。此时复制库内路径，并在 Notice 里说清换了什么、为什么。让「复制」这个动作什么都不做是最坏的一种——他只会以为按钮坏了，然后去找一个并不存在的毛病。

这与 §33.4「画不画」与「点了会怎样」分开答是同一条纪律的另一半：那里的问题是要不要画出来（手机上没有文件管理器可去，静默缺席），这里的问题是已经画着的东西点下去该怎么办（照做，换个口径，说一声）。

### 34.5 算路径的那几行搬进 core

`localPath` / `vaultBasePath` 从 `modules/appearance/reveal.ts` 搬进 `core/localPath.ts`，两个模块共用：外观的出境口把路径交给操作系统，状态栏把路径交给剪贴板。

三条判据：

- **DRY 不是洁癖**。两份代码今天字节相同，分叉发生在明天某一次修 Windows 分隔符时，那时同一个库会在两个按钮上给出两种路径，而且不报错。回归里有一条断言 `adapter.getBasePath()` 在整个 `src/` 里只出现一次。
- **它谁都不属于**。这件事既不谈片段也不谈笔记，只回答「Obsidian 眼里的相对路径在操作系统眼里叫什么」——正是 core 的收留标准。
- **它让 reveal.ts 的自述变成真的**。那个文件的 L3 写着「只会因为 Electron 变而变」，而算路径与 Electron 毫无关系；搬走之后，备案第 10 条那句「借来的只有打开这一步」从一句说明变成了物理事实。

两个函数返回可空而**不抛**：事实层只回答事实，怎么应对交给调用方——外观翻成一句中文抛出去让按钮说话，状态栏降级复制库内路径。事实层一旦替调用方决定了反应，两个调用方就只能共用同一种反应。

分隔符按 `Platform.isWin` 给，而不是一律正斜杠，也不靠「库根里有没有反斜杠」去猜（反斜杠在 macOS 上是合法的文件名字符）。理由是这条路径的去处是**人**：他要粘进终端、粘进资源管理器、发给同事，那时它得看起来像这台机器上的一条路径，而不是两半拼起来的。

**本节不新增红线缺口**：`FileSystemAdapter` 与 `getBasePath()` 在 `obsidian.d.ts` 里都标着 `@public`。

## 35. 手机接进来的那个窗口（v0.21.0 · 只改首页）

### 35.1 认路文件在手机上必然落空

安装契约第三节第 6 步在系统根铺下 `CLAUDE.md` 与 `AGENTS.md`，回答的是「新会话怎么知道这是什么地方」。它有一个没写出来的前提：**智能体打开的就是系统根**。

手机接进来的会话不满足这个前提。工作目录由客户端给，常常不在系统根上，有的客户端根本不让选。于是首页「换个窗口，怎么让 Agent 认路」把手机与「有些客户端不自动读」并列，是把一个必然当成了偶然；那句短口令（「先读它根目录的 CLAUDE.md」）本身没错，但它假设智能体已经站在那个文件夹里，而手机上它没有。

### 35.2 缺的不是说明书，是三件具体的东西

| 手机上真正缺的 | 首页那一节怎么答 |
| --- | --- |
| 路径从哪儿来——手机上没法浏览文件夹 | 在电脑上用 §34 那个复制口径取一次，发给自己，取一次一直能用 |
| 它到底连上没有——手机上看不见文件树 | 口令要求先跑一次 `notectl.py status`，把三本库的位置报回来 |
| 会不会被自作主张地改写 | 口令复述红线一，并禁止手写文件、禁止用编辑器直接改笔记 |

第二条是这段口令区别于「随便说一句让它去读 CLAUDE.md」的全部价值，与 §25 那两段升级口令同一条判据：**要它自证真的干了活**。桌面上用户看得见文件树，回执错了当场就发现；手机上他只看得见对话，而「好的，请说」与一次真实写入在屏幕上长得一模一样。

### 35.3 口令只做路由，不做第二份契约

「灵感还是剪藏还是日记」「链接怎么排」「人名连不连成双链」一个字都不进口令，它们只在 `.ziminos/skills/capture/SKILL.md` 里有一份。理由与 §25 末尾那句相同：**做法写第二份，迟早只改一份，而且不报错。**

口令因此只写四样东西：系统根路径、两份本地契约的位置、先跑 `status` 自证、红线一连同「禁止手写文件」。其中路径是硬编码的，这正是回归要钉的地方（见 35.5）。

它还多一句「我粘的可能是某一篇笔记的完整路径，真是那样的话你自己截」——截路径是机器的活儿，让用户在手机上用手指去掐掉最后三段，恰恰是这套系统一贯反对的那种「把机器该干的活儿留给人」。

### 35.4 它是第二版专属，而降级必须给得出去处

第一版没有 `notectl.py`。让智能体直接去改 `灵感集.md` 技术上做得到，但灵感集顶部那块查询、插入位置与单条格式都是逐字节定死的，交给模型每次都可能不一样，而写歪了不报错——那正是第二条红线要挡的事。

所以首页那一节明写「第一版没有这条路」，并且**同时给出替代**：第一版在手机上记灵感走 Obsidian 自己——手机装 Obsidian、同步那本库，命令面板里的「记录灵感」照常可用（那条命令没有任何桌面守卫，插件本来就跑在手机端）。只说「不行」会把用户推去自己想办法，而他最容易想到的办法，恰好就是让智能体手写笔记。

### 35.5 发布前验收

1. 手机那一节点名的两个路径 `.ziminos/skills/capture/SKILL.md` 与 `.ziminos/skills/scripts/notectl.py`，在 `skill-pro/SKILL.md` 里真的被铺下。
2. 口令要它跑的 `status` 是 `notectl.py` 真有的子命令。
3. 取路径那几步点名的「复制哪一种路径」「本机完整路径」「复制当前笔记路径」，是设置页与命令表里真有的名字。
4. 回归只在手机那一节的正文范围内断言，不整篇搜 README——同样两个路径在「换个窗口」那段里也出现，整篇搜等于没搜。
5. 本节不改一行代码：`main.js` 不变，插件版本号不动，`data.json` 不受影响。

## 36. Eagle 附件桥接（v0.22.0）

### 36.1 不是再写一个 Obsidian 插件

产品只有一个 Obsidian 入口：既有 ziminOS。新增的是 `modules/eagle`，不是第二个会争抢粘贴事件、另存一份设置、再让用户判断先开谁的社区插件。

但 Eagle 必须有一只手能调用自己的资源 API，所以交付形态是**一个产品、两个运行时**：

```text
Obsidian / ziminOS                    Eagle / 第一方伴侣
粘贴或拖入 File                      只监听 127.0.0.1
        │                                     │
        ├─ 临时取得本机路径 ──鉴权导入──────▶ eagle.item.addFromPath
        │                                     │
        ◀──────────── 稳定 itemId ────────────┤
        │
Markdown 只写 ziminos-eagle://v1/primary/{itemId}
        │
阅读/实时预览 ──按 ID 取内容；点击──按 ID 在 Eagle 打开
```

平台边界因此很清楚：Obsidian 模块随 ziminOS 加载，Eagle 伴侣是后台服务插件；macOS 与 Windows 共用同一份 `platform: all`、`arch: all` 包。移动端与 Linux 都不注册粘贴/拖放/渲染监听，只在设置动作被显式触发时说明平台限制。

### 36.2 Markdown 认身份，不认位置

笔记里不写 Eagle 文件路径、文件夹 ID、伴侣端口或资源库实体路径，只写：

```text
ziminos-eagle://v1/primary/{itemId}
```

`itemId` 是 Eagle 项目身份，文件夹与真实路径只是它此刻住在哪里。因此：

- 在**同一 Eagle 资源库**里移动附件、改文件夹、重新分类，`itemId` 不变，Obsidian 链接无需更新；
- 移动整个 Eagle 资源库目录时，Markdown 仍不变，但实体库路径安全校验会拒绝旧会话，重新配对一次；
- 切换到另一套 Eagle 资源库时不猜它是不是原来那套，必须重新配对；
- 真正在 Eagle 中删除项目后，链接如实失效，不制造一个脱离 Eagle 的隐藏副本来伪装仍然可用。

图片写成图片 Markdown，PDF、压缩包等写成普通链接。阅读视图与实时预览把图片内容临时水合成 blob URL；blob 只在内存与 DOM，卸载时统一撤销。点击图片或普通附件链接按 `itemId` 唤起 Eagle。

### 36.3 写入必须 fail closed

附件事件只有在桌面端、开关已开、事件尚未被其他插件接管且确实含 File 时才接管。`preventDefault()` 必须发生在第一个 `await` 之前——慢一步，Obsidian 已经把本地副本写进库，后面 Eagle 再成功也成了双份。

接管之后不再退回 Obsidian 本地附件：Eagle 离线、未配对、当前资源库不匹配、导入失败，都撤掉占位符并明确告诉用户「没有在 Obsidian 本地保留副本」。成功项与失败项逐个结算，多文件粘贴不会因一个坏文件抹掉已经导入的结果。

有原路径的拖入文件直接把路径交给伴侣；剪贴板截图等只有内存字节的 File 才物化到系统临时目录，Eagle 导入结束即清理。临时文件不是用户资产，也永不进入笔记库。

### 36.4 配对与本机安全边界

伴侣只绑定 `127.0.0.1`，不监听局域网地址，不发 CORS 许可；POST 只接受 `application/json`，让网页的跨站写请求必须先经过不会获准的 CORS 预检。配对窗口显示 6 位一次性码，有效期 5 分钟；一分钟内连续五次错误即限流。成功后签发 256 位随机令牌，除 `/v1/pair` 外所有端点都必须携带令牌。

两端各自在应用本机存储里保存凭据：Obsidian 端用官方 `SecretStorage`，Eagle 端用插件 localStorage。令牌不进 `data.json`、Markdown、URL、DOM 属性或日志；因此不会跟 Obsidian Sync、Git 或笔记分享离开设备。请求还同时验证逻辑库键与配对时的 Eagle 实体资源库路径，避免用户切了库却把附件误写进另一套资产。断开会同时撤销 Eagle 端客户与 Obsidian 端令牌；若伴侣当时离线，本机凭据仍立即清除，但界面必须明确提醒用户稍后到伴侣窗口手动移除旧授权，不能把单边清除说成双边完成。

Eagle 端只调用官方 `eagle.item.addFromPath/getById/open`、`eagle.folder.getAll/create/createSubfolder` 与 `eagle.library`、`eagle.shell`，不直接改 `metadata.json`，不把 Eagle 内部文件结构当 API。

### 36.5 设置与交付

入口住在「设置 → ziminOS → 编辑 → Eagle 附件」：启用开关、显示随包安装的 `.eagleplugin`、配对/检测/断开、本机端口、项目外附件的可选 Eagle 文件夹 ID 都在一段。它不另开第九张设置页，因为附件就是编辑时发生的事。

`npm run build` 同步 Obsidian/Eagle 两份 manifest，再用 `package-eagle.sh` 按固定白名单、权限与时间戳生成可复现的 `ziminOS-Eagle-Bridge.eagleplugin`；同一版源码在不同工作区重建必须得到同一 SHA-256。单库与三库安装/升级契约都把它当受管程序复制和校验，但**绝不静默安装或启动**。安装 Eagle 插件、看到配对码并授权连接必须由用户亲自完成。

v0.22.0 只改变此后经粘贴/拖放进入的附件，不批量迁移已有本地附件，也不删除旧文件。历史迁移若以后要做，必须是独立、可预览、逐项确认且有失败清单的一次性工具，不能偷偷夹在插件升级里。

### 36.6 编辑器跳转语义（v0.22.1）

阅读视图把 Markdown 外链渲染成真实锚点，普通单击即是打开；实时预览、源码模式与 YAML 属性区则是 CodeMirror 编辑器，普通单击首先必须能放置光标和修改值。因此统一交互为：

- 阅读视图：普通单击打开 Eagle；
- 实时预览、源码模式、YAML 属性值：macOS 用 `⌘ + 单击`，Windows 用 `Ctrl + 单击`；
- 右键菜单继续提供「在 Eagle 中打开」与「复制 Eagle 身份链接」。

实现不依赖 Eagle 路径，也不把旧 URI 换成新格式。`protocol.ts` 在当前行的源文本中严格识别 v1 URI，并把 `[label](uri)` 的可点击区间扩到 label；`editor.ts` 只通过 Obsidian 公开的 `registerEditorExtension` 注册 CodeMirror DOM 手势，由鼠标坐标反解当前行。YAML 属性控件不保证暴露锚点或源字符位置，所以只在最近的小型控件文本中恰好有一条 Eagle URI 时接管；有多条就不猜，避免打开错附件。

### 36.7 最小化恢复与退出唤起（v0.22.2）

`eagle.item.open(itemId)` 只保证在主列表展示项目，不保证已最小化的主窗口回到前台；Eagle 完全退出后，伴侣进程也不存在，回环 HTTP 更无法自己启动宿主。两种状态因此分层处理：

- 伴侣在线：先用 `eagle.item.open(itemId)` 定位，再用 Eagle 4.0 Build 18+ 的公开 `eagle.app.show()` 恢复主窗口；Build 12–17 回落为 Eagle 原生项目深链；
- 伴侣不在线：只在这次用户点击触发的回环连接失败后，Obsidian 端通过 Electron `shell.openExternal()` 把 `eagle://item/{itemId}` 交给操作系统，由已注册的 Eagle 唤起应用并消费深链。

原生深链是一次性设备动作，不写回 Markdown，不保存 Eagle 安装路径，不启动定时器。只有“根本连不上伴侣”才走这条线；若伴侣明确返回 401（凭据错）、409（资源库不匹配）或 500（运行错），必须原样报错，禁止用深链绕过安全校验。原生深链中的 itemId 仍经同一身份正则验形，不接受路径或查询串。

### 36.8 按 Obsidian 项目自动归档（v0.22.4）

附件归属在导入发生的那一刻确定，唯一事实源是宿主笔记的库内路径：笔记位于设置中的项目根或归档根时，根目录下第一层文件夹名就是项目名；更深的卡片子目录不改变归属。项目目录根部的散落笔记与两棵根以外的笔记不猜项目。projects 模块持有这条业务规则，main 只把 `项目名 | null` 注入 Eagle 模块，两个业务模块不互相 import。

伴侣收到项目名后必须先通过官方 Folder API 创建或复用严格的 `项目/项目名称` 两级目录，再把最终子目录 ID 作为 `eagle.item.addFromPath` 的 `folders` 参数。创建是导入事务的一部分：目录无法确定时附件不进入未归类区，而是沿既有 fail-closed 语义停止并报错。所有目录创建在伴侣内串行，避免两个并发项目同时发现根目录不存在、各建出一份“项目”；同一级出现多个同名目录时不任选其一，要求用户先消除歧义。

原有 `eagleFolderId` 不删除，但收窄为**项目外附件**的兜底目的地：项目笔记永远按上述规则进入 `项目/项目名`，其他笔记才读取固定 ID，空值仍进未归类区。Markdown 身份协议不变，仍只写 libraryKey + itemId；Eagle 文件夹路径只出现在成功提示，不进入笔记，所以用户日后在 Eagle 手工移动附件仍不需要更新链接。本版不回扫、不搬运历史附件，也不监听项目改名；它只保证此后从某篇项目笔记新导入的附件准确落位。

项目导入使用独立的 `/v1/projects/import` 端点，不复用旧版 `/v1/import`：这是版本兼容的失败保险，不是为了多一条路。若 Obsidian 已升级而 Eagle 伴侣仍旧，旧伴侣会在真正写附件之前返回 404，新客户端把它翻译成“伴侣版本过旧”；若继续沿用旧端点，旧伴侣会无声忽略陌生的 `projectName`、先把附件写进未归类区再返回成功，用户只更新一半就会制造最难发现的错位资产。项目外附件仍走旧端点，因此旧 Obsidian + 新伴侣维持原行为。

## 37. 分栏中的后台写入不再回顶（v0.22.3）

### 37.1 根因不在滚轮，在“打开”的定义

旧实现只用 `workspace.getActiveFile()` 判断一篇笔记是否正在使用。单栏时这个判定成立；左右分栏各打开 A/B 时则不成立——用户点到 B 之后，A 只是不活动，并没有离开屏幕。

自动排版随后用 `Vault.process` 重写 A，`updated` 维护用 `FileManager.processFrontMatter` 再写一次。这两个 API 保证的是文件内容不被并发覆盖，不是编辑器视口不变；Obsidian 把磁盘更改回推给那个仍在场的 MarkdownView 时，可能重建内部视图并把滚动条放到 0。

同时，光标记忆只监听 `file-open`。从 A 点到已打开的 B 只会发生 `active-leaf-change`，A 的位置没有被记下。因此这不是一个问题，而是两条边界同时漏了“已打开的另一分栏”。

### 37.2 一层保当下，一层保下次

`core/markdownViewState.ts` 用公开 API 扫描所有已加载 leaf，只对 `instanceof MarkdownView` 且路径相同的视图记下 `currentMode.getScroll()`。排版与 `updated` 的原写入方式都不变；只在外层保护视口，写后立即恢复一次，下一帧再恢复一次抵消延后排版。写入期间若分栏已换文件或切换阅读/编辑模式，旧位置不再有权恢复。

`cursorMemory.ts` 则让 `file-open` 与 `active-leaf-change` 进入同一条 remember → adopt 流水线。前者管同一分栏换文件，后者管两个已打开分栏之间只换焦点。视口保护回答“A 此刻不要动”，光标记忆回答“下次回 A 去哪里”，两者不互相假装。

### 37.3 验收

1. 左右分栏各打开 A/B，A 滚到中部编辑，然后点 B：A 的排版与 `updated` 落盘，视口不回顶。

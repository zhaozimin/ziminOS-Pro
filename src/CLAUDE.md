# src/

> L2 | 父级: ../CLAUDE.md

插件源码根。这一层四个文件：main.ts 承担两件事——把「Obsidian 交给我们的运行时」翻译成「模块能用的上下文」并分发出去，以及把彼此需要、却不该互相认识的能力接上线；余下三个是插件唯一的图形界面，各答一问——settingsModel「有什么」、settings「骨架怎么画」、settingsPanels「每一页塞什么」。三家两次分出来，两次都由那条 ≤800 行先于人察觉。

## 成员清单

main.ts: 插件入口与唯一装配点。loadData 读回的未知 JSON 先经 core/types 的 normalizeSettings 逐字段验形 → 装配 ZiminosContext → 注册 init-vault 命令 → 分发十四个模块的注册函数 → 装配文件与旧版入口 → 装配左侧边栏 → 注册二十二个笔记内视图 → 挂载设置页。calendar 的 ItemView 在自己的注册函数中挂载，main 只注入「指定周期与锚点日期打开笔记」的能力。左侧边栏必须排在全部命令注册之后，因为它照着注册台的花名册摆图标。十个跨模块函数类型洞都由本文件接上，模块之间不反向 import。v0.17.0 起 explorer 那三样（计数、最近文件、状态栏路径）合成一个洞交给设置页，而不是三个——它们同属一个模块。全部事件与定时器经 registerEvent / register 托管，故 onunload 无需手写清理。
settings.ts: 设置页 ZiminosSettingTab 的**骨架**：标签栏怎么画、一页分哪四段、开关与文本框长什么样、折叠区怎么收。八张页各自的控件 v0.17.0 分给了 settingsPanels.ts（判据与 v0.14.0 分出 settingsModel 时同一条：变更理由不同；触发点又是那条 ≤800 行——它到了 895 行）。V3 起它按系统模块切成标签页（v0.17.0 起八张），切法不是新发明的分类，就是本目录 modules/ 下的目录本身；页标识与目录同名是纪律而非巧合——设置页的分页若与代码的模块边界对不上，「客户的设置在哪」的答案就会取决于当初谁把它排在了哪一段。三个模块刻意没有自己的页，判据是同一条「一个控件撑一整页是把分页做成摆设」；explorer 反过来照同一条判据拿到了自己的一页「文件」（v0.16.0：开不开、数什么、含不含子文件夹三项彼此独立，缺一个就说不完整）。appearance 只有一个开关、about 只有一张名片（v0.9.2 拍板，且它们本就是开荒交付物的一部分与落款）——开关排在开荒页初始化之后，名片是开荒页尾唯一排在高级折叠之后的东西（它不是设置，是署名，落款排在正文与附录之后正是它在纸上的位置）；books 的三项（标签前缀、标签条数、微信读书的连接）住在**项目**页里，v0.12.0 时的理由是「一个可配置项都没有」，v0.14.0 有了配置项之后理由换成更硬的一条——**一本书就是一个项目**，书落在项目目录、走项目的四态流转归档，给它单开一页等于在界面上否认代码里那条已经成立的事实。format v0.17.0 并进 editing 页（用户明令）：判据是它们**发生在同一个时刻**——粘贴、光标、走开之后的整理都在你敲字的那会儿，排版单列会逼学员先分清「整理格式算不算编辑」；模块本身仍独立，只是设置不再单列成页。clients 同版并进人脉页：它单列成页的旧理由（客户与人脉是两个物种）对**命令**仍成立、对**设置**不成立——两页加起来只有四个字段，其中两个还是同一种东西（人脉目录 / 客户目录）；分页的意义是「一页看完就不必再往下翻」，而不是「每个物种都得有张页」，页内按「人脉」「客户」切段即可。八张页的身份收在 TABS 一张表里，同时喂标签栏与每页页头，因此两处不会各说各话；标签图标取自 COMMAND_ICONS（与左侧边栏同一套 Pikaicons 笔画），标签栏是「整行底线 + 当前页填充胶囊」、标签自然宽度左对齐一行排下，v0.9.1 起弃 emoji；开荒页不再重列一份模块清单——八张标签一直摆在屏幕最上方、点一下即到，在首页把同样八行重列一遍是把索引误当成了介绍，那句交付状态改由各页页头承担。每页自己的控件挂在 `Record<TabId, PanelRenderer>` 上，加一页却忘了写渲染是编译错而不是一张空白页。十一个进表的文本字段收在 TEXT_FIELDS 一张表里，每条自带 tab、advanced 与可选的 section：tab 回答「这是谁的设置」（目录名归属它服务的模块），advanced 回答「该不该收进折叠区」，判据是「改了会不会让学员的库与课程讲义对不上」——所以客户渠道与产品清单不在折叠区里，那是学员自己的业务数据；section 是页内小标题，相邻两行段名一变就切一道标题（与边栏页按分组切标题同一套画法，段序因此不需要另一张表），只有人脉页用得上它。字段类型自 v0.14.0 起分成两层：TextField 是「画一个文本框需要知道的全部」，TextFieldSpec 才带去处——为的是让面板也能画文本框，读书笔记的标签前缀必须紧挨着它的条数下拉框，而骨架画的字段一律排在面板之前，交给骨架就会被拆到两段里去；分层之后没有闲置字段。一页的骨架固定为页头 → 明面字段 → 自有控件 → 高级折叠，四段的先后是一条跨八页的承诺；唯一排在折叠之后的是开荒页尾那张作者名片，它归骨架而不归面板——落款的位置是全页面的承诺，不是某一页自己的事。侧边栏那一页不认识任何一条具体命令：清单现读 ctx.commands 的花名册，分组标题按相邻两行的 group 变化切出来，因此加一条命令、改一个图标都不牵动这个文件。六件它干不了的事（执行开荒、开微信读书的扫码窗口、让状态栏按钮重新显隐、让边栏图标重新显隐、让文件那三样按新设置重画、画作者名片）经 SettingActions 一个对象注入（v0.17.0 起契约本体住在 settingsModel——骨架与面板两边都要认它，放在共同的下游才不成环），而不是六个位置参数——中间三个的类型都是 `() => void`，摆成位置参数时调换顺序照样能通过编译，出的错却没有任何编译期信号。页面只改全局设置对象并即时落盘；唯一自留的是「当前停在哪一页」，那是页面状态不是领域状态，随插件实例存活、不进 data.json。
settingsModel.ts: 设置页的**数据模型与契约**——注入契约 SettingActions、八张标签页的身份 TABS、全部界面文案 TEXTS、文本框表 TEXT_FIELDS、面板自持的 BOOK_TAG_PREFIX_FIELD，以及三个下拉框的显示名 FOLDER_COUNT_LABELS、RECENT_SORT_LABELS 与 FILE_PATH_SCOPE_LABELS，连同它们的类型。它零渲染代码、零 obsidian 依赖（图标名只是字符串，口径类型只是从 core/constants 借来的联合类型），因此「这个库到底有哪些设置」这个问题读一个文件就能答完。v0.14.0 从 settings.ts 分出来，判据是变更理由不同：加一个设置项、改一句文案、调一次字段顺序动的是这里的表，与渲染无关；改滚动行为、改标签栏样式、改折叠区画法动的是那边的类，与有哪些设置无关。分家的触发点是那条 ≤800 行的约束——它先于人察觉到一个文件在同时干两件事。
core/: 无业务语义的基础设施层，被所有功能模块单向依赖，自己不认识任何模块。V2 起它还含视图引擎的事实层与呈现层；v0.21.0 起还含「本机绝对路径怎么算」这唯一一处答案（localPath.ts），外观的出境口与状态栏的复制共用它。
modules/setup/: 开荒模块，只保证 PARA 骨架与「开荒过没有」这个事实，其余产物由各模块自报 VaultSeed。
modules/projects/: 项目管理模块，建项目、卡片登记与状态流转住在这里。它还供着「一个文件夹 + 一篇 MOC」这套容器流程，项目、领域与书籍三类容器共用它。
modules/books/: 读书笔记模块，一条命令从豆瓣查到书目、建出《书名》容器、把微信读书 / Kindle / 苹果图书三处的划线取回来合并进书的 MOC，再让学员把值得拓展的那几条摘成卡片。它是唯一存网络凭据的模块；日历联网但不登录、不存凭据。v0.14.0 沿「机器查得到的就不该问人」将书的 UID 收口为 ISBN，标签收口为豆瓣分类。
modules/inspiration/: 灵感收集模块，把参考 QuickAdd 脚本移植为 ziminOS 自带命令，生成由独立 Dataview 运行的未完成任务视图，并将文本生成与 Obsidian 写入分离。
modules/calendar/: 中国日历模块，以本地农历换算与 ISO 周为事实层，以 holiday-cn 镜像和内置当年快照为法定休息/调休补丁，以 Dust 式年/季/月独立导航的 ItemView 把日/周/月/季/年点击注入复盘模块的周期笔记入口。
modules/review/: 复盘模块，五级周期笔记、主题链与项目数据五视图。
modules/contacts/: 人脉与客户模块，两类档案、六条命令（人脉两条、客户四条）与十六个视图。
modules/format/: 排版模块，一条整理命令与一个编辑监听，替代学员原本要自己装的 Linter。它的两个设置 v0.17.0 起住在「编辑」页的后半截（同一个时刻发生的事，见 modules/editing 的 L2），模块边界不受影响。规则本体住在 core/markdownStyle，本模块只回答「什么时候对哪一篇跑它」；它绝不整理用户正开着的那一篇——中文输入法在合成中途被外部改写会吞字。断环靠 formatMarkdown 幂等而非守卫，因此插件自己插进去的那一行（里面有用户现敲的字）照样会被整理。同样不生产笔记。
modules/appearance/: 外观模块，右下角状态栏的 CSS 片段开关，v0.20.0 起还负责把片段交到用户的编辑器手上（每行一个「打开这个 .css」，页脚一个「片段文件夹」）。不生产笔记。它一个模块占两处红线缺口，且刻意分住两个文件：接触 Obsidian 非公开 API 的**第一处**在 snippets.ts（另一处见 modules/legacy），直接向 Electron 伸手的**第二处**在 reveal.ts（第一处见 modules/books 的扫码窗口）。分文件的判据是变更理由不同——前者随 Obsidian 的 CSS 子系统变，后者随 Electron 变。两处都声明成可选、运行时二次验形、探不到即降级。
modules/ribbon/: 左侧边栏模块，三十八个 Pikaicons 图形与「哪几条命令摆出来」（三十五个对应命令，dock / explorer / editing 服务设置页那三张标签页）。同样不生产笔记；与 appearance 不同的是它全程只用公开 API（addIcon / addRibbonIcon / Command.icon）。
modules/eternal/: 赛博永生模块，第二版（付费·三库）专属，全仓库唯一一个**默认不注册**的模块——main 只在版次标记判定为 pro 且本库角色对得上时才接它的线。它只记意图不搬文件：归档时往本库一篇可见的 Markdown 上追加一行「欠了这一笔」，真正的跨库拷贝与提炼交给桌面智能体。这条分工不是将就，是第三条红线的直接推论——Obsidian 的 vault API 被沙箱锁在本库内，借 Node fs 写隔壁库会是第三处缺口且手机上必炸；而提炼本来就只有智能体干得了，让它一次进门把搬运与提炼一起做完更顺。它的两张清单分住两本库，各自只讲自己库里的事实。
modules/editing/: 编辑模块，两件打字时的顺手事——粘贴到选中文字上就成外链、每篇笔记记住上次的光标位置。它同时是「编辑」页的主人，排版那两个设置作为后半截住在同一页。不生产笔记、不注册命令、不画界面，因此是唯一一个连同步函数都不用交回的模块（监听与记忆每次触发都现读设置）。光标位置存在插件目录自己的状态文件里，绝不混进 data.json。
modules/explorer/: 文件模块，同一个问题的三个面——我在哪个文件（状态栏路径，v0.21.0 起还能选复制库内路径还是本机绝对路径）、这个文件夹里有多少（目录树上的计数）、我刚才去过哪儿（侧栏最近文件）。合起来是「不会在自己的库里迷路」，因此同住一页、只交回一个同步函数。它是全库唯一认识文件浏览器 DOM 的地方，但走的是公开的 getLeavesOfType 与 View.containerEl，不碰社区插件常读的 view.fileItems。
modules/legacy/: 旧版入口模块，把 Obsidian 1.6 挪走的三个按钮（切换笔记库、帮助、设置）注册成三条命令并默认摆进左侧边栏。它是第二处、也是唯一另一处接触非公开成员的地方（v0.17.0 经用户明确授权，备案第 8 条）；上游那个插件没有许可证，因此连打包交付这个选项都不存在。
modules/about/: 作者名片模块，官网/教程双域名、海外 GitHub 与大陆 Gitee 双开源主页、四个自媒体频道连同 Simple Icons 品牌图形与头像照片编译进 main.js。同一个渲染函数挂两处：「关于作者」视图（v0.10.0 起住在 README，导航是工位不放署名）与设置页开荒页尾的落款。

## 依赖方向

单向且不可逆：`main.ts → modules/* → core/*`，界面那三家自成一条 `settings → settingsPanels → settingsModel → core`。main 认识所有模块，模块之间彼此不认识、也不认识 main——因此加一个模块只是在 main 里多几行，删一个模块只需删掉那几行。

有十一处跨模块需求真实存在：日记主题、记人情、客户开荒、书籍容器、微读连接与断开、外观重绘、边栏重绘、文件夹计数重绘、作者名片、日历点击打开指定锚点日期的周期笔记，以及第二版新增的归档移交（projects 交出刚归档的容器身份，eternal 接住写出库单）。它们不被写成模块间直接 import，而是各自声明函数类型作为洞，由 main 用另一个模块的能力填上。依赖图因此仍是一棵树而不是一张网。

第十一处那个洞还多担一件事：它是**版次隔离的落点**。免费版根本不递这个参数，于是流转命令里那条 if 恒为假，归档流程与第二版出现之前逐字节相同——「保留第一版」因此是代码结构，不是承诺。

三处重绘同步与其余七处形状相同，动机却不同，值得单独记一笔：其余七处是「模块 A 要用模块 B 的能力」，这三处是「已经画在屏幕上的 DOM 不会自己再问一次设置」——状态栏那个按钮、边栏那列图标、目录树上那串数字，谁画的谁负责收。

开荒同样走这条路：modules/setup 只认 VaultSeed 契约，各模块自报诉求，main 收齐后递进去。于是新增一个模块不需要修改开荒代码一行（OCP）。

ZiminosContext 是这条依赖链上唯一的传参形态。模块不接收 Plugin 实例细节、不各自读写 data.json、不自行 new Guard、也不直接调 plugin.addCommand；settings、guard 与 commands 都是全局唯一引用，设置页改完开关，正在监听的模块下次触发时立刻看见新值，中间没有任何同步环节。唯一需要同步环节的是已经渲染出来的东西——状态栏那个按钮、边栏那列图标与目录树上那串计数都不会自己再读一次设置，所以它们是 SettingActions 那六个洞里的三处重绘同步。

命令一律经 ctx.commands 注册，这条纪律是 V3 新加的，理由与 FIELDS 收口同源：命令面板、左侧边栏、设置页三处都要拿这条命令的身份，各自 addCommand 的话，图标与名字迟早在三处对不齐，而对不齐既不报错也没人发现。

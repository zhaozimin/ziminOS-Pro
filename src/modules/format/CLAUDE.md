# modules/format/

> L2 | 父级: ../../CLAUDE.md

排版模块。它和 appearance、ribbon 一样不生产笔记、不报 VaultSeed，在开荒流程里完全缺席；它管的是所有模块都管不着的那件事：**这一篇写得规不规范**。

它替代的是学员原本要自己装、自己配的 Linter 插件，但刻意只做那一件最基础的事——标准 Markdown 的写法，而不是一百条可配置的重排。判据是零基础学员：他不知道「表格上下要空一行」意味着什么，更不该为此去读一份英文配置文档；但他的库里每多一篇不合规的笔记，将来换任何一个工具打开都会错位一次。

## 成员清单

formatter.ts: 模块的全部——一条命令、一个编辑监听、一条落盘路径。规则本体不在这里，在 core/markdownStyle：那是一趟纯字符串变换，可以在 node 里逐条断言；本文件只回答「这次变化该不该排一次整理」与「到点之后怎么整理」。「什么时候整理才不伤人」v0.34.0 起交给 `core/editDebts`，与 updatedMaintainer 同一份实现——此前两边各写一份，v0.33.0 只修好了那一边的「关标签页也算走开」，这一边一直在拿「最近活动过」当「开着」（关掉标签页之后要等下一次开笔记才整理），两边也都不认改名。三条设计写在下面。

## 最后一道写入闸与分栏保护

欠账保证结算时这一篇不在眼前，但它不构成写入授权：读盘后与 `vault.process` 真正提交时都再以 `isNoteInFront` 问一次现场。读盘途中被用户点回眼前的笔记，这笔账原样留着等下一次走开；守卫与再入时间戳也只在内容确实变化的那一刻登记。

「不在眼前」不等于「没显示」：分栏中 A 仍在屏幕上，用户点到 B 后 A 只是失焦。它可能还捏着最后两秒没存盘的字，欠账因此在结算前先让显示着它的分栏存盘，缓冲区干净了，随后的重写才只是一次静默重载；若此时用 `vault.process` 重写 A，Obsidian 仍会刷新那个非活动视图，滚动条可能归零，所以所有写入还经 `core/markdownViewState` 包裹：写前捕获同一笔记在所有已加载分栏中的滚动位置，写后原样恢复。

## 什么时候动手，什么时候绝不动手

**它绝不整理你正在编辑的那一篇。** 这是本模块最要紧的一条纪律：中文输入法在合成中途被外部改写会吞字，就算不吞字，光标也会从他正在打的位置上移开——而「停手两秒」这个信号在斟酌一句话时太容易误判。已失焦但仍在另一分栏显示的笔记可以整理，但必须保住它的视口。

它曾被当作本模块与 updatedMaintainer **最大的不同**——那边只改 YAML 里一个字段的值，看着小得多，两秒防抖理应够用。v0.33.0 由真机改正：那边的症状与这边一模一样（合并弹窗 + 视口乱跳），因为**代价与写多少字节无关，只与「写盘的那一刻编辑器手里有没有未保存的改动」有关**，而 `modify` 事件来自 Obsidian 自己的保存、不是来自用户停手。两个常驻监听因此现在守同一条边界、用同一套「记下它脏了、等他走开再补」。剩下的两处不同仍然成立：看不看 SelfWriteGuard，以及改一个字段还是整篇重写。

于是自动整理只在三个时刻发生：用户从一篇改过的笔记切走或关掉它（`active-leaf-change` 与 `file-open` 都订，前者管换面板、后者管同一面板里换文件，漏一个就会留下永远等不到整理的笔记；中途改了名，账跟着新路径走）；一篇没开着的笔记被改动（比如插件刚往今天的日记里插了一行）；以及用户自己按下命令——那一条不受任何限制，因为此刻动手是他自己要的。欠账不存进本机：排版任何时候都能从内容重新算出来，退出时没整理完的那一篇，下次改它时照样会被整理——这是它与 updated 的时刻不同的地方，那个错过就没了。

## 断环靠幂等，不靠守卫

整理会写盘，写盘触发 `modify`，`modify` 又排下一次整理。断开这个环的是两件事，顺序不能颠倒：

其一，**先读一遍算算改不改得动，改不动就不写**。这不是省一次 IO，是命门——只要「没变化也照写」，这个环就永远转下去。真要写时仍走 `vault.process` 重算一遍，那个回调拿到的是最新内容，于是读与写之间用户敲下的字不会被这次整理吞掉。

其二，**formatMarkdown 幂等**：第二趟算出来的与第一趟一字不差，于是第二趟自然落进「不写」那一支。这条性质在 core/markdownStyle 的头部被声明为设计前提，不是碰巧成立的性质。

本模块因此**故意不看 SelfWriteGuard**，这是它与 updatedMaintainer 的另一处不同：那边看见「插件刚写过」就跳过，而插件替人插进去的那一行（记人情、增加付费、记收款、记灵感）恰恰最需要被整理——里面有用户现敲的字。v0.34.0 起那几类写入干脆不再登记守卫（它们是人的编辑，updated 应当照记，见 core/guard），对本模块没有影响，因为本模块本来就不看。写盘前仍然 `guard.mark`，那是给别人看的：整理是机器的反应，不该被 updatedMaintainer 记成用户的编辑。代码里还留了一把一秒的再入锁，它挡不住设计错误，只是不把「幂等」这条性质押在一句注释上。

## 与设置的接线

v0.17.0 起这两样不再有自己的页，它们是「编辑」页的后半截——用户明令「排版和编辑应该算作一起」，判据是同一个时刻：粘贴、光标、走开之后的整理都发生在你敲字的那会儿。并的是页，不是模块：本模块的边界、命令与监听一个字都没变，只是画那两个控件的地方从 `format` 那一页搬到了 `editing` 那一页的下半段。

两样东西存在设置里，分工清楚：`autoFormat` 回答「谁来按」，`formatRules` 回答「按下去做哪几件事」。它们刻意不合成一个开关——自动关掉之后命令仍按九条勾选执行，合并就没法表达「我自己按，但按下去要全套」。

`formatRules` 存的是启用中的规则 id 清单而不是九个布尔字段，与 `ribbonCommands` 同法同因：加一条规则不必动设置契约，而老库升级时那条新规则不在清单里、于是默认不开——「不替用户改他没选过的东西」。

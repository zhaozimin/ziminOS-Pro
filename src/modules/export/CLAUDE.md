# src/modules/export/

> L2 | 父级: ../../CLAUDE.md

把当前 Markdown 笔记导出为一整张 PNG 或单页 PDF，导出之前先让用户在真实的纸上把版式调到位。两种格式共用同一份离屏渲染结果：先按当前笔记可见正文宽度建立纸面，再等待 Markdown、ziminOS 代码块、图片与字体稳定，最后按真实 `scrollWidth / scrollHeight` 一次性栅格化；因此页眉、页脚、水印与正文不会在两个导出器里各实现一遍。

**本模块 v0.24.0 的全部设计压在一条判据上：内容与装饰是两种寿命。** 内容渲染昂贵且只该发生一次（解析 Markdown、内联远端图、等字体与版面稳定）；装饰廉价却要在每一次拖动滑块时重来。两者原先焊在 `renderArticle(ctx, file, options)` 一个函数里，于是「实时预览」只能靠整篇重渲染——那是卡顿的另一个名字。拆成 paper（内容）与 decorate（装饰）之后，预览每帧只重放装饰，内容一帧都不重算。

**第二条判据：预览不是导出的仿真，预览就是导出物本身。** 纸默认停在离屏舞台上，预览只是把那个舞台挪进弹窗并按比例缩放；被 dom-to-image 拍下来的，始终是用户刚刚看着的同一个元素。若另画一份「示意图」，两者迟早走岔，而那时预览就在骗人——它给出的信心恰恰是最后才会被戳破的那种。截图前照终值再施一次装饰，则是为了堵住最后一道缝：用户拖完滑块立刻点导出时，预览排队中的那一帧可能还没轮到；`applyDecorations` 幂等，重放一次的代价是零。

**第三条判据管的是品牌标志（v0.24.0）：一个 logo，三处各自决定放多大。** 页眉、页脚与水印都能放它，但路径只有一个字段——你只有一个标志，让人在三处各选一遍同一张图不是灵活，是重复劳动。三处各有一个尺寸，**0 就是这一处不放**，与「文字留空即关闭」同一条语法，不必为标志再学一套开关。三个尺寸默认全 0，于是老库升级之后导出的那张图与升级前逐像素相同——新功能的默认值应当是「不发生」，而不是替他做了个决定。也因此，「这一段关不关」的判据从「文字为空」改成了**「文字与标志都没有」**：只放一枚标志不写字，正是落款最常见的样子。

风格落盘而不是只活在本次会话（`settings.exportStyle`），因为它的用途是**品牌**——品牌的定义就是每次都一样。只在用户点下「导出」之后才存：拖动途中的每一个中间值都不算数据，取消就该什么都没发生。

## 成员清单

layout.ts: 无 DOM 的口径与几何层；模板占位符、文件名清洗、浏览器画布上限内的自适应倍率、PDF 单页 14,400pt 边界内的等比纸张，以及水印砖的尺寸、SVG 与落点。它刻意不量文字宽度——测宽要 canvas，canvas 一进来整层就不再可单测；宽度由装饰层量好递进来，于是「一行字斜过来占多大地方」仍是纯算术。
logo.ts: 标志层，回答一个很窄的问题——库里那条路径，变成能直接嵌进纸里的那串字节。它单独成文件的理由是**时序**：读盘是异步的，而装饰层必须全同步（预览每帧重放一次，那条链上一旦出现 await，帧与帧就会乱序）。于是解析被提前：路径变了才解一次，解出来的 ResolvedLogo 同步递给装饰层。它同时把图降采样到导出真正用得到的尺寸——一张 4000px 的原图编进 data URI 会让水印那一层的样式串膨胀到几 MB，而它最终只会被画成 80px 高；统一栅格化成 PNG 而不是「够小就原样透传」，是为了让标志只有一种字节形态，而那一种处处都画得出来。
paper.ts: 内容层，只回答「这篇笔记铺开来是什么样、有多大」。用官方 `MarkdownRenderer` 离屏重渲染全文（而不是截当前可见区），远端图片经 `requestUrl` 内联，等字体与连续三帧版面稳定后按 `scrollWidth` 回填真实宽度。交出的 ExportPaper 同时管着「借给预览」与「收回离屏」两个动作——祖先带 transform 的元素不该被拍，这条纪律因此不散落在调用方手里。
decorate.ts: 装饰层，把一套风格施加到一张已经渲好的纸上，先清后建因此**幂等**，并且**全同步**——标志的字节由 logo.ts 预先解析好递进来，本层一个 await 都没有（这条由回归读去掉注释后的源码钉住）。页眉页脚是一行 flex（图在左、字在右、整行按对齐落位），因此「靠左」说的是 justify-content；标志只钉高度、宽度随比例走，换一张更宽的标志时这一行的高度不跟着跳。水印平铺与单个共用同一张 SVG 底图，区别只在 `background-repeat` 与 `background-position`——两种排布若各写一套，改一处必然漏另一处。水印层的宽高按此刻真实的 `scrollWidth/scrollHeight` 写死而不是 `inset: 0`：纸的盒子高度与它的 scrollHeight 在内容溢出时并不相等，而截图取的正是后者。
modal.ts: 唯一人机交互面。选标志走 core/modals 的 ChoiceModal 而不是让人手打路径——库里的图片是一个封闭集合，这条纪律与那个文件里写着的「凡取值来自封闭集合一律走 ChoiceModal」同源：手打出来的路径能通过一切非空校验，然后安静地渲不出图。谁该变灰由 EXPORT_SLIDERS 的 requires 字段决定而不是在这里逐根判断，因为那个判断一旦写错，用户会被锁在「要开标志得先拖那根滑块、而那根滑块正关着」里出不来。左边是缩放着的真纸，右边是控件；每一次改动只重放装饰、经 rAF 合帧。控件全部挂在 refreshers 一张表上，于是「恢复默认」不必逐个想起谁需要被同步——想不起来的那一个正是会出错的那一个。位置用位置来问：对齐是一排三枚互斥按钮，单个水印的落点是一张九宫格，而不是把空间压成一列文字的下拉框。平铺时那张九宫格整行收起而不是变灰——留着一个永远无效的控件，用户会以为是它坏了。
exporter.ts: 编排与运行时边界，只讲流程：渲一张纸 → 交给预览 → 照终值再施一次风格 → 一次性截图 → 按格式交付。桌面优先借 Electron 保存对话框，探不到则与移动端一起回落到笔记库附件位置。

## 依赖方向

`exporter → {paper, decorate, modal} → layout → core/exportStyle`。paper 与 decorate 彼此不认识：一个只认内容，一个只认风格，两者唯一的交汇是那个被传来传去的 `article` 元素。modal 不认识 paper 怎么渲出来的（它只拿到一个已经渲好的 ExportPaper），因此它永远没有机会在预览里重新解释一遍 Markdown——那条边界由 tests/export.mjs 明文钉住。

持久化契约 `ExportStyle` 住在 `core/exportStyle` 而不是本目录，理由与 markdownStyle / device 完全相同：`normalizeSettings` 要验它的形，而 core 不能反向 import 一个功能模块，否则依赖图从一棵树变成一张网。那份契约里的 `EXPORT_SLIDERS` 同时是界面的滑块范围与持久化的验形区间——一份事实两处使用，因此「界面能拖到的值」与「重启后还认的值」不可能对不上。

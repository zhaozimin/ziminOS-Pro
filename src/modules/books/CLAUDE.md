# src/modules/books/

> L2 | 父级: ../../CLAUDE.md

读书笔记模块。它回答一个很具体的问题：学员在微信读书、Kindle、苹果图书里读书划线，那些句子怎么进到这个库里来，进来之后怎么变成他自己的知识。

**这个模块推翻过一次自己，两版都记在这里，因为推翻的理由比结论值钱。**

第一版（v0.12.0）走「官方纯文本导出 + 粘贴解析」：三家 App 的同步插件全走私有网络接口，与当时的「插件内零网络请求」红线冲突，于是让学员在 App 里导出、粘贴进来。它红线一条不破，却把学员的操作从三步压到了两步——**而那两步本来就该是零步**。用户的判决原话：「你让用户手动填写了太多没有必要的信息」。他说得对：书目字段（出版社、ISBN、页数、评分）机器查得到，划线在哪台设备上机器也查得到，把它们留给人不是克制，是失职。

第二版（v0.13.0，当前）：用户明令放宽第二条红线——允许联网、允许登录。于是**一条命令走完全程**：问书名 → 从豆瓣候选里指认哪一本 → 其余全自动（抓书目、建《书名》文件夹与 MOC、把本机与云端的划线取回来直接写进「全部划线」小节）。学员的操作次数从「三步 + 两个插件 + 一次手工汇总」变成**一次命令 + 一次点选**。

两版的产出并存：粘贴那条路留着当兜底（Windows 没有苹果图书、微读没登录、网络不通时它照样能用），但它不再是主路。

v0.14.0 沿着同一条判据再推了两格，没有第三版：**书的 UID 就是它的 ISBN**（书自带一个全世界通用的号，再发一个只有本库认得的时间戳，是给同一个东西造两个主键），**书的标签就是豆瓣的分类**（`#书籍/{分类}`）。两样都是「机器查得到的就不该问人」的直接推论，与第二版是同一句话。

v0.34.1 又把文件身份与展示身份拆开：`MOC-《书名》` 继续服务文件树定位，`aliases` 至少保存书本的真实名称。手动建书取用户输入去掉最外层书名号后的文本，豆瓣建书有副标题时取完整书名、无副标题时取主书名。导航因此只展示人的语言，而不牺牲 MOC 的内部命名规则。

## 成员清单

douban.ts: 书籍信息的来源。学员建一本书时只该做一件事——报出书名、指认哪一本，其余（作者、译者、出版社、出版年、ISBN、页数、评分、封面、豆瓣链接、分类词）一律自动填。让人手打这些字段是把书目数据库的活儿摊派给读者，而它们恰恰最容易打错又最难发现（ISBN 错一位仍然是合法的一串数字）。取数分两步走，因为豆瓣的两条通道待遇不同：**JSON 搜索接口（/j/search 与 rexxar）对非浏览器来源一律 403，而搜索页与详情页的 HTML 照常 200**，且搜索页把结果原样铺在 `window.__DATA__` 的明文 JSON 里——于是走 HTML 这条路（两处实测确认）。解析与取数分家：parse* 是纯函数，喂存档 HTML 就能离线验证。两处坑是端到端实测逼出来的：其一，搜索首条常是**丛书**（搜「人类简史」第一条就是「[丛书] 人类简史三部曲」），它的详情页没有 ISBN 与页数，建出来是个空壳，因此丛书/套装/系列一律从候选里剔除；其二，详情页仍可能失手（改版、限流），所以拿候选那行摘要（`作者 / 译者 / 出版社 / 年份 / 定价`）兜底补齐。分类词（v0.14.0）是第三处坑：详情页那个「豆瓣成员常用的标签」小节**已经不在页面上了**（四本实测样本无一有 `db-tags-section`），但同一份数据完整留在页首那行广告投放参数 `criteria = '7:写作|7:方法论|…|3:/subject/{id}/'` 里——豆瓣拿它去定向投广告，因此它必须与常用标签同源同序。取它而不取 DOM 是权衡后的选择：页面版式改版频繁，那行参数是发给广告系统的接口。它失效时的表现是「这本书没有标签」，不是报错也不是标错，所以没有兜底的必要。
isbn.ts: 书的身份证号，纯函数零依赖。全库每篇笔记都有 UID，别的笔记是 14 位时间戳（因为它们没有别的身份），书有——ISBN 在任何一台机器任何一个库里都是同一串数字，于是「这两篇是不是同一本书」变成一次数字比对，而不是比对书名（同名书、繁简、副标题写不写，全都会让书名比对失手）。两处约束定死了它的形状：其一，`UID` 在库级属性表里登记为 **number**，属性类型是全库共享的一张表，某一篇写成字符串就与其余笔记不同构，而这种不同构既不报错也没有任何视图会挡下——所以拿不出数字就交 null 让调用方回落时间戳；其二，ISBN 有两代，13 位纯数字与 10 位末位可能是 X，后者按国际标准换算成 978 开头的 13 位（无损转换，不是猜测），因此老书也拿得到它的真号。换算实测自证：小王子的 ISBN-10 `7020042490` 算出 `9787020042494`，与豆瓣自己列的 ISBN-13 逐字相同。
tags.ts: 豆瓣的分类词到 Obsidian 标签之间那道翻译，纯函数，只依赖 core/constants 的两个标签常量。分类不让学员填，理由与书目字段同源：他填的是此刻想到的词，豆瓣给的是几万人读完投出来的词——后者才是这本书在知识地图上的真实位置，也才可能与他书架上另外二十本对得上。本文件只解决最容易出错的那一段：**豆瓣的分类词不一定是合法标签**。标签里不能有空格、点号、括号，而「尤瓦尔·赫拉利」「2017 书单」比比皆是；非法字符不报错，Obsidian 只会在那个字符处把标签截断，`#书籍/尤瓦尔·赫拉利` 悄悄变成 `#书籍/尤瓦尔`——一个谁也不会去核对的半截词。因此走白名单（Unicode 字母含汉字、数字、下划线、连字符），其余一律换成连字符；前缀多认一个斜杠（写「阅读/书籍」是正当用法），做法是**按斜杠切段、每段各自归一、再拼回去**而不是把斜杠也放进白名单——后者省事，却会让「阅读 / 书籍」这种斜杠两边带空格的写法拼出 `阅读-/-书籍/写作`（空格变成的连字符紧贴斜杠，而掐头去尾只掐整串两头），更狠的是「书籍 /」把整个书架的根变成 `书籍-`，标签面板里 `书籍/` 一展开什么都没有。按段归一之后，「斜杠是分层符」这件事在代码里也成立，而不只写在注释里。bookTags 是**全函数**：前缀与条数都是学员敲进去的自由文本，空串、怪数、手改 data.json 写进来的东西一律在这里回落默认，与 core/folders 的 normalizeFolderPath 担同一职——条数的判据是「在不在 BOOK_TAG_COUNTS 里」而不是「大不大于零」，因为 `NaN <= 0` 是 false、`n >= NaN` 恒为 false，一个 NaN 会一路穿过守卫与截断变成「豆瓣给几条写几条」，而设置页此时仍显示着「前 5 个」。取前 N 条而不是全取：豆瓣按投票数排序，截断本身就是筛选，不需要再发明一条「多长算废话」的规则。
sourceAppleBooks.ts: 划线来源之一，也是三个里最确定的一个——数据就在本机两个 SQLite 里（`BKLibrary` 与 `AEAnnotation`），零网络零登录，「同输入同结果」原样成立。取数走 `spawn('sqlite3', [库, SQL, '-json'])`：macOS 自带 sqlite3（实测 3.51.0），因此不必打包任何 sqlite 库，也不必碰原生模块——Obsidian 插件带原生模块是个死结。它比复制粘贴多给两样东西：**章节名**（ZFUTUREPROOFING5）与**批注**（ZANNOTATIONNOTE），那两样在复制出来的文本里根本不存在。库文件名带版本后缀且随 macOS 变过，所以只认目录、扫里面的 .sqlite；同目录有多份历史库时按修改时间从新到旧逐个探 `sqlite_master`，书库只认 `ZBKLIBRARYASSET`、标注库只认 `ZAEANNOTATION`，不把目录返回的任意第一项误当现行主库。打开方式试两次且顺序不能反（2026-08-14 真机实测改出来的）：先 `mode=ro`（只读，但**认 -wal**），失败再退 `immutable=1`。苹果图书是 WAL 模式，而且把大量新数据长期留在 -wal 里迟迟不回写主库——实测那台机器上主库 0 本书 0 条标注、-wal 里 1 本书 4 条标注。此前写的 `immutable=1` 会让 sqlite **完全忽略 -wal**，于是插件读到一份陈旧快照，如实汇报「这台机器上没有苹果图书的划线」——一句听上去像事实的假话，而学员手里正开着那本划得满满的书。「不去碰别人正开着的库」这个初衷没错，只是选错了参数：`mode=ro` 同样一个字节都不写。退回那一支也不是摆设：只读连接读 WAL 需要 -shm，库彻底 checkpoint 过、-shm 不在时 `mode=ro` 开不了，而那时陈旧快照与真相恰好是同一份。
sourceKindle.ts: 划线来源之一。它只做一件 parsers 不做的事：**把 My Clippings.txt 找出来**——学员的认知里没有「那个文件在哪」这一条，让他去找等于把一步变成三步；而它的位置是确定的（插上的 Kindle 是一个卷宗，`documents/My Clippings.txt` 是固定路径），扫一遍挂载点即可。解析仍交给 parsers，同一份格式规则不该有第二份实现。
sourceWeread.ts: 划线来源之一，三个里唯一需要登录、也因此唯一会失效的一个。登录只做一次且不碰账号密码——开一个真正的浏览器窗口让学员用微信扫码，成功后从那个窗口的会话里取走 Cookie（`@electron/remote` 的 BrowserWindow，实测存在于 Obsidian 桌面版 app.asar；备案见 L1 deviations 第 5 条）。判据是「Cookie 里有没有 wr_skey」而不是「跳到了哪个地址」——落地页改过不止一次，而 Cookie 是这件事本身。取数走**两套通道**，这是 2026-08-14 真机实测定下来的：书架仍走 Cookie（`/api/user/notebook`），划线与想法走**取数网关**（`i.weread.qq.com/api/agent/gateway`，POST，认 `Bearer` 令牌而不认 Cookie，令牌用登录态在 `/api/skills/apikeyGet` 换得到，因此对学员仍是零操作——扫一次码，别的不必管）。非如此不可：老的 `weread.qq.com/web/*` 两条路都已作废——`/web/review/list` 回 200 + `{"errCode":-2012,"errMsg":"登录超时"}`；`/web/book/bookmarklist` 更彻底，无论带不带 Cookie、书号真假一律回 200 + `{}`，连错误码都不给。这条路是照 obsidian-weread-plugin 找到的：它的 `api.ts`（V1）与我们原来撞的是同一堵墙，`api-v2.ts` 才是活路。实测同一本书：老路 0 条，网关 3 条划线 + 1 条想法。令牌刻意不落盘，它随时能拿登录态再换，存下来只会多一份会过期、要维护、断开时要记得一并清掉的凭据——全插件的持久凭据仍只有 Cookie 一份，「断开」因此仍然只需清那一个字段。换不到令牌时降级为「只取带想法的那些」，并**必须留下一句交代**：静默地少交一半，与「这本书没划过线」在学员眼里长得一模一样，而前者是我们的问题。顺带记一笔：书架条目上那个 `bookmarkCount` 不可信（实测报 0，实有 3 条），拿它对账的想法试过并已放弃。由此定下本文件最要紧的一条纪律：**判成败不能只看 HTTP 状态码**。微读失败时照样回 200 并把错误写在正文里，只看状态码就会把一次失败当成「这本书一条划线都没有」讲给学员听——而那正是那条红线的反面。空壳接口更阴，它连错误码都不给，于是拿书架顺手给的 `bookmarkCount` 对账：取回来的比它少就说明是我们失手，把话说明白，而不是让学员以为自己记错了划过什么；哪天接口活过来，这句对账自己就不说话了，不必有人记得回来删。章节名有两个来源——划线接口自带的章节表，与想法条目自带的 `chapterName`；后者不是冗余，一本书可能一条纯划线都没有（只有「划一段再写句话」的想法），那时章节表是空的。
sources.ts: 三个来源的汇流处。它存在的理由就是「一步」这个目标：学员不该被问「你这本书的划线在哪个 App 里」——那是他刚做完的事，机器自己能查。三条纪律：探测不抛异常（某个来源坏了只是这次没贡献，不该拖垮建书）、书名匹配从严到宽（逐字 → 去标点空白 → 互相包含且不短于四字且作者对得上，宁可漏一本让他手动指，也不能把《人类简史》的划线倒进《未来简史》）、来源之间不去重（那是 mergeHighlights 的活儿）。匹配这一关收的是**一批名字**而不是一个书名，同样是真机逼出来的：《思维 : 关于决策、问题解决与预测的新科学》主书名只有「思维」两个字（文件名只能用主书名），微读那头写的却是带副标题的全名，于是三轮全落空——第三轮恰恰被那道四字门槛挡住。出路不是把门槛降到两个字（那会让《活着》匹配上一堆书），而是把这本书已知的每个名字都拿来试：主书名、带副标题的全名（正是写进 aliases 的那个）；全名一到手第二轮就直接命中，门槛一寸不动。「读一本书」与「同步这本书的划线」必须递同一批名字，后者从 frontmatter 的 aliases 里取，否则同一本书在两条命令下会得到不同的匹配结果。`SourceHit` 因此多了一个 `note`：「一条都没取到」至少有三种成因（没有匹配到这本书 / 书上确实没划过 / 接口取不到），三者在数据上一模一样，只有来源自己分得出；每个可用来源即使没匹配到也必须返回一条 note，不能把漏匹配伪装成「这本书没有划线」。
readBook.ts: 主干命令「读一本书」，也是整个模块存在的理由。它只问书名与候选，其余自动完成；UID 用经校验的 ISBN，tags 用豆瓣分类词。「同步这本书的划线」共用同一取数与合并内核，只在合并真正改变正文时写盘，幂等同步不制造虚假修改事件；写进去的是用户自己的划线，不标记自写，书的 updated 照记。三条异步命令共用同一异常边界，把未预料失败收束为中文 Notice；无限时长的取数提示由 finally 关闭，失败也不把「正在取回」永远留在屏幕上。
parsers.ts: 粘贴兜底那条路的读入口，也是全模块唯一认识外部**文本**的地方。纯函数、零 import——同一段文本必须永远解析出同一批划线，这是「脚本驱动」在本模块的具体兑现。识别顺序按标记的无歧义程度排：先 Kindle（`==========` 分隔行在三种格式里独一无二），再苹果图书（「摘录来自」出处块），最后微信读书；三种都认不出返回 null，由调用方讲清支持哪三种，绝不猜。**「认出格式但一条划线都没有」不是 null**——一份只含书签的 My Clippings 认得出是 Kindle，只是没有可导入的东西；混为一谈的话学员会得到一句「认不出这段文本的来源」，然后去怀疑自己复制错了。微信读书是唯一的例外：它没有独一无二的分隔标记，只能靠解析出东西来反证，一条都没有时不能硬认。三家的格式规则都是照真实导出样本与生产级开源解析器逐条核实的，不是凭印象写的正则，其中三处坑值得记住：其一，微信读书有两代版式，现行版式的**章节行没有任何标记**，全靠空行数区分：跨段划线的续段只隔一个空行、想法正文的段间隔一个空行、想法里「原文：」的续段一行不隔，而章节前面隔着两个以上空行。把无标记行一律当章节，或者反过来把它一律当续段，都是这个格式最常见的错法——后者会让紧跟在想法条目后面的章节名被吞进原文里，还连带把那一章的划线全部记到上一章名下；其二，微信读书「发表想法」条目里的「原文：」往往还会以一条独立划线重复出现，所以解析完在书内先按归一文本去重一次，想法**并**回被评论的那条（并而不是「谁先谁算数」——同一句话隔半年重读会有第二个想法条目共用同一段原文，丢掉后来那条，学员第二次读的收获在解析阶段就没了）；其三，Kindle 的笔记与标注是两个平级条目，靠位置区间才能认出「这条批注批的是哪句话」，拆开呈现等于把批注和它批的话分了家——而个人文档与 PDF 的条目**只有页码没有 location**，取不到就退成 `[0,0]` 的话全书区间相等，每条笔记都「覆盖」第一条划线、一律挂错人，所以坐标取不到时是 null，宁可让那条笔记独立成行也不按顺序猜主人。
highlightIdentity.ts: 划线身份层，只回答「哪些输入是同一条」。身份键只压平空白与成对闭合的 Markdown 强调/高亮/删除线/行内代码包裹，正文中的 `=`、`_`、`~`、反引号等语义字符必须保留，避免 `x=1` 与 `x1` 这类不同原文静默撞键。它还收口同批有序归并；后来来源携带的想法与章节只补缺失信息，不覆盖先到原文。
identity.ts: 「哪篇笔记算一本书」只答一遍，导入与摘卡两条命令共用同一个答案，与 contacts/identity 担同一职。身份靠 `type: book` 认、不靠文件夹——与全库视图同一条纪律。与人脉不同的是**归档目录里的书不排除**：给读完的书补录几条划线是正当动作，不是错误；人脉那边的归档意味着「不再经营这段关系」，书这边的归档只意味着「读完了」。
templates.ts: 本模块写下的字长什么样，只有两样：划线的行形态与摘出来的卡片。行形态 v0.14.0 由缩进列表改成**标注块**——`> [!quote]` 装划线，`> [!note]` 嵌一层装想法，每块之后留一个空行当分界。换的理由是学员看着自己的笔记说的：「并不能清晰地显示划线和我写的内容」。原先两者都是 bullet，只差一层缩进与一个表情，三五条排下来书的声音和人的声音糊成同一串灰字——而这两种字的价值完全不同：划线是书的，想法才是他的。取 quote/note 两个内建类型而不自造名字，是因为 Obsidian 与 Minimal 都为它们备了配色与图标，自造的在没装对应片段的库里会退化成灰框，而这套系统承诺换主题不必改笔记。想法嵌在划线块里而不平列，是因为想法**是对着某一句写的**，平列会让它变成一条与上下文无关的独白。书的 MOC 骨架**不在这里**——那份文本属于容器流程，由 projects/templates 按 BOOK_KIND 生成；本模块不重复实现一份 MOC。卡片十字段严格按 CARD_FIELDS 生成，于是「摘出来的卡」与「手建的卡」在属性面板里长得一模一样。
createBook.ts: 建书命令 `create-book`。它只管书特有的三问——书名（必答，文件名自动包上《》，去书名号后的真实名称作为非空 aliases）、作者、为什么想读——后两问 Esc 或留空都直接放行，与开荒问名字同一姿态：宁可跳过也不打断。防覆盖、光标落点与全部错误文案由容器流程统一给出，这里一句都不重写。
importHighlights.ts: 导入命令 `import-book-highlights`，负责选书、解析、确认与原子写入。确认框是唯一授权点；预览只负责授权，成功提示只认 `vault.process` 内最新内容的真实账目。mergeHighlights 先经 highlightIdentity 把同批重复键的想法合并，再只增写入；全程保留原 LF / CRLF / CR。
extractCard.ts: 炼卡命令 `excerpt-book-card`，读书笔记从素材走向知识的那一步。只在书的 MOC 上可用，选中一段划线就在书的文件夹里长出一张卡片，划线原文以引用块打底、光标停在它下面——数据在上、发挥在下。`up` 双链按 cardInit 的同一公式拼（全路径 + 书名作显示名），因此 MOC 底部的「读书卡片」表与反链视图对它零改动全认。

## 书名契约

`createBook.ts` 的手动入口与 `readBook.ts` 的豆瓣入口都必须交出非空 aliases：前者去掉用户可能已输入的一层《》，后者优先取「主书名：副标题」、没有副标题就取主书名。`BookContainerPreset` 把 aliases 收紧为非空元组，是为了让新的建书入口若遗漏真实书名，在编译期就失败，而不是等到导航上出现 `MOC-`。

## 审计后不变式

本机来源的 Node 能力只在 `Platform.isDesktopApp` 通过后按需取得，移动端不解析 Node 内建模块。每个来源独立失败，任何「只成功一半」的结果都必须带 note，不得伪装成「书上没有」或完整同步。同批次的划线身份在写入前归并，想法做有序并集；同步提示使用 `vault.process` 内的真实合并账目。ISBN-10/13 进入 UID 前验证校验位。

## 一本书就是一个项目

书没有自己的目录设置，也没有第二台状态机：它住 `01-projects`，读完走既有的「完成项目」搬进归档。这不是省事，是**书本来就符合项目的定义**——它有终点。领域没有终点（健康、手艺、人脉），项目与书都有，于是三者共用 `createContainer` 那一套「文件夹 + MOC」，差别全部收在 `ContainerKind` 那张表里（落在哪个根目录、写什么 type、问不问归属、带不带小节骨架）。`transitions` 的类型判据因此从 `project` 放宽成 `MOVABLE_TYPES`，其余守卫、确认框与回滚一字未动。

代价说清楚：项目目录里会混着书。这被认为是对的——「这本书」和「写那门课」在学员的一周里本来就是并排推进的两件事，把书赶进 `03-resources` 反而要求他每天在两个地方找活干。导航页那张按 `type == "book"` 筛的「书籍」表负责把它们单独理出来，那张表在 V1 就写好了，本次只是终于有东西可收。

## 依赖方向

本模块**不 import projects**。建书要走容器流程，于是声明了一个 `BookContainerCreator` 的洞，由 main 用 `createContainer` 与 `BOOK_KIND` 填上——与 `PersonPicker`、`DailyNoteProvider`、`SeedApplier` 同一手法，依赖图仍是一棵树。

不报 VaultSeed：开荒不该预置一本谁也没读的书，也不该多一个空目录。三条命令都不进默认边栏（判据「一天里可能按不止一次」不满足），在设置 → 边栏勾一下就上。

设置页也没有本模块的标签页，但理由自 v0.14.0 起换了一条。此前是「一个可配置项都没有」；现在有三项（标签前缀、标签条数、微信读书的连接），它们住在**项目**那一页——不是因为它们少，是因为**一本书就是一个项目**：书落在项目目录、走项目的四态流转归档，给它单开一页等于在界面上否认代码里那条已经成立的事实。仍然没有出现的是书目字段的开关（作者、出版社、ISBN、评分怎么写）：豆瓣怎么给就怎么落，让人去配等于让人去改事实。微信读书那一项在设置页而不只在命令面板，是「人主导」的兑现——它是全插件唯一一份存在 data.json 里的凭据，必须有一处能看见它在不在、并且能当场撤掉；命令面板那条「连接微信读书」只能连不能断，一条只往一个方向走的命令不构成开关。断开只清本机那串 Cookie，不去动微信读书那边的任何东西。设置页不 import 本模块，扫码那一步经 `SettingActions.connectWeread` 由 main 填洞。

## 三条对学员的承诺

这三条都是评审逼出来的，共同点是**错法都不报错**，只让学员默默吃亏：

**每一次取消都出声。** 三个取消点（选哪本书、粘贴、粘贴里选哪本书）说同一句话，并告诉他剪贴板还在。学员可能刚粘完几百 KB 的 My Clippings，屏幕上什么都不发生的话，他分不出「取消了」和「插件卡死了」。这是仓库的既有惯例——建项目连「没输名字」都要说一句。

**Esc 在同一个模块里只能有一个意思。** 建书的三问里 Esc 是「跳过这一项」，那么摘卡的概述那一问也必须是跳过；若在那里让 Esc 变成「整张卡片作废」，学员会照着几十秒前刚学会的手势把自己的卡片按没，还得回去重新选中划线、重新起名。取消点是「卡片叫什么」那一问，不是概述那一问——必答项才配当取消点。

**写入前的最后一道闸要拦住站错书。** 确认框比对「识别出的书」与「要写入的书」，对不上就亮一条橙色警告。写入只增不删，一整本书的划线落错地方就只能手工删——而站错书恰恰是最容易发生的：Obsidian 会替你恢复上次打开的那篇 MOC。

## 与排版模块的先后

导入**必须先打开那本书、再写盘**，顺序反过来会踩排版模块的纪律：它对「没开着的笔记」排一次两秒后的整篇重写，而两秒后这篇已经在学员眼前了，于是「绝不整理你正开着的那一篇」形同虚设，整篇重排会把他正敲的中文吞掉。先打开，那次 modify 就落在「正开着的那一篇」这一支上，排版会一直等到他走开。

这是全仓库第一处「改一篇没开着的笔记、随即把它打开」的流程，所以这条先后关系此前没有人需要考虑。

## 合并的三条法

导入必须可以反复执行，因为学员会读一半导一次、读完再导一次。三条法保证它安全：

**读得懂两代形态，只写新的。** v0.14.0 换行形态时没有迁移存量笔记——「只增不删不改」这条承诺对已经写下的笔记同样成立。于是 mergeHighlights 的盘点段两种都认（标注块与缩进列表），`ExistingHighlight.legacy` 记着每条是哪一代；补挂想法必须按**那条划线自己的形态**落笔，往旧笔记的列表行下面塞一块标注会得到一条既不属于列表也不属于引用的孤儿行。新划线一律走标注块，因此一本旧书会长成新旧混排——那是诚实的样子，不是缺陷。

**去重键是「去掉全部空白与强调符」的划线文本，章节名同样归一。** 不这么归一的话，排版整理往汉英之间补一个空格、或者学员顺手把一条划线加粗，同一句话下次导入就成了「新的」——而重复的划线不报错，只是让那本书的划线越来越长。**章节名漏了这层归一是最先犯的错**：排版整理照样会把「### 第1章 A的意义」改写成「### 第 1 章 A 的意义」，于是划线认得出、章节认不出，每导入一次就在小节末尾新开一个同名章节块，同一章在页面上被切成好几段，且没有上限。查表用归一键、写标题用原文，两件事分开。

**只增不删不改。** 学员在小节里的手改（加粗、批注、删行）一概不碰。删过的行会在下次导入时回来——这是「只增」的正直代价，好过为了记住删除而引入一份影子状态：那份状态一旦与笔记本身分叉，谁也说不清哪份算数。

**想法不许静默丢，也不许挂错主人。** 一条划线可以有好几条想法（隔半年重读、写下第二条体会是真事），所以 `ParsedHighlight.thoughts` 是数组；「这条想法是不是新的」只问**这条划线自己**有没有过，拿整个小节的想法当判据的话，「重要」「同意」这类短评一旦在别处出现过，学员这次写的就被静默丢掉。落刀时同一行号上想法排在新划线之前——两者会算出同一个数（既有划线是本段最后一行时，它后面那个位置既是本段的追加位、也是它自己的想法位），不分先后的话那条缩进的想法会挂到刚插进去的新划线名下。想法是学员亲手打的字，是整份导出里最贵的部分；划线是书的，想法才是他的。

写入位置的规矩与 core/markdown 的 `insertIntoSection` 同源：新划线插进它所属章节块的末尾，章节不存在就新开一块，小节里若出现围栏（学员挪过 base 块）插入点一律停在围栏之前，`## 全部划线` 标题被删就在文末重建——位置不理想好过拒绝写入。全部插入点按原始行号登记、从后往前落刀，因此既有的行一个都不动。

**没有章节的划线落在第一个 `###` 之前那一段的末尾**，一个章节都没有时才是小节末尾。这条是真机样本测试逼出来的，第一版写的正是「一律追加到小节末尾」：Kindle 与苹果图书都不给章节，而同一本书很可能先从微信读书导过一次（带章节），于是小节末尾恰好是最后一个章节块的内部——那条划线在页面上就长在了它根本不属于的那一章名下。归错章不报错，只是让人日后翻到时以为自己记错了书。

parsers.ts 那套解析规则与本节的合并规则合起来才是「导入」这件事的全部。两者都用真实导出样本逐条验证过（三家的格式变体、跨段划线、想法去重、笔记挂载、书签与剪贴上限占位句的丢弃、重复导入、手改容错、章节归位），改任何一条之前先照 docs/设计规格书-V2.md §19.8 那份验收清单走一遍——这些规则的错法有一个共同点：**都不报错**。

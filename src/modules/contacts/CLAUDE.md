# src/modules/contacts/

> L2 | 父级: ../../CLAUDE.md

人脉与客户模块。它回答两组不同的问题：经营视角（认识谁、谁在变冷、该给谁送东西、谁还欠着谁）与交付视角（钱从哪来、货给了没、还欠谁的活、哪类问题该做成课）。两组共用一套档案机制，但客户是与人脉并列的独立物种，不共用模板。

## 成员清单

templates.ts: 两类档案、两份模板、两张 MOC 的文本生成，纯函数。一条贯穿全文件的纪律——模板文件的 type 必须留空：识别身份靠 type 不靠文件夹，模板一旦自带 type: person，它自己就会变成名录里的一个人、投喂名单上的一张嘴、记人情选人列表里的一个候选。MOC 之间的 `[[MOC-客户]]` 双链从路径常量推导，不维护第二个名字。新客户档案天然带「客户答疑」只读块；ensureClientAnswerView 只负责给存量档案补这一块，保持换行风格且幂等，不把一次迁移逻辑塞进模板字符串调用方。
identity.ts: 「谁还算数」这个问题的唯一答案处，被三条命令与十几个视图共用；选人弹窗 pickPerson 也在这里，候选跨人脉与客户两库，因为现实不分家——客户可能是朋友，熟人也可能派活给你。身份靠 type 认，唯一还认位置的是归档——「不再往来的人」需要一个退出机制，而他的身份没变，变的是你不再经营这段关系，这件事只能用位置表达。lastContactDayOf 只认日记：档案互链与 MOC 里的名录链接都不算联系，否则名录会变成一张永远全绿的假表，而这套系统里最值钱的恰恰是那个 ⚠️。
ledger.ts: 日记里三类记录的解析层。三类记录同一个入口（当天日记），靠一行的形态自动分流——带全角竖线且第二段是去/来的是账本行，任务行是待办，其余提到人名的是关键事件。学员不需要记住三种语法，他只是在写日记，档案自己会把该拿的拿走。债主只认首段的链接，这条判据与记账命令的写法严格对偶，否则「[[张三]]｜去｜替 [[李四]] 带的话」会让李四凭空背上一笔债。
createContact.ts: 「新建人脉」。三连问的顺序是设计过的——姓名是自由文本放最前，分层与方向都是封闭枚举放在后面：先付出的成本最小，中途反悔损失最少。重名一律打开而不覆盖，同名的很可能就是同一个人；默认 up 经 moc.ts 寻址，老学员更新插件后仍指向已有旧 MOC，不制造悬空新名。
recordFavor.ts: 「记人情」。四步点选变成日记里的一行标准账本行。它不认识复盘模块，只声明了一个「拿到今天的日记」的洞（DailyNoteProvider），由 main 填上。事项里的全角竖线会被清洗成半角，否则一句「他讲了 A｜B 两种方案」会把这一行多劈出一段、状态段随之错位——而错位后的行依然是合法 Markdown，不会有任何报错。
personViews.ts: 长在人物档案上的四视图（相关项目、人情账本、关键事件、待办），人脉与客户档案共用。稳定事实进 frontmatter，发生的事进日记，档案自动检索。待办勾选写回源日记，写前必须校验行号与原状态；勾选是用户在改那篇日记，不标记自写，日记的 updated 照记。
circleViews.ts: 长在人脉 MOC 上的四视图（人脉名录、投喂名单、本月生日、人情余额）。名录按 up 归属链接分组而非按分类枚举分组，这是整套系统的地基——卡片不带分类，想新分一个圈子只需建一张圈子 MOC 并把那批人的 up 指过去，名录自动多一组；换工作时整组重估靠的就是它。
client.ts: 客户模块的开荒贡献与五条命令。clientSeed 随默认开荒生成 `MOC-客户.md`；文件名与补齐后打开的入口都经 moc.ts 从 CLIENT_MOC 推导，已有旧名时沿用旧名，不并排新建第二张 MOC。原「初始化客户模块」保留为老库补齐与误删修复入口，「补齐客户答疑检索」则只迁移 type: client 的存量档案，且必须由用户明确运行，不在升级时静默改正文。
clientViews.ts: 客户与付费的十个视图。「客户答疑」以 `obsidian/QA` 标签与 frontmatter 客户双链为双重归属条件，在客户档案按更新时间倒序汇总答疑、领域与日期；正文链接不参与，避免普通提及被误收入。其余九视图保持原契约，客户名录仍按人物汇总金额与交付状态。
seed.ts: 人脉模块的开荒贡献（一个目录、一份模板、`MOC-人脉.md`）。全新库只产新名；已有旧 MOC 时沿用它，并让新建总控台正文链接到客户侧真实存在的新名或旧名。客户保持独立模板与独立 clientSeed，main 在同一次默认开荒中同时收齐两份贡献。
moc.ts: 两张内建 MOC 的命名兼容层。basenameOf 统一从路径取双链名；resolveBuiltInMocPath 按「新名已存在 → 旧名已存在 → 返回新名待创建」寻址。它不静默重命名用户笔记，只保证更新插件后的新写入继续连向真实存在的总控台。

## 链接身份

人情账本写人的双链时使用完整库内路径并以姓名作别名；姓名只是显示，路径才是身份。同名档案因此不会再由 Obsidian 的 basename 解析规则随机指向另一个人。

## 模块契约

对外暴露 contactsSeed、clientSeed、pickPerson、三个 register 函数与三个视图数组，由 main.ts 调用。main 把两份 seed 一起交给默认开荒，并把 SeedApplier 再递给客户补齐命令；两个函数类型的洞（DailyNoteProvider、SeedApplier）仍由 main 填——本模块因此不 import 复盘模块，也不 import 开荒模块。pickPerson 是反方向的同一件事：项目模块建项目时要问「这是谁委托的」，它不 import 本模块，只声明一个 PersonPicker 的洞，由 main 用这里的 pickPerson 填上。

**`client` 与 `with` 不能互换。** client 是商业契约标记，写下它等于宣告「我欠这个人一个交付」，服务区三张表全靠它过滤，「服务客户」更是直接用它反推身份。朋友一起做的事必须走 with，否则朋友会被无声注册成客户、项目会挂进「我还欠谁的交付」、结案后还会污染案例库的选题统计。

**付费流水的三条格式纪律照原样交付**（键名用中文、一笔一行不嵌套、产品名写在值里）。它们原本是为躲 Dataview 的解析行为而定的，插件自己解析时并不会踩那些坑——但学员的库里可能同时装着 Dataview，两边看到的必须是同一笔账。

**三条轴互不蕴含**：tier 是联系节奏、direction 是关系位势、gift 是主动投资意愿。发小是「密 + 平行」却不在投喂名单上，大客户是「熟 + 向上」却铁定在名单上。所以是三个字段，不是一个。

# src/modules/projects/

> L2 | 父级: ../../CLAUDE.md

项目管理模块是 ziminOS 的第一块业务能力，也是后续模块的架构样板。V2 把开荒编排搬去了 modules/setup——它横跨全库骨架并要收齐三个模块的诉求，住在这里是让物理位置对读者说谎；本模块只留下自己那份 seed。三处移植逻辑（建容器 / cardInit / transitions）逐段对应课程原有的三份 QuickAdd 脚本，移植只允许三类替换：inputPrompt → core/modals，QuickAdd 注入的 settings → ZiminosSettings，QuickAdd.obsidian 解构 → 直接 import；其余逻辑连同守卫与错误文案原样保留。这条纪律 V3 破过一次并已备案：建项目的归属由两项拆成三项，因为原脚本那两项里「自己的项目」选完仍会追问一句「和谁一起做？（自己独做就按 Esc 跳过）」——一个必须靠取消键才能走完的流程，是在拿取消当确认使。拆开之后「自己做」直接进下一步，`with` 单独成为一项，client / with 的区分反而更硬。

## 成员清单

templates.ts: 纯函数集合，无副作用，全部返回 string。MOC 的 frontmatter、共用 Base 代码块、手动模板与导航页都在此生成，其他文件一律不拼字符串。MOC Base 只读 `this.file.path/folder/asLink()`：项目文件视图收直属文件与 `up` 归属，附件视图递归收非 Markdown，全部视图合并归属与子树；四类产出（项目、领域、书籍、手动 MOC）因此字节同源，容器搬移后不改代码即自适应。导航页以公式把四态翻译成 Emoji，两种 Base 都用 `!file.inFolder("90-system")` 排除整棵系统目录树。tags 落成列表而非行内数组，与 author 写成单元素列表同因：属性类型是全库共享的一张表，写法一分叉，属性面板与查询就各说各话；写进去的字不带井号——属性里写的是标签本身。
baseMigration.ts: 存量 Bases 迁移的纯文本判定与事务内核，不依赖 Obsidian。它只把三类可证明的旧形态送到 templates 定义的终态：旧导航、旧硬编码 MOC、用户确认方案前的单表相对 MOC；没有 Base 的合法 MOC 追加终态。`MOC-人脉` 与 `MOC-客户` 虽满足普通领域 MOC 的命名和 type 形状，却是独立总控台，必须先按内建路径常量排除。当前版直接跳过，自定义/多 Base/围栏未闭合返回冲突而不猜。批处理把“尝试写入”也计入回滚栈，覆盖磁盘已提交但 Promise 随后拒绝的歧义失败，并汇总所有回滚失败。
migrateBases.ts: 「升级存量 MOC 数据库」命令的 Obsidian 编排层。扫描范围只有导航、手动 MOC 模板及命名/类型同时吻合的项目、领域、书籍容器 MOC；人脉与客户两张内建总控台即使改成统一的 `MOC-目录名` 也由身份层排除，不会被误补项目 Base。第一扇窗口展示逐文件前后文本与冲突，确认后才写盘；每次写入都再次比对预览原文，拒绝覆盖窗口停留期间的新编辑。任何一步失败都调用 baseMigration 的逆序批量回滚，再用结果窗口交代失败点与未能恢复的文件。
seed.ts: 本模块面向开荒的窗口，把「两份手动插入用的模板 + 导航页」翻译成 VaultSeed 契约。v0.19.0 起它**不再开第一个项目**：那一步会弹一个输入框问用户的名字，而那恰恰是他刚点完「初始化」、正等着看结果的一瞬间——一个凭空出现、还向他索取的弹窗，把「装好了」变成了「怎么又要我填」。开荒的职责到骨架为止，建项目本来就有一条命令。收尾改由 setup 放一次礼花：同样是告诉他成了，但不索取、不阻塞、不需要他做任何决定。随之作废的还有 templates 里的 firstProjectDescription 与 VaultSeed 的 finish 钩子——后者唯一的实现者就是这里，留着是一份没有实现的契约。它不申报任何目录：01-projects 与 90-system/Template 属于 PARA 骨架，由笔记库本身保证存在，不因某个模块存在而存在。分出这个薄文件的理由是依赖方向——开荒一旦反过来 import 本模块，「模块之间彼此不认识」就破了，而那条不变式正是「加一个模块只需在 main 多几行」的前提。
moc.ts: 「一个项目或领域的 MOC 叫什么名字」这件事的唯一出处。V3 起是 `MOC-文件夹名`，为的是让学员在文件树里一眼认出哪一篇是总览——此前父子两级写着同一个词，谁是总览全靠记。它有三个消费方：建容器照它落笔、卡片登记照它反推归属、状态流转照它认出「这是不是一篇 MOC」。Base 已改用 `this.file.asLink()` 读宿主实时身份，不再成为第四个命名消费方。读取侧一律走 resolveMocPath：先认新名，认不到再认老名，因此 V3 之前建的项目一个都不必改名。
location.ts: 附件容器位置的最小事实出口；项目/领域/资源/存档均取根目录下第一层文件夹为容器名，更深卡片不改归属；日/周/月/季/年笔记则全部折叠为单一 diary 路由。main 把结果注入 Eagle，附件模块因此不复制业务目录语义。
createContainer.ts: 「一个文件夹 + 一篇 MOC」的唯一实现，项目、领域与书籍三类容器共用。差别全部收在 ContainerKind 那张表里：落在哪个根目录、写什么 type、问不问归属、带不带正文小节骨架；Base 不在差异表里，三类容器都由 templates 注入同一份。名称合法性、防覆盖、光标落点这些规矩因此只在此处定义一次。BOOK_KIND 是这张表当初预言的第三条：书住项目目录、有 status、不问归属，只多一个「全部划线」正文落点。书的三问由 books 模块问完再装进 preset；preset 自 v0.14.0 起还能覆盖 UID 与 tags，本流程因此不认识 ISBN 或豆瓣，只认识一个数字和一串标签。
createArea.ts: 领域这一类容器的入口，薄得理直气壮——领域没有委托人，因此既不需要选人那个注入洞，也没有开荒预设。它与 createProject 并列，共用 createContainer。
createProject.ts: 项目这一类容器的入口，命令 create-project。流程本体住在 createContainer，本文件只留「项目」那份规格与两样领域没有的东西：开荒用的 preset、选人能力那个注入洞。问答顺序是设计过的：名称 → 归属 →（只有挂了人的归属才问）选人 → 概述；概述放最后，前面全是点选，中途取消不至于让人白写一段话；归属必须在动土之前问完，客户委托却没选到人时中止，不留半个空文件夹。归属这一问是整条流程里信息量最大的一步，所以选项文案直接把后果写出来——写下 client 等于把那个人注册成客户，三张客户表全靠它过滤，「周六和张三去旅游」这类私人项目必须走 with。候选人住在人脉模块，本文件不 import 它，只声明一个 PersonPicker 的洞由 main 填上。接受可选 preset 让开荒跳过全部问答——但 preset 同样要过名称校验，它源自用户输入，并不比手打的更可信。
cardInit.ts: 卡片登记，命令 init-card 与新建笔记时的自动登记。由路径反推笔记归属哪个 MOC，补齐十个标准字段并写入 up 双链。写盘只走 processFrontMatter 做字段合并，绝不整篇重写；缓存层与 processFrontMatter 回调内各判一次是否已登记，防的是缓存延迟造成的重复写入。
transitions.ts: 四条状态流转命令 project-done/paused/dropped/active，只负责移动容器与写入状态事实。可流转的身份由 MOVABLE_TYPES 一处判定，v0.12.0 起是 project 与 book 两种；它在同一次 frontmatter 写入里落 status 与 **archived**，确认框之后还会重读实时 status，不让旧计划覆盖弹窗停留期间的新事实。MOC Base 以 `this.file` 自适应新位置，流转不再搜索、替换或回滚任何数据库代码。异常后仍按磁盘上的源/目标路径决定是否反向搬移，只在 frontmatter 回调真正触达后恢复 status 与 archived。它还是全模块唯一按子树登记自写的地方：renameFile 搬走一整棵树，Obsidian 随即逐个改写卡片里指向 MOC 的全路径双链，抑制范围必须与写入真实影响面对齐，正反两次搬移都如此。
updatedMaintainer.ts: 全插件唯一常驻的编辑监听，替代原方案里由 Linter 承担的 updated 维护。它与 cardInit 共守同一张卡片——那边写出生字段，这边只碰 updated 一个字段。它最容易失控：写盘本身会再次触发 modify，故必须靠 SelfWriteGuard 断开自激回路，并用 per-file 防抖把连续击键收敛成一次写盘。「只给已有 YAML 的笔记记账、绝不主动注入 YAML」是它对用户的底线承诺；防抖把判定与落盘隔开两秒，因此守卫两头都站：事件到达时判一次决定排不排计划，落盘前再判一次决定这计划还算不算数，而「这篇笔记现在不该记账」还会反过来撤销已排下的旧计划——否则用户刚删掉的 YAML 会在两秒后自己长回来。`processFrontMatter` 外层统一经 `core/markdownViewState` 保住所有已显示分栏的滚动位置：文件安全与视图安全是两条契约，前者不会自动推出后者——而对正开着的那一篇，后者根本兑现不了，所以它压根不写，见下。

## 不写用户正开着的那一篇

`processFrontMatter` 外层那层滚动保护对**正开着的那一篇**根本兑现不了，v0.33.0 由真机改正。`modify` 来自 Obsidian 自己的保存而不是用户停手：他保存后接着敲，两秒后这一笔就落在一个脏缓冲区上，于是 Obsidian 报「已被外部修改，正在自动合并更改」并把整个文档重新灌回编辑器——一篇满是远端图片的笔记会因此把所有图片高度清零重量，视口跳到谁也没要求过的位置，用户每敲几个字被弹开一次。滚动保护救不回来：合并晚于这次写入的 Promise，而捕获下来的那个滚动值指向的版面已经不存在了。

判据因此不是「改一个字段还是整篇重写」，而是**写盘的那一刻编辑器手里有没有未保存的改动**——这一条上 updatedMaintainer 与 formatter 完全一样，所以它搬来了同一套纪律：正开着的那一篇只记下「它脏了」，等用户走开（`active-leaf-change` 与 `file-open` 都订）才补，落盘前再以实时活动文件作最后一道闸（改名会让 openPath 一时失准，这道闸也兜住它）。这也正是 `updated` 想说的那个时刻：他还在改，「最后一次修改」就还没发生，此刻写下的值下一秒就过期。防抖于是只剩它该管的那一半——那些没开着的笔记。

「走开」包含**关掉这篇笔记**，而这一格是用户点出来的，差点漏掉。关掉最后一个标签页时 `active-leaf-change` 照样触发，可 `getActiveFile()` 的官方语义是「当前视图不是 FileView 时返回**最近活动过的**文件」——也就是刚被关掉的那一篇。于是「我走开了」看上去从没发生，那笔账留在 `dirtyWhileOpen` 里，要等下一次打开任意笔记才补，中间退出 Obsidian 就丢了。**「开着」与「最近活动过」是两件事，这个洞就长在两者之差上**，所以本模块给「开在眼前的那一篇」下了定义：`activeOpenPath` ＝ 活动文件且真的显示在某个 `MarkdownView` 分栏里（判据就是要防的那件事本身——没有分栏显示它，就没有编辑器能捏着它的未保存改动）。

这个定义**只能有一个**，这一条是被自己的回归逼出来的：补上走开钩子之后测试仍然红，因为落盘前那道闸还在问「是不是活动文件」，于是钩子刚决定要写的那一笔又被挡回去——两处判断各自都对、合起来互相抵消、什么也没发生，而且不报错。现在事件处理器、走开钩子与写入闸门都从 `activeOpenPath` 取。

## 关系身份

新建容器写入 `principal/client` 关系时，目标采用完整库内路径并附 basename 别名。属性面板仍只显示姓名，但同名人脉与客户不再共享一个含糊的 basename 身份。

## 模块契约

对外暴露 projectsSeed 与七个 register 函数，由 main.ts 调用；模块内文件之间的调用不外泄。唯一的例外是 createContainer 与三份 ContainerKind：它们也被 main 直接取用，为的是给读书笔记模块填「建一个书籍容器」那个洞——books 不认识本模块，本模块也不认识 books，两边只在 main 的装配段里握一次手。

命令一律经 ctx.commands 注册，回调一律用 callback 而非 checkCallback：命令在任何笔记上都可见可点，不会凭空消失——这条纪律现在由 CommandRegistry 统一执行，模块想绕开都没有入口。它同样适用于左侧边栏：一个会自己隐身的图标比一句提示更让人困惑。点下去之后的反馈按风险分三类：create-project 与四条 transitions 的每一次拒绝都配一句中文 Notice 讲明为什么不行；migrate-moc-bases 先给逐文件差异与冲突清单，只有确认后才写；init-card 则沿用 initialize-card-note.js 的静默放行，不在管辖目录、已登记、是 MOC 本体、无活动文件都直接返回不作声。后者不是疏漏而是移植纪律：原脚本的守卫与文案一字不改，要给它补提示得先在规格里授权。

设置里的目录与时间格式是自由文本，可能被清空或写错，校验责任在读取侧而不在设置页。两者各有唯一守门人：目录经 core/folders 的 normalizeFolderPath，时间格式的空值回落收在 core/time 内部——模块把 settings.dateTimeFormat 原值递进去即可，没有哪个读取点需要、也没机会自己抄一遍兜底。

凡同时写 created 与 UID 的地方一律走 core/time 的 nowStampAndUid：原脚本先取一个 now 再派生两个字段，各取一次会在跨秒边界上让同一篇笔记的两个时间身份差一秒。

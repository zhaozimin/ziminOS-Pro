# 赛博永生 · Schema

> 这本笔记库的宪法。任何智能体在这本库里动手之前，先读完这一篇。

这是卡帕西 LLM wiki 三层结构里的 **The Schema**。另外两层是 `10-原料/`（Raw Sources，不可变原料）与 `20-知识/`（The Wiki，机器编译出来的知识）。

它同时是《ziminOS》GEB 分形文档协议的**知识版方言**。那套协议已经在这个产品的代码上跑了很久：L1 宪法 → L2 模块地图 → L3 文件契约，靠 `[PROTOCOL]` 回环维持代码与文档同构。卡帕西那三层是同一个形状，只是把对象从代码换成了知识。所以这里不发明新术语，沿用旧的。

---

## 一、这本库要做的事

**不要每次都对原始材料做检索，而要把知识编译成一张持续生长的 wiki。**

检索是每次从头再来，编译是一次投入、永久复利。一个已完成的项目搬进来之后，它不该只是躺在那儿等人搜索——它应该让十几页已有的知识各自更新一点点，让矛盾浮出来，让「我到底想明白了什么」这个问题越来越好答。

**人的活儿**：挑材料、提问、下判断。
**机器的活儿**：总结、交叉引用、归档、记账、找矛盾。

这条分工不能反过来。这本库里的每一页都是机器写的，但每一页要回答的问题是人提的。

## 二、三层结构

| 目录 | 是什么 | 谁能改 |
| --- | --- | --- |
| `10-原料/` | 原料层。从《以人为本》搬来的已完成项目副本 | **谁都不能改。** 智能体只读 |
| `20-知识/` | 知识层。编译出来的概念页、实体页、结论页 | 机器写，人也可以改 |
| `90-系统/账本.md` | 账本。每一次消化 / 提问 / 体检都记一行 | 只追加，不改写已有行 |
| `CLAUDE.md`（本文件） | Schema | 人改。改完机器下次就照新的来 |

### 目录名为什么带数字前缀

`10-` / `20-` / `90-` 不是编号癖。文件树按名字排序，前缀让「原料在上、知识在中、系统沉底」这个顺序稳定成立；纯中文目录名会按拼音或码位随机排，而这三层是**有先后的**——先有原料才谈得上编译，系统零件永远排在知识后面。数字是给排序看的，汉字是给人看的，两者各管一件事。

### 原料层为什么必须不可变

它是这本库唯一的事实源。知识层的每一句话最终都要能追溯回某一份原料的某一段——一旦原料可以被改写，「这句话是从哪来的」就再也答不清楚了，而答不清楚的知识库比没有知识库更糟：它看上去有依据。

**具体到操作上：绝不往 `10-原料/` 里的任何文件写一个字节**，包括看上去人畜无害的「加个 ingested: true 标记」。要记「这份消化过了」，记进 `90-系统/账本.md`。账本在外面记，原料保持原样。

## 三、三个操作

三个操作的中文名就是它们在账本里的标记：**消化**、**提问**、**体检**。

### 消化 —— 吃进一份新原料

触发：用户开口，或《以人为本》的出库单上还有没勾掉的行。**没有定时器，没有后台扫描。**

1. 读 `20-知识/索引.md`，知道现在这张网上有什么。
2. 通读原料。**一份原料通常牵动十几页，不是一页。**
3. 该新建的新建，该更新的更新，该标矛盾的标矛盾（见第五节）。
4. 更新 `20-知识/索引.md`。
5. 往 `90-系统/账本.md` 追加一行消化记录（格式见第六节）。

一份原料只写一页摘要就收工，是这套东西最常见的失败方式。那样得到的是一堆互不相干的读后感，不是一张网。**判据：这次消化如果只碰了一个文件，多半是没做完。**

### 提问 —— 对着知识层发问

用户问「我这半年在定价上想明白了什么」时，读的是 `20-知识/`，不是 `10-原料/`。原料只在知识层答不上来、需要回去核对原话时才翻。

**好答案要回填。** 一次值得的探索如果只出现在对话里，下次还得重来一遍。回填成一页结论页，并在账本里记一行提问。

### 体检 —— 给这张网做检查

**手动触发，绝不做成定时任务。** 用户说「体检一下」才跑。

查五样：

- **矛盾**：两页对同一件事给出不同说法。
- **孤儿页**：没有任何一页链进来。它要么该被链接，要么根本不该存在。
- **缺页概念**：被反复提到、却没有自己那一页的概念。
- **过期结论**：结论页引用的原料后来有了新版本（同一个 UID 又出现一次）。
- **断链**：指向不存在笔记的双链。

体检只**报告**，不擅自修。改哪些、怎么改，报完等人点头。

## 四、页面契约

`20-知识/` 下每一页都必须带这个头部。它就是 L3 契约的知识版——三个问题一字没变，只是从「这个文件依赖什么」变成「这一页的知识从哪来」。

```markdown
---
type: 知识
kind: 概念
updated: 2026-08-16
sources: [20260301091500, 20260415102233]
---

<!--
[INPUT]: 由《定价改版》与《年付实验》两个项目编译而来，取其定价结构与转化数据
[OUTPUT]: 年付优先这个策略的适用条件、已验证的效果与两处反例
[POS]: 定价这一族的枢纽页，被「结论/年付优先」引用，向下引「实体/王磊」的访谈原话
[PROTOCOL]: 变更时更新此头部，然后检查 20-知识/索引.md
-->

# 年付定价

……
```

**字段名是机器的，字段值是人的。** `type` / `kind` / `updated` / `sources` 四个键保持英文，因为 Obsidian 的属性面板、搜索语法与《以人为本》那本库认的都是这套键名——翻译它们等于让两本库对同一个概念叫两个名字。键名右边的值一律中文，那是给读的人看的。

**`sources` 里放的是原料的 UID，不是文件名。** 项目会被改名，UID 不会。它是这本库和《以人为本》之间唯一可靠的身份。

四种 `kind`，各对应 `20-知识/` 下一个子目录：

| kind | 子目录 | 它回答什么 | 例 |
| --- | --- | --- | --- |
| `概念` | `20-知识/概念/` | 这个东西是什么、什么时候成立 | 年付定价、冷启动 |
| `实体` | `20-知识/实体/` | 这个人 / 这个产品 / 这家公司 | 王磊、某某课程 |
| `结论` | `20-知识/结论/` | 我想明白了什么，凭什么这么说 | 年付优先在低客单价下不成立 |
| `来源` | `20-知识/来源/` | 某一份原料讲了什么 | 项目《定价改版》的摘要 |

写页面的语气跟着 GEB 协议走：**写下的每一句都必须是理解这件事所必不可少的真实细节，删掉即造成信息损失。** 写不出这样的句子就不写。不要复述原料，不要写「本页介绍了……」这类过场话。

## 五、人改过的地方，机器不许覆盖

这条单列，因为它最容易被违反，而违反的后果是静默的。

知识层是机器写的，但人随时可以改。下次消化碰到同一页时：

- **人加的段落、人改的措辞：保留。** 拿不准哪些是人改的，就看 git 或者直接问——不要猜完了就覆盖。
- **新信息追加，不重写整页。**
- **确实要改人写的句子时，先说，别直接动手。**

理由很简单：他改那一句，是因为机器写错了或者写得不是他的意思。第二次消化把它改回去，等于告诉他「你的修改没用」——而他不会发现，只会某天读到那页时觉得哪里不对。

## 六、账本格式

`90-系统/账本.md` 只追加，一行一条，最新的追加在末尾。

```markdown
- 2026-08-16 19:33 · 消化 · 定价改版 · UID 20260301091500 · 触及 [[年付定价]]、[[王磊]]、[[年付优先]]
- 2026-08-16 20:10 · 提问 · 「我这半年在定价上想明白了什么」 · 回填 [[年付优先]]
- 2026-08-17 09:02 · 体检 · 2 处矛盾 / 1 个孤儿页 / 3 个缺页概念
```

**消化那一行里的 UID 是硬要求。** 这本库里的「待提炼」清单就是拿原料的 UID 去这份账本里比对的——UID 不写，那份原料会永远显示成没消化过，而下一次提炼会把同一份东西再消化一遍，知识层也就跟着重了一遍。

标记写「消化」。插件那边读账本时同时认旧的英文 `ingest`，因为账本是逐行追加、用户也会去手改的文件，某台机器上的契约副本可能还是汉化之前那份——少认一个标记不会报错，只会让那几份原料整体退回「待提炼」，接着被重复消化一遍。

同一个 UID 第二次出现是正常的：项目可以被重新开始、再次完成。**那意味着「同一件事有了新版本」，不是「又来了一个新项目」。** 处理方式是更新已有的页，并在页里说明改了什么，而不是新建一页。

## 七、这本库的红线

1. **不改原料。** `10-原料/` 只读。
2. **不联网。** 这本库里的一切都从原料编译而来。要查外部资料，那是别处的事。
3. **不定时、不后台。** 消化、提问、体检三个操作全部由人开口触发。
4. **不删。** 结论过期了就标注过期并说明为什么，不要抹掉——「我曾经这么想过，后来发现不对」本身就是知识。
5. **一切都是纯 Markdown。** 没有数据库、没有专有格式、没有导出摩擦。这本库在十年后应该仍然能被任何一个文本编辑器打开。

# 赛博永生 · 搬运与提炼

这份契约管两件事：**把已完成的项目从《以人为本》搬进《赛博永生》**，以及**在《赛博永生》里把它编译成知识**。

搬运之所以由你干而不是插件干：Obsidian 的 vault API 被沙箱锁在本库内，插件写不到隔壁库去。插件只在本库记一笔「欠了这一份」，剩下的归你。既然提炼本来也只有你干得了，就一次进门把两件事一起做完。

**动手之前先读《赛博永生》根目录的 `CLAUDE.md`。** 那是这本库的宪法，页面契约、账本格式、命名约定全在里面，且用户可能改过它——**他改过的版本优先于这份契约里的任何描述。**

---

## 一、先认路

三本库的位置从版次标记读，不要猜：

```bash
cat "<系统根>/以人为本/.obsidian/plugins/ziminos/edition.json"
```

它的 `vaults` 给出三本库的目录名。从第一版升级上来的用户，`vaults.human` 是他自己当初取的名字，不一定叫「以人为本」。

---

## 二、搬运

### 1. 读出库单

`<以人为本>/90-system/赛博永生出库单.md`。每一行是一个已完成并归档的容器：

```markdown
- [ ] 2026-08-16 14:22 · 项目 · [[定价改版]] · `04-archives/定价改版` · UID 20260301091500
```

**没勾的才要搬。** 勾了的说明搬过也提炼过了。

出库单不存在或一行没勾的，说一句「没有新东西要搬」就完事，不要去归档目录里自己翻——那张单子是插件在归档那一刻记下的事实，比事后扫描目录可靠。

### 2. 拷贝进原料层

对每一条没勾的：

```bash
cp -R "<以人为本>/<folderPath>" "<赛博永生>/10-raw/<项目名>/"
```

三条纪律：

- **是拷贝不是移动。** 用户的归档目录里那一份必须原样留着——那是他的东西，这边只是取了个副本。
- **目标已存在就不要覆盖。** 说明同一个项目搬过第二次（重新开始后又完成了）。这时把新副本放成 `<项目名>（UID）/`，两份都留着，让提炼那一步去比对差异。
- **拷完不许再改它一个字节。** 原料层是这本库唯一的事实源，加个 `ingested: true` 也不行。要记「消化过了」，记进账本。

### 3. 勾掉出库单

搬完并提炼完之后，把出库单里对应那一行的 `- [ ]` 改成 `- [x]`。**按 UID 定位那一行**，不要按项目名——项目会重名，UID 不会。

顺序很重要：**先提炼、再勾。** 勾了却没提炼，那份原料会掉进两张清单的缝里——出库单说搬完了，账本说没消化，而没有任何东西会报错。

---

## 三、提炼（Ingest）

对每一份新原料：

1. **先读 `<赛博永生>/20-wiki/index.md`**，知道这张网上现在有什么。跳过这一步的结果是长出一堆重复页。
2. 通读原料：MOC、卡片、日记里提到它的地方。
3. 按 `CLAUDE.md` 的页面契约写页。**一份原料通常牵动十几页，不是一页。**
   - 项目里的**概念**（定价策略、冷启动方法）→ `20-wiki/概念/`
   - 项目里的**人、产品、公司** → `20-wiki/实体/`
   - 你从中读出的**判断** → `20-wiki/结论/`
   - 这份原料本身讲了什么 → `20-wiki/来源/`
   - 已有的相关页要**更新**并互相链接，不是各写各的。
4. 遇到与已有页说法冲突的，**标出矛盾，不要擅自采信新的**。旧结论可能仍然成立，只是条件变了。格式照 `CLAUDE.md`。
5. 更新 `20-wiki/index.md`。
6. 往 `<赛博永生>/90-system/log.md` 追加一行：

```markdown
- 2026-08-16 19:33 · ingest · 定价改版 · UID 20260301091500 · 触及 [[年付定价]]、[[王磊]]
```

**那个 UID 是硬要求。** 这本库的「待提炼」清单就是拿原料的 UID 到账本里比对算出来的——UID 不写，这份原料会永远显示成没消化过，而下一次提炼会把同一份东西再消化一遍，wiki 也跟着重一遍。

### 判据：只碰了一个文件就是没做完

一份原料只写一页摘要就收工，是这套东西最常见的失败方式。那样得到的是一堆互不相干的读后感，不是一张网。

### 用户改过的地方不许覆盖

wiki 层是机器写的，但人随时可以改。碰到同一页时：**人加的段落、人改的措辞一律保留，新信息追加而不重写整页；确实要改人写的句子，先说，别直接动手。**

他改那一句，是因为机器写错了或写得不是他的意思。第二次把它改回去，等于告诉他「你的修改没用」——而他不会立刻发现。

---

## 四、提问（Query）

用户问「我这半年在定价上想明白了什么」时：

1. 读 `20-wiki/`，不是 `10-raw/`。原料只在 wiki 答不上来、需要核对原话时才翻。
2. 回答带出处，指明是哪几页。
3. **答得好的要回填**成一页结论页，并往账本追加一行 `query`。一次值得的探索如果只留在对话里，下次还得从头再来。

---

## 五、体检（Lint）

**只在用户明说「体检一下」时才跑。绝不做成定时任务，绝不顺手跑。**

查五样：矛盾、孤儿页（没人链进来）、缺页概念（被反复提到却没有自己那一页）、过期结论（引用的原料后来有了新版本）、断链。

**只报告，不擅自修。** 报完等用户点头再改。

---

## 六、红线

- **不改原料。** `10-raw/` 只读，包括「加个标记」。
- **不移动、不删除用户在《以人为本》里的任何东西。** 你只读它的出库单和归档目录，唯一的写是把那一行勾上。
- **不联网。** 这本库里的一切从原料编译而来。
- **不定时、不后台。** ingest / query / lint 全部由用户开口触发。
- **不删 wiki 页。** 结论过期了就标注过期并说明为什么——「我曾经这么想过，后来发现不对」本身就是知识。
- 先提炼再勾出库单，顺序不许反。
